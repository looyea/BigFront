# mp-publish 面试题精选

> 共 15 题，覆盖 A 调试与质量 / B 审核与合规 / C 发布与灰度 / D 交付工程视角。

## 一、调试与质量（A 类）

### 1. 真机调试 2.0 解决什么问题？与 vConsole 的分工？
真机调试：把 DevTools 接到真实设备上——断点/Network/Storage 全真环境，适合"模拟器正常真机异常"（渲染差异、键盘、蓝牙、网络）；vConsole：端内浮层日志，适合体验者**自助反馈**（截图即日志）。两者共享 `wx.setEnableDebug` 生态（呼应 mp-publish 第一节表）。
**来源**：微信开发者工具官方文档《真机调试》

### 2. wx.getRealtimeLogManager 与 console.log 的区别？为什么要"主动打点"？
console 只留本地；实时日志上报云端可检索（openid/时间/页面维度过滤），是线上排障唯一抓手。主动打点策略：请求失败、授权拒绝、关键状态机迁移、`App.onError` 兜底——**日志是写给付费运维的自己**（呼应 exp-server 日志分层、node-cli 的 stderr 纪律）。
**来源**：微信小程序官方文档《实时日志》

### 3. 自动化测试在小程序怎么落地？
miniprogram-automator 连接开发者工具/CI，可编程：launch → page.navigateTo → element.tap/query → 断言（配 jest）；坑：元素异步渲染需 waitFor、模拟器与真机行为差异使 E2E 只当"冒烟"层。分层仍是金字塔：纯函数单测为主、automator 冒烟为辅（呼应 react-testing、vue-testing、exp-testing）。
**来源**：miniprogram-automator 官方文档

## 二、审核与合规（B 类）

### 4. 审核周期与"加急"机制？项目排期怎么给审核留余量？
常规 1~7 天（多数 24h 内）、每月有限次数的"加急审核"通道（用于线上故障修复等紧急场景，别当常规）；排期规则：**发布日=提审日+2 天缓冲起步**，大促/节假日前更严（人工池排队）。版本计划倒排，审核是外部依赖不是内部任务（呼应 exp-deploy 发布窗口管理）。
**来源**：微信官方《关于小程序审核时限的说明》公告

### 5. "同一个功能，别人过了我没过"，怎么应对审核不确定性？
① 逐条对照《审核规则》与驳回话术找差异（常见：类目、文案、资质）；② 用申诉通道附操作录屏与设计说明；③ 灰度策略：先小版本试水争议功能；④ 沉淀团队"驳回知识库"。成熟团队把这当作**外部质量门禁**管理而非对抗（呼应 mp-publish 第三节）。
**来源**：微信小程序审核规则官方文档；运营规范合集

### 6. 虚拟支付为什么是高危区？
iOS 侧虚拟商品（会员/课程/金币）走小程序内购触发苹果 IAP 争议——微信直接**禁令**（安卓也规范）；解决方案：实体商品、或会员/课程转 H5/App 成交。答题体现"平台规则之上的OS规则"这一层依赖认知（呼应 mp-openapi 资质表）。
**来源**：微信官方《小程序虚拟支付业务管理规范》公告

## 三、发布与灰度（C 类）

### 7. 小程序的"回退"能回到什么状态？数据兼容要注意什么？
回到上一线上版本（分钟级）；但**后端不会自动回退**——新字段/新枚举/云数据库 schema 变更若未做"向后兼容一个版本"，回退即白屏。规范：接口加字段只增不改不删（一个周期后清理）、端能力开关默认关（呼应 exp-rest 版本兼容、react-deploy 的回滚约束）。
**来源**：微信官方版本回退说明；接口兼容性通识

### 8. 为什么"配置化开关"被反复强调？给一个最小实现。
小程序无热修，回退是核弹（全量回滚粒度粗）；开关是手术刀。最小实现：登录后/冷启动拉一次 `GET /config` → 存 globalData+Storage（带版本号）→ 页面渲染分支 `flags.newCart ? ... : ...` → 后台可实时翻转。三件套约定：新模块必挂开关、开关有过期清理 SOP（呼应 mp-cloud 接缝论、exp-feature-flag 概念）。
**来源**：Feature Toggles 通用实践（Martin Fowler 体系）；社区降级方案设计帖

### 9. 体验版和线上版的域名/环境隔离最佳实践？
体验版走预发域名（也进白名单！）、后端按 referer 或自定义 header `X-Env` 区分流量做数据隔离或影子库；支付用沙箱/小额自购；体验版成员可开调试模式看日志。原则：**环境与数据隔离是提审通过率的一部分**（审核时数据错乱=体验驳回）（呼应 mp-network 面试 2）。
**来源**：多环境实践社区精选；微信官方沙箱测试说明

## 四、交付工程视角（D 类）

### 10. 把"上传提审"接进 CI，需要哪些凭证与安全考虑？
miniprogram-ci 私钥文件（在后台生成、**绑定 IP 可选**）——密钥进 CI Secret 管理（不进仓库，呼应 node-config 环境变量纪律、mp-login AppSecret 同级对待）；流水线步骤：lint+test→构建→包体红线检查→ci.upload(版本号取 git tag, 描述取 changelog)→通知群。人工点按钮只留"提审"这一下（不可自动化代提，尊重平台）（呼应 exp-deploy、vite 构建产物门禁）。
**来源**：miniprogram-ci 官方文档；CI 密钥管理通识

### 11. 上线后 24 小时你要盯哪些数字？
启动成功率、JS 异常率（对比基线）、页面打开 P75、核心转化漏斗（首页→详情→下单）、接口错误率/时延（前后端 traceId 对齐）、灰度各档差异。**每个数字配"动作阈值"**：异常率 +0.5% 触发排查、+2% 直接回滚评估（呼应 exp-perf 监控、react-performance 真实用户监控）。
**来源**：小程序后台运维中心指标说明；SRE 黄金信号通识

### 12. 面试官问"你如何理解小程序开发与 Web 开发在'完成'定义上的差别"，怎么答？
Web：代码合并部署即完成，故障可热修快回滚；小程序：**提审通过才叫完成**——质量闭环外置给平台（合规、隐私、体验皆审核项），交付链路多了"外部审批+不可热修+回退粗粒度"三个约束。因此工程实践要前移：自查清单、配置开关、兼容设计、日志可观测——把"控制不了的"用"提前准备的"对冲（呼应 exp-deploy、react-deploy 全链路对比）。
**来源**：本课综合框架（官方发布流程文档+发布工程通识）

## 补充（新专题 13-15）

### 13.  为什么"配置化开关"在小程序被反复强调？给一个最小实现。

因为端代码不能热更、改一行都要走上传+审核+用户更新周期，一旦线上出问题或被驳回，纯硬编码只能"再发一版等审核"，响应慢、回滚窗口长。把"是否启用某功能/走哪条逻辑/文案/阈值/域名环境"做成后端下发配置，就获得"不发版即时改行为"的能力，等于绕开了不可热更的限制去控制业务开关与灰度。最小实现：① app.onLaunch/onShow 拉一次 config 接口（带版本号缓存到 Storage 做冷启动兜底，秒开用旧值、异步更新）；② 存进 globalData/store，暴露 featureFlag(key)/getConfig(key)；③ 页面按 flag 决定渲染/跳转；④ 配置项含"降级开关"（新功能一键关）与"版本兼容字段"（老版本小程序遇到新配置能安全忽略）。要点：配置要可缓存、可回滚、有默认值、且校验版本——服务端下发不是免死金牌，字段缺失/类型错要兜底。这与前端"远端配置/灰度系统"同构，只是小程序因审核约束收益更大。

微信官方文档《发布流程与审核规范》；掘金《提审被拒的 12 类高频原因清单》

### 14.  体验版与线上版的域名/环境隔离最佳实践是什么？miniprogram-ci 接入要注意哪些凭证安全？

环境隔离：① 用"小程序的发布阶段(开发/体验/正式)对应不同 API 环境"——同一份代码靠编译时环境变量/不同 appid/不同配置接口下发切 baseURL，绝不让线上包连到测试库；② 在 mp 后台分别为体验/正式配置各自的服务器域名白名单（域名要备案+HTTPS）；③ 数据隔离——体验环境用独立数据库/影子数据，避免污染生产；④ 登录/支付用沙箱或独立商户配置，测试单与生产单隔离；⑤ 构建产物不带"切环境"的手改开关，靠流水线注入。miniprogram-ci 接 CI：用 CI 密钥库/环境变量存"小程序上传用的密钥文件(.key)/私有密钥、appid"，绝不提交进仓库；用机器人权限的独立上传密钥、定期轮换；CI 只做"预览/上传体验版"，"提审/全量发布"留人工审批门（发布是需审核动作，别全自动直上生产）；构建产物带版本号+变更说明，配合分阶段放量与回退。核心：环境切换自动化、凭证不外泄、发布留人工闸口。

SegmentFault《小程序版本灰度与分阶段发布实践》；知乎《审核申诉与整改沟通模板》

### 15.  面试官问"你如何理解小程序开发与 Web 开发在'完成'定义上的差别"，怎么答？

Web 的"完成"≈代码合并/部署即达所有用户（自己可控、随时回滚、灰度自定）。小程序的"完成"要多过几道不由你控制的关口，所以"写完"远不等于"上线且用户拿到"：① 审核关——要预留审核周期与"被驳回"的时间缓冲，合规（诱导分享、隐私、虚拟支付、类目资质、内容）是发布的一部分，"别人过了我没过"的审核不确定性要主动应对（申诉、措辞、开关先关）；② 更新关——用户侧有版本缓存、更新有滞后，你得考虑"新旧版本并存"（向后兼容、接口版本化、灰度放量），不像 Web 刷新即新；③ 长尾环境关——不同机型/系统/基础库版本，"最低基础库版本"没配好会出现"我这儿好好的用户那儿报错"，完成包含线上真机分布达标；④ 运维关——回退、配置降级、实时日志监控。一句话：Web 完成=功能可用，小程序完成=功能可用 ∧ 过审 ∧ 已放量到用户 ∧ 兼容长尾 ∧ 有回退兜底。把这层差异讲清，体现的是"端到端交付与发布风险意识"，而不只是把页面写出来。
