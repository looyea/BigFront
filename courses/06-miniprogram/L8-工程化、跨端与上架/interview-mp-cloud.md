# mp-cloud 面试题精选

> 共 15 题，覆盖 A 云开发机制 / B 安全与数据 / C 与自建后端对照 / D 状态管理与架构。

## 一、云开发机制（A 类）

### 1. 云开发为什么能"免域名白名单"？
wx.cloud.* 走微信自有网关通道（SDK→微信基础设施→你的云函数/资源），不是任意 https 请求，故不受"服务器域名"白名单约束；反过来也意味着**离开云 SDK 的自定义请求依然要白名单**（云内云外两套规则并存）（呼应 mp-network 第一节）。
**来源**：微信云开发官方文档《云调用与域名白名单》

### 2. 云函数的运行模型：一个请求经历什么？
事件触发→（无热容器时）冷启动拉起运行时→执行函数（超时上限可配，默认 3~20s 档）→返回 JSON→计费（GBs/调用次数）。无状态、短执行、并发弹性——设计习惯按"一个函数一个用例"（呼应 node-deploy-perf 的 Serverless 章节、exp-rest 粒度）。
**来源**：云开发官方文档《云函数基本机制》；Serverless 通用概念

### 3. 云函数本地调试怎么做？和 Express 调试差在哪？
CloudBase CLI/工具内置本地模拟（mock 云上下文与数据库），或连"云端测试环境"跑真库；差距在于：没有本地全链路 inspector 挂起体验、依赖云端触发器（定时/DB 触发器）要在控制台模拟——治本：把业务核心抽成纯函数模块，云函数只做 adapter，纯函数在本地 Vitest/Jest 测（呼应 node-testing、exp-testing 的分层可测性）。
**来源**：CloudBase CLI 官方文档《本地调试》

## 二、安全与数据（B 类）

### 4. 小程序端直接读写云数据库，安全怎么兜底？
三层：① 集合安全规则（读写条件表达式，auth.openid 体系）；② 字段级：敏感字段放仅云函数可写的集合/字段（端规则拒写）；③ 业务校验一律云函数（服务端唯一可信执行点）。规则语法写错≈全开放，上线前用"规则模拟器"跑正反用例（呼应 exp-validation 不信任客户端、exp-security）。
**来源**：云开发官方文档《数据库安全规则》

### 5. 云数据库是 MySQL 还是 Mongo？事务支持吗？
文档型（类 Mongo）：集合/文档/JSON 查询、支持聚合与**事务 API**（runTransaction，单库跨集合能力有限制）；但复杂多表 join、强一致高并发事务场景明显弱于关系型——数据模型要按"文档聚合根"重设计，不是搬 SQL 表（呼应 exp-rest 资源建模、数据库设计通识）。
**来源**：云开发官方文档《数据库概述/事务》

### 6. getTempFileURL 与直接 https 链接的区别？为什么云存储文件不能随便分享永久 URL？
云存储文件私有，临时链接带签名+有效期（默认 2h 量级）；直出永久链接=要么公开读权限（被盗链、内容泄露）要么每次现取临时链（端上做缓存映射）。头像/订单凭证类文件必须坚持临时链+有效期策略（呼应 exp-static 的文件权限、node-https-tls）。
**来源**：云开发官方文档《getTempFileURL》

## 三、与自建后端对照（C 类）

### 7. 一个订单系统，哪些模块适合云函数、哪些必须自建？
适合云：表单提交、内容 CRUD、轻量定时任务、订阅消息发送（云调用免密钥）；倾向自建：库存强一致扣减（分布式事务/锁）、风控、复杂优惠券叠加、与既有 ERP/多端中台整合。混合架构（核心自建+边缘云函数）是常见终态——面试答题体现"按一致性要求分层"的判断（呼应 exp-auth/exp-rest、react-architecture 边界）。
**来源**：云开发官方案例库；混合架构社区复盘精选

### 8. 从云开发迁移到 Express，工作量清单？
① 身份：getWXContext 的 openid → code2session+token 体系重建（mp-login 链路）；② 数据：文档导出+schema 重设计（SQL 化或留 Mongo）；③ 逻辑：云函数逐函数翻成路由+中间件（结构相近，机械工作）；④ 文件：存储桶迁移+URL 策略；⑤ 域名白名单与备案回到手动档。列清单的价值在说服老板"可逆"（呼应 09-express 全包、mp-network 第一节）。
**来源**：云开发数据导出官方文档；迁移实战帖

### 9. 云开发的成本模型与"账单惊吓"防范？
按量：调用次数/GBs/读写字数/存储/下行流量——惊吓高发在**数据库读次数**（列表页 N+1 查询）与** CDN 流量**（大文件直出）。防范：查询批量（一次多取+缓存）、热点数据端侧 TTL 缓存（mp-storage）、配额告警、压测估成本（呼应 exp-perf 容量规划、node-deploy-perf）。
**来源**：云开发计费说明；社区账单案例帖

## 四、状态管理与架构（D 类）

### 10. "服务端状态"与"客户端状态"分离在小程序怎么落地？
分离轴：是否权威在后端、是否会他人改变。落地：`api/`（云函数/request）返回的数据统一进一层缓存（store 或 SWR 风格 hook：内存+Storage 双级、stale 标记回源）；纯 UI 态（弹窗开关、表单草稿）留组件 data。mobx-miniprogram 的 computed/action 恰好承接派生与副作用（呼应 react-data-fetching、vue-pinia、mp-storage 读写路径）。
**来源**：React Query 文档（服务端状态概念源头）；mobx-miniprogram 文档

### 11. 无后端团队想做带排行榜的互动小程序，给一套完整技术方案。
端：原生/Taro 皆可；数据：云数据库（分数集合，安全规则"仅写自己 doc"防作弊+服务端云函数校验）；排行榜：定时云函数聚合快照（避免每次全表读）+ 端缓存；防刷：频率限制+内容安全云调用（msgSecCheck 检测昵称）；消息：订阅消息提醒名次变化。展示"云开发全家桶"的熟练度与边界意识（防作弊在云函数不在端）（呼应 mp-openapi 订阅、exp-security）。
**来源**：云开发排行榜官方模板；防作弊通用实践

### 12. 为什么很多公司"云开发进、Express 出"？这算失败吗？
不算——是生命周期匹配：MVP 期云开发消灭运维、验证期换自建获得掌控与多端复用。架构没有道德属性，只有当下适配度。工程上要做的是"为迁移留接缝"：业务核心云函数内也保持 handler/service 分层、数据模型文档化（呼应 react-architecture 的演进观、exp-patterns 分层）。
**来源**：技术演进通识；云开发官方"上云路径"文案对照

## 补充（新专题 13-15）

### 13.  云函数的运行模型（一个请求经历什么）？冷启动、并发、状态与自建 Express 有何不同？

一个请求：小程序端 wx.cloud.callFunction 带 data → 云网关鉴权、注入 WXContext（OPENID 等）→ 调度一个函数实例（无则冷启动：拉起运行时、加载依赖、执行入口）→ 函数内可读写云数据库/存储/调微信接口 → 返回结果（含计费时长/内存）。与 Express 的差异：① 无状态、按需拉起：别把常驻内存/全局变量当缓存（实例可能被回收或多实例并存，跨请求不共享，缓存要放数据库/存储/Redis 类外部）；② 冷启动：低频函数首次调用有拉实例延迟，靠预留实例/定时保活缓解；③ 并发由平台弹性扩，不自己管进程池；④ 单次执行有时长上限（默认几十秒）与内存规格，长任务要拆/异步化。⑤ 部署=上传函数代码，无需管服务器/域名/运维，但受限于平台（依赖体积、超时、地域、锁定）。

微信官方文档《云开发：数据库/云函数/存储》；掘金《云开发替代自建 Node 的一人项目实录》

### 14.  "云开发进、Express 出"很常见，这算失败吗？给出该迁移/该留下的判断。

不算失败，是"按阶段选工具"。云开发赢在起步：免域名/证书/运维/密钥、前后端一仓、免费额度试错快，适合 MVP、活动、小团队、无专职后端。触发迁移到自建 Express 的信号：① 复杂后端——重业务逻辑、多数据源/第三方、长任务、需要事务性强的关系模型或既有 MySQL、需要精细权限中台；② 成本结构——调用量/存储量大到云按量比自建服务器贵，或有稳定高并发；③ 锁定/合规——多端复用同一后端（还要服务 App/Web）、数据需可迁出、私有化；④ 性能/可控——需要常驻缓存、连接池、自定义中间件、灰度粒度。迁移工作清单：接口层（callFunction→HTTP 路由）、鉴权（WXContext→自解析 code2session+token）、数据库（云文档→ ORM/MySQL 或保留 Mongo）、存储（getTempFileURL→CDN/对象存储+签名 URL）、配置域名白名单/HTTPS。结论：把云开发当"加速起步、可退出的后端托管"，从第一天就别把业务逻辑写死进云函数、保持数据模型可移植，退出成本才低。

SegmentFault《云数据库权限规则与安全规则踩坑》；知乎《云函数冷启动与并发计费怎么权衡》

### 15.  无后端团队想做"带排行榜的互动小程序"，给一套完整技术方案（含防刷）。

用云开发端到端：① 数据层——用户表、分数/流水表、榜单可用"分数+时间"复合索引，或云数据库聚合；高频读排行榜用 Redis 类有序集合自建（若纯云开发则用集合 + 定期快照缓存到存储/文档，避免每次全表排序）。② 写路径——分数变更走云函数统一处理（端不直写分数），云函数里做校验与幂等。③ 实时性——榜单读加 TTL 缓存 + 定期重算，不必每次全量。④ 防刷（互动+排行榜的高危区）：服务端为准（绝不信任端上传的分数）、用 getWXContext 的 OPENID 绑定身份、限制单用户频率/上限、关键得分需"可验证的行为链"（如完成一次带签名的动作回调才计分）、异常检测（增速、设备、时间戳）、必要时接风控/验证码。⑤ 文件（头像/截图）用云存储 + getTempFileURL（临时签名 URL，防盗链、不发永久链接）。⑥ 触发用户用微信订阅消息（在主动交互时申请）。整体原则：把"计分/排名/防刷"全放服务端（云函数），端只做展示与发起，权限用 DB 安全规则兜底。

CSDN《云存储临时链接与下载域名的工程处理》；InfoQ《Serverless 在小程序后端的成本与可迁移性评估》
