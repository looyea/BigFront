# mp-storage 面试题精选

> 共 15 题，覆盖 A API 与限制 / B 存储分层设计 / C 敏感与治理 / D 跨端对照。

## 一、API 与限制（A 类）

### 1. Storage 的容量限制与隔离维度？
单 key 1MB、总量 10MB；隔离维度是"小程序 appid × 当前微信用户"——不同小程序互不可见，同一小程序不同微信号各自独立，**与手机号/账号无关**。换微信号等于换存储（呼应 mp-storage 第一节）。
**来源**：微信小程序官方文档《数据缓存》

### 2. 同步 API 和异步 API 怎么选？冷启动该注意什么？
热路径/启动路径一律异步（同步磁盘 IO 阻塞逻辑层，事件响应变慢）；只有"必须在同一同步流里拿结果"（如模块顶层初始化 token）才用同步，且越少越好。冷启动连续多个 getStorageSync 是启动耗时的常见元凶——合并成一个"信封 key"一次读出（呼应 mp-performance 启动优化）。
**来源**：小程序性能指南《启动优化》；微信开放社区同步读卡顿案例

### 3. getStorage 读一个不存在的 key 会怎样？
异步版走 fail（errMsg 含 "not exist"）？——实测行为：异步版 fail、同步版返回空字符串 ''。封装层务必统一成"返回 null/默认值"，别让调用方处理两种失败形态（呼应 mp-storage 第一节、exp-validation 归一化思想）。
**来源**：微信开放社区 getStorage 行为问答精选；官方文档

## 二、存储分层设计（B 类）

### 4. token、用户资料、草稿、字典表、图片，分别放哪？
token：Storage（持久登录态）+globalData 内存镜像；用户资料：内存/store 为准，Storage 存展示副本，冷启动恢复后回源校准；草稿：Storage+TTL（可容忍被清）；字典：Storage 长缓存+版本号失效；图片：**不进 Storage**——临时文件/文件系统/CDN 现取（呼应 mp-storage 第二、四节矩阵）。
**来源**：《小程序本地数据分层》社区架构帖；通用缓存设计原则

### 5. 设计一个缓存失效策略，给出三种以上。
① TTL 过期（写时带 e 字段，读时惰性删+启动 sweep）；② 版本号/键名带版本（`dict:v2`，结构变更整批作废）；③ 主动失效（后端下发 etag/updatedAt，比对后回源）；④ 容量驱逐（超阈值按"最近最少使用"删可重建 key——自造简易 LRU）。字典用②、草稿用①、资料用③（呼应 vue-pinia 持久化、react-data-fetching 失效策略）。
**来源**：缓存失效策略通识；社区 cache.js 方案精选

### 6. 多页面同时写同一个 Storage key 会互相覆盖吗？怎么缓解？
后写覆盖先写（无并发控制、无事务）。缓解：写"合并后的完整对象"而非读-改-写（避免竞态窗口）、防抖合并写（500ms 聚合）、关键数据交后端做权威合并（呼应 mp-setdata "别把 Storage 当数据库"）。
**来源**：微信开放社区 Storage 竞态讨论

## 三、敏感与治理（C 类）

### 7. 把用户手机号明文存 Storage 有什么风险？怎么整改？
端上任何本地存储都不该放 PII 明文：设备越狱/调试环境可读取，泄露即合规事故（个保法/GDPR 视角）。整改：本地只存脱敏展示值或 uid，明文需要时后端鉴权后接口取（带审计）；token 也应短时效+可撤销（呼应 mp-login 面试 9、exp-security）。
**来源**：《个人信息保护法》最小必要原则；小程序隐私治理官方公告

### 8. 用户反馈"清空缓存后会员身份丢了"，说明设计上错在哪？
把**权威状态**（会员等级）存进了可清除的本地层——身份永远以服务端按 uid 查询为准，本地只该存"渲染缓存"。排查话术：先看该数据被清后能否从后端完整重建，不能重建的就是放错了层（呼应 mp-storage 第二节一致性列）。
**来源**：微信开放社区账号态丢失案例讨论；前端状态分层通识

### 9. getStorageInfo 有什么实战用途？
返回 keys/currentSize/limitSize（KB）——做"缓存监控与自愈"：启动时检测用量>80% 触发 sweep 驱逐；上报体积分布发现"某个 key 塞了 900KB 列表"的异常者（呼应 mp-performance 监控）。
**来源**：微信小程序官方文档《getStorageInfo》

## 四、跨端对照（D 类）

### 10. localStorage / IndexedDB / sessionStorage / 小程序 Storage 的能力对照？
localStorage：5MB 左右、同步、字符串 only；IndexedDB：异步、MB~百MB、可存二进制/索引用查询；sessionStorage：标签页级；小程序 Storage：10MB、原生支持对象（仍序列化）、按"小程序×用户"隔离、可被平台清理。定位：介于 localStorage 与 IndexedDB 之间，但**没有事件通知（storage event）与批量事务**（呼应浏览器存储相关课程与 vue-pinia 持久化选型）。
**来源**：MDN Web Storage/IndexedDB 文档；微信小程序官方文档对照

### 11. 为什么小程序的 Storage 不能当"离线数据库"用？
无查询能力（只能整 key 读）、无事务、10MB 顶、可被清、多端不同步。真离线需求（工单巡检类）要上：文件系统存 SQLite 替代（sql.js + 文件持久化）或云开发离线 SDK——架构上优先"弱网兜底+服务端权威"，别在端上做主存储（呼应 node-fs、mp-cloud）。
**来源**：社区离线方案讨论；小程序文件系统文档

### 12. 草稿自动保存怎么做不卡输入？
输入事件防抖 500ms~1s 后异步 setStorage；草稿对象做**增量合并**（只改的字段进信封）；页面 onHide/onUnload 各补一次"立即保存"（异步回调可能赶不上销毁，用同步兜底一次）；恢复时草稿时间戳晚于服务端版本才提示续写（呼应 mp-events 防抖、react-forms 草稿方案）。
**来源**：编辑器/表单草稿实践帖；微信开放社区 onHide 保存时机问答

## 补充（新专题 13-15）

### 13.  token、用户资料、草稿、字典表、图片，分别该放哪？给一套存储选型。

按"敏感/权威/体积/生命周期"分：① token→Storage（跨启动持久、清缓存可重登兜底），端上只此一份凭据；② 用户资料（昵称头像等非敏感展示）→内存 store + 可缓存到 Storage 做秒开，但以接口为准；敏感字段不本地久留；③ 草稿（未提交、允许丢一点）→Storage（结构化 JSON，防抖写、带 TTL/版本号），别占图片空间；④ 字典表（低频变更、较大）→Storage + 版本化，随版本更新拉取覆盖；⑤ 图片/音视频等二进制→绝不当 Storage（Storage 只存字符串且占容量），走临时文件路径/本地文件管理器（文件系统 API）或每次从 CDN 加载缓存目录。核心：Storage 存"小的可序列化文本"，大二进制与敏感权威各归其位（文件系统/网络/后端）。

微信官方文档《存储 API 与容量限制》；掘金《Storage 作为缓存层的失效与配额治理》

### 14.  给一个带失效策略的本地缓存设计，列出三种以上失效方式并说明各自适用。

统一 key 前缀 + 存 `{ data, expireAt, version }` 包装。失效策略组合：① TTL 过期（expireAt 时间戳，读时判过期即弃）——适合字典、首页配置等"能容忍几分钟旧"；② 版本号/接口驱动失效（后端下发 configVersion，变了整体清/覆盖）——适合结构会变的数据；③ 手动事件失效（下单成功→清"订单列表"缓存；退出登录→清全部业务缓存，带用户维度前缀 uid_ 隔离）——适合强一致；④ LRU/容量兜底（getStorageInfo 看占用，超阈值清最旧）——防撑爆 10M；⑤ 启动/前台刷新（onShow 后台静默重拉，旧数据先渲染做秒开+更新）。落地成 cache.get(key,{ttl}) / cache.set / cache.delByPrefix / cache.clearUser。注意多页写同 key 竞争→写加"带时间戳的比较/单点写"、读缓存只作展示不作鉴权。

SegmentFault《storage 存 token 的安全边界与加密方案》；知乎《小程序分包异步化与存储预热实践》

### 15.  小程序 Storage 为什么不能当"离线数据库"？和 localStorage/IndexedDB 能力对照？

Storage：单 app 10M（含所有 key）、单 key 数据上限 1M、只存可序列化文本、同步/异步读写、无查询能力（只能按 key 取整块，不能条件查/排序/索引）、会被用户清缓存/系统回收、跨页共享但无并发控制。对照 Web：localStorage≈Storage（同步、按 key、5M、无查询）；IndexedDB≈真正的浏览器本地数据库（异步、结构化、可建索引、游标查询、容量大得多）——小程序没有 IndexedDB 的等价物，故"复杂查询/大数据集/事务"的离线库场景小程序做不了，只能拿 Storage 当 KV 缓存，需要"库"就上文件系统存 SQLite 类方案（受限）或干脆后端。结论：Storage 定位是"轻量 KV 缓存"，把业务数据权威留服务端、离线强需求要靠服务端 + 增量同步，而不是把 Storage 硬当数据库（容量、查询、可靠性三重不支持）。

CSDN《一次性数据缓存与版本迁移的坑》；InfoQ《本地缓存与服务端真相不一致的排查案例》
