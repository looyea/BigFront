# 小程序是什么与双线程架构

> 目标：在写第一行代码前，先建立"小程序到底是个什么东西"的心智。它**既不是网页(H5)，也不是原生 App，更不是简单的 WebView 套壳**。本课讲：小程序的定位与演进、和 H5 / 原生 App / 混合开发的对比、**逻辑层与渲染层分离的双线程架构**（为什么不能用 `document`/`window`）、这套架构带来的性能与安全取舍。这是理解后面 setData、分包、性能优化的地基，多处与 **04-vue / 05-react 的渲染模型**对照。

---

## 一、小程序到底是什么

- **宿主内嵌的轻量运行时**：微信（及支付宝/百度等）在 App 内提供一套"渲染 + JS 引擎 + 官方 API"，小程序代码运行在这套受控环境里；
- 对用户：无需下载安装、"用完即走"、从聊天/扫码/搜索直接进入；
- 对开发者：用类似 Web 的技术栈（WXML/WXSS/JS）开发，但**不能自由访问 DOM/BOM**，一切系统能力（支付、登录、蓝牙、定位）都要走微信提供的 `wx.*` API；
- 本质是"**微信定制的一个浏览器 + 一层原生能力桥接**"，并强制安全沙箱。

呼应 **react-jsx / vue-template-syntax**：你会觉得写法像 HTML 模板，但渲染路径完全不同（见第三节）。

---

## 二、和几种形态的对比

| | H5 网页 | 原生 App | 混合(Cordova) | 小程序 |
|---|---|---|---|---|
| 运行环境 | 浏览器 | 系统 | WebView + 插件 | 微信双线程运行时 |
| 分发 | URL | 应用商店 | 应用商店 | 平台托管、免安装 |
| 性能 | 中 | 高 | 偏低(单 WebView) | 接近原生(双线程优化) |
| 能力 | 受限浏览器 | 全系统 | JS 桥 | 仅 wx.* 受控能力 |
| 更新 | 即时 | 发版审核 | 发版 | 静默热更新 |
| 生态 | 开放 | 分散 | 分散 | 依托超级 App 流量 |

小程序取各家之长：**开发体验像 Web、性能接近原生、分发像 H5、能力像 App**——代价是**被平台规则强约束**（域名白名单、审核、隐私合规，呼应 mp-network、mp-publish）。

---

## 三、双线程架构（核心）

小程序最关键的設計：**逻辑层与渲染层跑在两个不同的线程**。

```
┌─────────────┐   setData / 事件    ┌──────────────┐
│  逻辑层      │ ◄──────────────────► │  渲染层        │
│ (JSCore /   │                      │ (WebView,     │
│  独立 JS VM)│                      │  WXML+WXSS)   │
└─────────────┘                      └──────────────┘
        ▲                                    ▲
        └──── 都通过"微信 Native 层"通信/桥接 ────┘
```
- **渲染层**：每个页面用一个 WebView 渲染 WXML/WXSS（但不给你操作 DOM 的能力）；
- **逻辑层**：JS 跑在独立的 JavaScriptCore（iOS）/ V8 类引擎里，**没有 `window`/`document`**——所以你在小程序里调 DOM API 一定报错（呼应 react-jsx：React 也让你操作"虚拟 DOM/Element"而非真实 DOM，但小程序更彻底，连虚拟 DOM 都由框架内部持有）；
- **两层靠 Native 层桥接通信**：`setData` 把逻辑层数据传到渲染层更新；用户的 `tap` 等事件从渲染层回传到逻辑层；
- 多个页面 = 多个渲染 WebView，但**共享一个逻辑线程**（这也是页面间可用 globalData 通信的基础，呼应 mp-communication）。

---

## 四、为什么要这么设计

1. **安全**：禁止任意 DOM/BOM，杜绝脚本随意跳转、注入、抓取，平台可控可审（呼应 exp-security XSS 防线）；
2. **性能**：渲染线程专心理描与合成，逻辑里跑重 JS 不至于直接卡住页面绘制（类比 **react-render-model** 的 render/commit 分离思想、Web Worker）；
3. **一致体验**：屏蔽不同机型 WebView 差异，由微信统一调度。

代价：
- **逻辑层↔渲染层通信是异步且有成本的**——`setData` 传大数据会明显卡顿（这是 mp-setdata、mp-performance 的头号优化点，呼应 react-performance "少传数据"）；
- 不能直接用 DOM，一切要"改数据驱动视图"（和 Vue/React 的声明式范式一致，呼应 vue-reactivity）。

---

## 五、开发范式一览

```js
// pages/index/index.js
Page({
  data: { msg: '你好，小程序' },        // 数据（逻辑层）
  onLoad() { /* 生命周期 */ },
  tapMe() { this.setData({ msg: '被点了' }); }  // 改数据→通知渲染层
})
```
```html
<!-- index.wxml -->
<view bindtap="tapMe">{{ msg }}</view>   <!-- 视图（渲染层） -->
```
- **改 `data` → `setData` → 渲染层更新**，而不是操作元素——这就是后面所有关卡反复用的主循环（呼应 vue-reactivity、react-usestate 的"数据驱动"）。
