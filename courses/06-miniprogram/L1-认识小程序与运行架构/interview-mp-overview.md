# mp-overview 面试题精选

> 共 15 题，覆盖 A 定位与对比 / B 双线程架构 / C 开发范式 / D 取舍·框架对照四类。

---

## 一、定位与对比（A 类）

### 1. 微信小程序和 H5、原生 App、React Native 有什么本质区别？

**答**：H5 跑在浏览器、能力受浏览器限制、URL 直达；原生 App 用系统 API、性能最好但要下载安装、走商店审核；RN/Weex 用 JS 驱动原生控件渲染。小程序是**超级 App 内嵌的受控运行时**：用类 Web 语法(WXML/WXSS/JS)，但跑在微信提供的"双线程 + 官方 API 沙箱"里——免安装、平台托管热更新、能力只能走 `wx.*`。可概括为"开发像 Web、性能接近原生、分发像 H5、能力像 App"，代价是被平台规则强约束（呼应 mp-overview 第二节）。

**来源**：微信小程序官方文档 — 技术介绍 / 开发指南、RN 对比分析

### 2. 小程序为什么能做到"免安装、即用即走"？

**答**：代码不由用户手动安装，而是在你打开时由微信**从平台按需下载并注入到其运行时**（一个加密的代码包在本地解析执行）。运行环境（渲染 WebView + JS 引擎 + Native 桥）由微信宿主统一提供，多个小程序复用同一宿主，所以启动快、无商店发版。更新也是平台侧下发新包静默替换，不经应用商店（呼应 mp-overview 第二节、mp-subpackage 按需加载）。

**来源**：微信小程序 — 运行机制、小程序架构科普

## 二、双线程架构（B 类）

### 3. 详细说说小程序的双线程架构，为什么要这么设计？

**答**：**逻辑层**（JS 跑在 iOS 的 JavaScriptCore / 安卓的 V8，不渲染界面）负责业务、数据、`wx.*` 调用；**渲染层**（每个页面一个 WebView）负责把 WXML/WXSS 画出来；两层不直接对话，**都经由微信 Native 层桥接通信**。目的：① **安全**——逻辑层拿不到 DOM/BOM，无法任意跳转/注入/抓取；② **性能**——渲染专注合成绘制，重 JS 不直接阻塞页面绘制；③ **体验一致**——屏蔽机型 WebView 差异。这与浏览器"渲染进程/脚本"分离、以及 React 的 render/commit 有相通之处（呼应 mp-overview 第三、四节、react-render-model）。

**来源**：微信小程序 — 技术架构、双线程原理科普

### 4. 多个页面的逻辑线程和渲染线程是怎么对应的？

**答**：**渲染层每个页面各有一个 WebView**（多页栈并存、切换更快、返回不重绘），但**逻辑层只有一个线程**服务整个小程序。因此页面间可以通过 `getApp().globalData`、事件等共享内存通信（都在同一逻辑线程）。这个"多渲染、单逻辑"的模型也解释了为何 `getCurrentPages()` 能同时拿到栈里多个页面对象（呼应 mp-communication、mp-route 页面栈）。

**来源**：微信小程序 — 页面与线程模型、globalData

### 5. 小程序的 setData 在双线程下到底做了什么？

**答**：`setData` 会把你在**逻辑层**改的数据**序列化后跨线程传到渲染层**，渲染层据此对新旧虚拟节点做 diff、更新真实 WebView DOM。所以它有两笔开销：跨线程通信 + 视图 diff。这就是为什么"传的数据越大、越频繁，越卡"，也为什么支持 `"a.b.c"` 路径只更新局部。它是小程序性能的牛鼻子（呼应 mp-setdata、mp-overview 第四节）。

**来源**：微信小程序 — setData、性能优化建议

## 三、开发范式（C 类）

### 6. 小程序里为什么不能直接操作 DOM？改界面应该怎么做？

**答**：逻辑层根本没有 `document`/`window`——DOM 归渲染层的 WebView 持有，出于安全与架构隔离不对 JS 开放。改界面的唯一正道是**"改数据 → `setData` → 渲染层更新"**，是声明式数据驱动（和 Vue/React 一样，不给你命令式操作元素）。个别场景用 `wx.createSelectorQuery` 查节点信息、或 `WXS` 在渲染层内响应（呼应 mp-wxml、vue-reactivity）。

**来源**：微信小程序 — 视图层更新、WXS 响应事件

### 7. WXML/WXSS/JS 分别对应 Web 里的什么？差异在哪？

**答**：WXML≈HTML 模板（但标签是 `<view>/<text>/<image>` 等组件、不能塞任意标签），WXSS≈CSS（多了 **rpx** 自适应单位、选择器受限），JS≈业务脚本（但无 DOM/BOM、用 `Page/Component` 注册生命周期）。像 Web 却又处处受平台约束。模板指令 `wx:for/wx:if` 更接近 Vue，而非 React 的 JSX 表达式（呼应 mp-wxml、mp-wxss、vue-template-syntax）。

**来源**：微信小程序 — WXML / WXSS 语法参考

## 四、架构取舍与框架对照（D 类）

### 8. 双线程相比"单 WebView"的 H5/混合开发，性能优势与劣势各是什么？

**答**：优势——渲染专注绘制、逻辑线程不被直接打断、页面多 WebView 缓存切换快、能力走原生桥更快；劣势——**逻辑层与渲染层之间的通信有额外序列化/传输成本**，滥用 setData 传大数据反而比单线程 H5 还慢。所以小程序优化的核心常是"减少跨层通信量与频率"。这是它相对 React Native 单线程通信模型的又一种权衡（呼应 mp-setdata、mp-performance）。

**来源**：微信小程序 — 性能优化建议、RN vs 小程序架构对比

### 9. 小程序、Vue、React 在"数据驱动视图"上有什么共同心智？

**答**：三者都是**声明式：UI = f(状态)**，开发者只维护数据、由框架负责把数据变化映射到视图。差异在机制：Vue 响应式拦截自动追踪依赖、React 靠 setState + 重渲染 diff、小程序靠 `setData` 显式把逻辑层数据推给渲染层做 diff。理解了这条共性，就能把 Vue/React 的心智迁移过来，但要注意**小程序的"改数据"必须显式 setData、且跨线程**（呼应 vue-reactivity-theory、react-render-model）。

**来源**：各框架官方文档 — 数据驱动 / 渲染机制

### 10. "宿主提供运行时"这种模式对开发/发布流程意味着什么？

**答**：意味着**受限但省心**：① 必须遵守平台规范（域名白名单、隐私协议、类目资质、审核）——不能像 H5 那样随意外链（呼应 mp-network、mp-publish）；② 发布走"上传→审核→灰度/全量"的平台流水线，而非自己部署服务器；③ 运行时由微信统一升级，你不必适配各机型浏览器，但要适配各版本 API 的最低基础库；④ 强绑定平台流量与规则。理解这一点对做工程化(Taro)与上架至关重要（呼应 mp-framework、mp-publish）。

**来源**：微信小程序 — 版本管理与发布、基础库兼容

### 11. 有人说"小程序就是套壳 H5"，这个说法错在哪？

**答**：错在抹平了架构差异。套壳 H5 是单个 WebView 直接跑网页、可访问 DOM、能力靠 JS 桥插件；小程序是**逻辑层与渲染层分离的双线程**、无 DOM、能力是平台原生封装的 `wx.*`、代码是加密包由宿主注入、受审核沙箱约束。两者安全性、性能模型、分发方式都不同。小程序的渲染 WebView 只是渲染层实现细节，绝不等于"一个能开 F12 的浏览器页"（呼应 mp-overview 第三、四节）。

**来源**：小程序架构 vs WebView 套壳科普、微信小程序 — 安全机制

### 12. 面试让你从零讲清一个小程序"点了个按钮界面变了"的全过程，你会怎么组织？

**答**：串双线程：① 渲染层 WebView 里用户 `tap`，事件经 Native 桥回传到**逻辑层**；② 逻辑层执行你绑定的 handler，`this.setData({x:1})`；③ setData 把变更**序列化跨线程发给渲染层**；④ 渲染层对新旧 WXML 节点 diff，更新真实视图；⑤ 若需要，再读回数据。要点出"事件是异步跨线程、setData 有通信成本、无 DOM 全靠数据驱动"。能把这条闭环讲顺，说明真正理解了小程序运行模型（呼应 mp-overview 第五节、mp-events、mp-setdata）。

**来源**：微信小程序 — 事件系统 / setData / 运行机制

## 补充（新专题 13-15）

### 13.  把「点一个按钮界面就变了」在小程序里从触发到上屏的完整链路讲清，越具体越好。

① 渲染线程捕获 tap，把事件（含 dataset/currentTarget）经 Native 发到逻辑线程；② 逻辑线程执行 onTap，改 this.data 或调 setData；③ setData 把「新数据」JSON 序列化，带上页面标识发回；④ 经 Native 中转给对应页渲染线程；⑤ 渲染线程收到后跑 WXML 的 diff（对比新旧 data 影响的节点），只更新变化的模板节点，走 CSS 重排/重绘上屏。关键考点：整条链路「跨线程至少两次往返」，所以 setData 是异步的（回调里才是新视图）、频繁/大数据 set 会把通信与 diff 成本叠加成卡顿、`setData({}, cb)` 的 cb 在视图层更新后触发而非逻辑层改完即触发。把这条讲清=讲清双线程的一切工程后果。

**来源**：微信小程序官方「运行机制/setData」与「性能注意事项」文档中对渲染/逻辑双线程与数据通信的描述。

### 14.  小程序、React Native、Flutter 三种「非纯 H5」方案在「逻辑跑在哪、视图怎么画」上的本质分野是什么？

小程序：JS 逻辑在独立 JSCore/V8 线程，视图用系统 WebView（Skyline 则是自研渲染）渲染 WXML/WXSS，二者靠 Native 中转通信——本质仍是「类 Web 技术 + 宿主托管 + 双线程隔离」。RN：JS 写逻辑，但视图映射到「原生控件」（新旧架构差别在通信桥 vs JSI 直连），不是 WebView 也不是自绘画布。Flutter：Dart 逻辑 + 自带 Skia/Impeller 引擎「自绘」每个像素（不依赖原生控件也不依赖 WebView），跨端一致性最强、包体最大。所以「小程序套壳 H5」错在：它把逻辑挪出 WebView、加了安全沙箱与宿主 API、渲染也可脱离标准 Web；但它确实复用了 Web 的排版思想（WXML/CSS 子集）。三选一的真问题永远是：一致性/性能 vs 团队技术栈 vs 生态与包体积。

**来源**：RN/Flutter 官方架构文档与小程序运行机制对照；跨端渲染模型社区综述。

### 15.  既然逻辑层是单线程、多页共享，那「全局状态、事件总线、跨页定时」要注意什么坑？

因为只有一个逻辑运行环境：① app.js 或某 util 模块里的模块级变量是「进程级单例」，多个页面/多次进入会共享同一份——用来做全局配置可以，用来做「本次会话的临时态」就会串页/脏残留，务必在合适时机重置；② 事件总线（EventBus/getApp 上的 emitter）注册与解绑要配对，页面 onUnload 不取消监听就会「返回后重复触发/内存泄漏」；③ 计时器放页面 onShow 起、onHide/onUnload 清，否则后台页 JS 仍在跑（小程序并未冻结已入栈页面逻辑）导致 set 到已隐藏页或叠加；④ onShow 里读 globalData 要容忍被别处改过。核心心智：逻辑层像一个常驻单例进程，页面只是它的多个视图窗口，别拿「页面级隔离」的假设去写全局可变状态。

**来源**：小程序运行机制（单逻辑线程/页面栈）与 globalData、事件通信的官方注意事项与社区踩坑。
