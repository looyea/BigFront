# svelte-migration-legacy 面试题精选

> 共 12 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。来源为一线面试与社区答疑的高频主题转述。

---

### 1. (A) Svelte 4 → 5 为什么能做到新旧语法同仓共存？"模式"到底钉在哪个粒度上？

**来源**：v5 迁移指南"渐进迁移"机制题

编译器逐文件判定世界观：`runes: 'auto'`（默认）下文件出现任何 rune 即按 runes 编译，否则按 legacy 编译——两套语法各自编译成同一 v5 运行时的产物，组件边界（props/事件）自动桥接。铁律：单文件内禁止混用（runes 模式文件写 `on:click` 编译报错），跨文件随意混。追问"为什么不做单文件混用"：`$: ` 与 `$derived` 在同一作用域下的依赖收集语义无法兼容——世界观冲突在文件内不可调和，按文件切是复杂度最低的折中。

### 2. (A) `export let` 迁到 `$props()` 后，"父改子随"的单向流有一个 v4 不存在的新约束，是什么？

**来源**：props 可变性收紧机制题（$bindable 设计讨论转述）

v4 里 `export let` 声明的 prop 子组件本地可重新赋值（只是不回流）；runes 世界 prop 默认**只读**，子组件要可写必须两头配合：子侧 `let { count = $bindable(0) } = $props()`，父侧 `bind:count`——否则宿主每次重渲染都会把值冲回（经典警告 "DO NOT MUTATE PROPS"）。迁移判据：v4 代码里凡是 `export let` 后紧跟本地改写/`$:` 派生自 prop 的模式，都要人判"真需求（加 $bindable）还是 bug（改本地 $state 镜像）"。

### 3. (A) `$:` 一个语法在 v5 被拆成三个出口，给出完整判型决策树。

**来源**：`$:` 语义分裂题（本课映射表深挖版）

先看形态：`$: 表达式`（无赋值）→ `$effect`（副作用）；`$: lhs = 表达式` → 再看 lhs 用途：渲染里被读 → `$derived`（纯派生）；只在事件/函数里被读、需要主动重算 → 普通函数调用或 `$derived.by`。第三层陷阱：`$:` 赋值 + 右边含函数调用副作用（隐式依赖收集在 v5 显式化后行为变化）。加分收尾：codemod 能判前两层，第三层必留标注——这正是"迁移半径"概念的具体展开。

### 4. (B) codemod 跑完 CI 就红了：某组件 `on:change` 监听全部失效。解释边界桥接为什么没兜住。

**来源**：事件桥接事故实录

桥接的方向性：legacy **宿主**监听 runes **子组件**时，子组件没有 dispatch 也没有 legacy 事件流——runes 组件的"事件"是回调 prop，legacy 宿主的 `on:change` 找的是 CustomEvent，两头对不上。反向（runes 宿主听 legacy 子组件 dispatch）同样要改：`onchange` 属性收不到 legacy dispatch 的 CustomEvent（细节以当期文档为准，考试点在于"桥接覆盖 DOM 事件、不覆盖组件通信协议变更"）。修法：组件对外协议与宿主监听语法必须在同一批 PR 里成对迁移——按文件切世界观，按**通信边**切批次。

### 5. (B) 迁移后某表单组件偶发"输入被父组件重渲染冲掉"，v4 同款代码没这问题。根因大概率在哪？

**来源**：prop 镜像模式回归题

v4 里 `export let value` + `bind:value` 到 input 的组合，子组件本地改写虽然不回流但能存活到下次父渲染前；runes 模式 prop 只读且父传值优先级更高——每次宿主重渲染 `value` 都覆盖用户输入。标准改法：`let local = $state(value)` 镜像 + `$effect` 同步外部变化（要处理双向环），或干脆 `bind:value` 全家桶（`$bindable`）。这题的普遍教训：**v4 的"将错就错"依赖了旧语义的侥幸**，迁移不是纯语法替换，是行为审计。

### 6. (B) `$$props` 与 `$$restProps` 的用法在 runes 组件里怎么重写？各给一行示例。

**来源**：rest 模式对位题（映射表零头清单展开）

`$$props`（全部 prop）→ `let props = $props()` 整包接住（但注意 L10 WC 关的坑：customElement 场景不显式解构会断属性同步——纯 Svelte 组件内合法）；`$$restProps`（除已声明外的剩余，典型用于透传 class/aria 到根节点）→ rest 模式：`let { title, ...rest } = $props()` 然后 `<div {...rest}>`。加分：v5 spread 属性对 `on*` 键的处理（`{...{onclick: fn}}` 等价 `onclick={fn}`），透传事件处理器的老 `$on:` 黑魔法在 v5 有阳间替代。

### 7. (B) 迁移 checklist：`beforeUpdate` 和 `afterUpdate` 在 v5 都没有对位 API，两类代码各自的重设计路径？

**来源**：被移除生命周期迁移实录

`afterUpdate`（DOM 更新后做事）→ `$effect`（本就在 flush 第三段 DOM 已同步后跑）或 `$effect(...); await tick()` 组合；滚动测量类还要区分"更新前抢救旧值"（`$effect.pre`，L9 锚点题）。`beforeUpdate`（状态变了 DOM 没更，常用于抓旧值）→ 没有直接对位：旧值用闭包 prev 模式在 `$effect` 里自存（`let prev; $effect(() => { use(prev); prev = x; })`），或状态提升让变更方显式携带旧值。收束金句：v5 删的不是功能，是"生命周期钩子"这个心智——换成"反应式图上的位置"心智（L9 flush 时间轴）。

### 8. (C) Vue 3（Options→Composition）、React（class→hooks）、Svelte（legacy→runes）三代迁移，哪个最难？给对比框架。

**来源**：三框架大版本迁移难度横向题（04/05 包联动收官题）

框架三维度：①共存机制——Vue 双 API 永久共存、Svelte 逐文件自动判档最工程化、React 无共存（一个组件只能一种形态）；②语义陷阱密度——React 最高（this 绑定→闭包陷阱、生命周期→effect 心智重建），Svelte 中等（`$:` 判型、prop 只读收紧），Vue 较低（composition 是加法不是替换）；③工具链——Svelte codemod 半径清晰、Vue 有官方 migration build、React 全靠社区 codemod+人肉。结论给软答案：共存与工具决定了"难"的下限，Svelte 迁移是三家里最"可编排"的；但 prop 可变性这类静默行为变更，谁家都逃不过人审。

### 9. (C) stores 在 runes 模式照常工作，官方留这条缓冲带的理由与"该不该现在迁掉"的判据？

**来源**：双响应式体系并存的边界题

理由：stores 是纯库机制（不属于编译器语法世界观），跨组件/模块外可访问/SSR 兼容这些存量价值 v5 没有等价一等物替代（全局 runes 依赖语言层提案演进），强拆只会逼团队冻结迁移。迁不迁判据：组件内部局部 `$derived` 可完全覆盖的 store → 顺手退役（少一套心智）；模块外访问、历史遗留共享 → 保留但**新代码禁增**（和语法迁移同款"增量止血"策略）。金句：缓冲带不是永久领地，是迁移节奏工具。

### 10. (D) 300 组件 8 人团队的迁移排期，老板要"不影响业务迭代"。给出方案与两个必须争取的资源承诺。

**来源**：团队推广节奏实战题（本课五步法的组织侧展开）

五步法组织化：地基周（全仓 v5 运行时+工具链，单 PR 可回滚）→ 增量止血（新文件 runes 规范入 lint/模板，零边际成本）→ 存量按叶子→容器拓扑序切批（每人每迭代 1-2 批，批 PR ≤50 文件可审）→ 收口日期钉死（写入团队 OKR，防止无限漂移）。两个资源承诺：①每批迁移 PR 的 review 时间要排进迭代容量（人审是半径外的主力，不让审的人加班审就是埋雷）；②回归测试预算——prop 可变性/事件桥接这类静默行为变更，自动化覆盖不到的要留手工回归窗口。风险对冲：豁免章（runes={false}）数量设上限并周报化，负债可视化。

### 11. (D) 你接手一个已半迁移的仓库：runes 未钉死、存量一半一半、无规范。前两周做什么？

**来源**：无主迁移现场接管题（审计三板斧的迁移版）

第 1 周摸底：codemod 前置检查（先升依赖与工具链版本对齐）；跑 `sv check` + 编译器警告全量清点（legacy 语法在 auto 模式有提示，产出"待迁文件拓扑图"）；抽样 10 个已迁文件人审质量（重点 prop 镜像与事件桥接两类静默伤——决定要不要回炉）。第 2 周立法：新建文件 runes 规范+模板；豁免章登记上限；定"通信边成对迁移"批次原则；把收口日期与 `runes: true` 钉子写进团队计划。心法复述：半迁移仓库最大的风险不是旧语法，是**双世界观下新写入的代码没人知道该用哪种**——先止增量，再清存量。

### 12. (D) 面试官压轴："如果 Svelte 6 再来一次语法革命，你的迁移方案怎么改？"

**来源**：元问题——方法论迁移性题（包收官验收）

答结构不给内容（因为没人知道 v6 语法）：①共存粒度大概率延续"按文件判档"（v5 已验证这是编排友好性最高的设计），方案骨架五步法可整体复用；②映射表换成新表，但"局部可判 vs 需理解契约"的 codemod 半径判据不变；③行为变更审计（prop 可变性这类静默伤）永远是迁移的真正成本，与语法糖多少无关——测试资产建设是跨迁移复用的护城河；④组织侧：增量止血+负债可视化两板斧通用。收尾：语法的革命会周期发生，迁移工程学只学一次——这题本身就是"可迁移性"的现场验收。
