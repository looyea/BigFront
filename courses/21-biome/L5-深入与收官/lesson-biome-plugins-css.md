# 自定义规则与扩展现状

## 一、诚实地说：插件还别指望

Biome 的**自定义规则/插件系统**（走 Wasm）长期处于 experimental/发展中。与 20-swc 成熟的 Wasm 插件、ESLint 庞大 JS 插件生态相比，「写个自己的 Biome 规则打进生产」目前**不是可靠选项**。把它当路线图上的东西，别当今天的依赖。

## 二、把「不能自定义」当设计哲学

Biome 团队明确表达过取舍：优先做「快 + 覆盖主流 + 零配置合理」，而非「无所不能的可插件化」。这意味着**配置即策略**——你能通过 biome.json 开关/调严重级别来表达团队约定，但改不了「规则集本身」。对绝大多数团队，这是优点（少造轮子、少维护自定义 lint），不是缺陷。

## 三、真实缺口怎么绕

遇到「某规则 Biome 没有、又确实要」：

1. 查官方规则清单确认是真没有还是换了名字；
2. 确无对等 → 让**个别 ESLint 插件**继续跑那一条（共存，呼应 L4 迁移）；
3. 是代码模式类需求（批量重构）→ 用 codemod（jscodeshift/rimraf 式）而非 linter。
   别为一条规则放弃引入 Biome 的整体收益。

## 四、CSS / GraphQL formatter 成熟度

Biome 对 CSS、GraphQL 有格式化支持，但相对 JS/TS 的成熟度低、部分标 experimental。用它们统一全仓排版很香（呼应 monorepo 关），但若你依赖复杂 CSS 处理（预处理、深度规则），lightningcss/postcss 生态更稳。选前先在你的真实文件上跑一遍看输出可接受。

## 五、盯住 nursery 与路线图

今天的「没有」可能明天进 nursery、后毕业进正式组。关注 nursery 组与官方博客的版本演进（如 Biome v2 带来的能力扩展），把「等它长出来」纳入预期——这也是本包反复的「主干我已会、细节回文档追」的宗旨体现。

## 小结
Biome 自定义插件系统仍 experimental、别当今日生产依赖；「不能任意自定义」是其「快+主流+零配置」的设计取舍、配置即策略；真实缺口用「确认无对等→保留个别 ESLint 插件→批量改用语义 codemod」绕过；CSS/GraphQL formatter 成熟度低于 JS、重度场景留专用工具；关注 nursery 与 v2 路线、别为一条规则弃整体收益。

## 部署预告
列一张你团队「希望有但 Biome 没有」的规则清单，逐条查证：是命名不同、是真缺、还是该用 codemod。对真缺的那几条，写清楚「保留哪个 ESLint 插件补」，形成你的「Biome 主干 + 极小 ESLint 补丁」终态蓝图。
