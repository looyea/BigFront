# 性能 · 面试题

> 共 12 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。来源为一线面试与社区答疑的高频主题转述。

### 1. (C) 为什么 React 老手转 Solid 后，很多性能优化习惯要扔掉？

React 的慢来自"状态一变整棵子树重渲染"，所以要 memo/useMemo/依赖数组去挡。Solid 组件只跑一次、更新细粒度直达 DOM，根本没有"组件重渲染"要挡——继续套用那套是空优化，反而该关注"别把粒度弄粗"。
**来源**：Solid 官方对比 React 性能叙事的高频转述。

### 2. (A) 在 Solid 里，"保住更新粒度"为什么是头号性能纪律？

因为性能全建立在"每个属性各自订阅、只更新变了的那一点"上。一旦解构 signal/props 或在 JSX 之前提前求值，就把本属于最小渲染 effect 的读取提成了组件级粗更新，粒度一粗，精确更新的优势就丢了。
**来源**：官方 components/reactivity 文档"别解构、别提前求值"再三强调点转述。

### 3. (A) createMemo 什么时候确实能提升性能，什么时候反而是负担？

能提升：把"多处读取且昂贵"的派生计算收敛成一份、依赖不变不重算、结果不变不通知下游。是负担：只是原样返回一个属性、没有任何过滤/排序/计算——官方点名这种情况多建了一个订阅者，不如直接读那个属性。
**来源**：官方对 memo"缓存计算、别过度包装"的取舍提醒转述。

### 4. (B) 一个 effect 被某个它顺手读到的信号拖着狂跑，怎么止住？

用 `untrack(() => 读它)` 就地屏蔽该次追踪，或用 `on(deps, fn, {defer})` 把依赖固定成你列出的那几个、还能跳过首次执行。本质是"我读了但不想订阅"。
**来源**：官方 untrack / on 用于精细控制依赖的典型场景转述。

### 5. (A) batch 对性能的意义是什么？store 有类似机制吗？

batch 把同步内多次写合并为一次更新，减少下游被触发的次数、避免中间态闪烁。store 一次改多个属性或 produce 里的多字段变更天然批处理，等价收益。
**来源**：官方 batch 与 store 自动批处理描述转述。

### 6. (B) 官方为什么建议"尽量别在 effect 里 set 信号"？会造成什么性能问题？

在 effect 里写信号容易触发新一轮依赖更新，可能造成额外渲染、极端情况下自我循环（infinite loop）。要算派生值应该用 memo，让"计算"和"副作用"分离，effect 只处理与外部系统的交互。
**来源**：官方 effects 文档明确警告转述为面试题。

### 7. (D) 首屏 JS 太大、TTI 慢，你在 Solid 里从哪几处下手？

路由级/重组件级 `lazy(() => import())` 做代码分割、配 Suspense 占位；数据用 `createResource` 非阻塞、让骨架与兄弟内容先出；避免在关键路径上同步 import 大依赖。核心是"只加载当前要渲染的"。
**来源**：官方 lazy / Suspense / createResource 组合的性能实践转述。

### 8. (B) 列表用普通 Array.map 渲染和用 For 有什么性能差？

`For` 是 keyed：按 item 引用建立每行自己的订阅，插入/删除/移动时只增删对应 DOM、其余复用，map 回调每项只跑一次。普通 `.map` 塞进 JSX 是一次性非响应式渲染，源数组一变整段重建，白白多销毁/创建节点。
**来源**：官方 control-flow（For→mapArray、复用）性能含义转述。

### 9. (C) 内存泄漏在 Solid 里通常从哪来？怎么防？

来自组件卸载后仍存活的引用：没清的 setInterval、事件订阅、WebSocket、第三方实例，或 `createRoot` 之外不自动回收的游离响应式作用域。防线是在 Owner 作用域里用 `onCleanup` 释放、必要时手动 dispose root。
**来源**：官方 effects/onCleanup 防内存泄漏一节转述。

### 10. (A) "props 是惰性 getter"这一点对性能为什么关键？

因为只有在真正被读取的那一刻，那次读取才被当前的最小渲染 effect 登记为依赖。你若提前把 `props.x` 取成局部变量，就退化成值快照、丢掉精确订阅，更新粒度随之变粗。惰性读取是细粒度更新的落地基础。
**来源**：官方 components 页 props 惰性求值机制的性能解读转述。

### 11. (D) 给你一个明显卡顿的大列表，你会按什么顺序排查与优化？

先看是否误用非 keyed 的 map 导致整段重建 → 换 `For`；再看每行是否解构/提前求值弄粗粒度 → 恢复惰性读；昂贵派生是否每行重复算 → 提到 memo；是否有不必要的 effect 在 set 信号造成连环更新 → 改 memo/合并 batch；最后按需 lazy 拆分子组件。
**来源**：Solid 社区性能答疑的通用排查路径转述。

### 12. (C) 既然 Solid 默认就快，为什么还要讲性能？哪些是它救不了的？

细粒度只解决"更新范围"，救不了：算法本身昂贵（N 大仍慢）、一次性加载过多代码/数据（首包/瀑布）、内存不释放、以及你亲手把粒度弄粗（解构/提前求值/无脑 memo）。这些仍需主动设计。
**来源**：对"框架快≠你的应用快"这一常见误区的辩证追问转述。
