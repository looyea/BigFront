# solid-memo 面试题精选

> 共 12 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。来源为一线面试与社区答疑的高频主题转述。

### 1. (A) createMemo 和 createEffect 都能按依赖重跑，本质区别是什么？
**来源**：派生 vs 副作用原语辨析题的转述。

memo **返回一个只读 signal 并缓存计算结果**，定位是"派生值"；effect 返回 void、只做副作用、不产出可复用的值。要一个"随依赖算出来、别处还要读"的东西用 memo；要"依赖变了就去执行一段副作用"用 effect。把派生写成 `createEffect(()=>setX(...))` 会慢一帧、多一个中间 signal、还可能自激回环。

### 2. (A) 为什么说 memo 是"惰性 + 缓存 + 即时一致"？
**来源**：memo 求值时机题的转述。

惰性：不读就不算（首次读时才求值并登记依赖）；缓存：依赖没变直接返回上次结果，不重算；即时一致：任何时刻读它拿到的都是"当前依赖下的正确值"，不像 effect 同步那样存在"源已变、派生还是旧值"的中间帧。这三点合起来让 memo 成为派生的正解。

### 3. (B) 温度示例：`createMemo(() => { if(!on()) return 'off'; return temp()+unit(); })`，on=false 时改 unit 为何不触发重算？
**来源**：动态依赖集经典题的转述。

memo 的依赖 = 本次执行**同步读到**的 signal。on=false 那次走了早返回分支，压根没读 temp/unit，所以它们不在本次依赖里，改 unit 自然不重算。这是特性（省算），排坑时要意识到"依赖随实际读路径动态变化"，别误判成 bug。

### 4. (C) React 的 useMemo 和 Solid 的 createMemo 能画等号吗？
**来源**：跨框架 memo 语义对比题的转述。

不能。React `useMemo` 是"渲染期间可选地缓存一个值"，依赖数组写错就失效/过度失效，且每次重渲都会重新评估这份 hook。Solid `createMemo` 是**响应式图里一个持续存在的派生节点**：只在真正依赖变化时重算，与"组件重不重渲"无关（组件根本不重渲）。前者是渲染期缓存优化，后者是细粒度响应式的派生源（呼应 svelte `$derived`）。

### 5. (B) 如何用 memo"收敛过度订阅/断链"？给个典型场景。
**来源**：高频源降频题的转述。

源每帧变但下游只关心一个粗粒度结论时，把结论包成 memo，下游只订阅 memo。例：`scrollY` 每像素都在变，`showTop=createMemo(()=>scrollY()>300)`，按钮显隐 effect 只订阅 `showTop` → 从 60fps 轰炸降到"布尔翻转才触发"。memo 在这里当了依赖图的"断路器"。

### 6. (A) createMemo 回调的第二个参数 init、以及 prev 各是什么？能干嘛？
**来源**：memo 回调签名题的转述。

签名是 `(prev, init) => T`：`prev` 是上一次计算结果（首次为初值），`init` 布尔标记是否首次求值。可用来做增量计算（基于旧结果合并新数据）、或首次时跳过某些昂贵操作，配合 `equals` 控制"算不算变了"。

### 7. (A) equals 选项默认是什么？设成 false 或自定义函数分别适合什么？
**来源**：memo 相等策略题的转述。

默认 `===`（结果引用/值相等就不通知下游）。`equals:false` 关闭短路——每次依赖变都通知，适合结果是不可变对象但你其实想每次都刷新下游。自定义 `(a,b)=>...` 适合"结构化相等"（数组比长度/内容、大对象比关键字段），从而在结果"语义没变"时抑制下游无谓更新。

### 8. (B) 什么时候用 memo 反而是负优化？
**来源**：memo 滥用题的转述。

一次性且极廉价的读——比如 JSX 里 `{count()*2}`，编译器本就会为该文本绑定建一个最小 effect，你再套一层 memo 只是多加一个响应式节点、多占内存与图遍历成本，收益为零。原则：**贵/复用/需断链才上 memo**，否则内联即可。

### 9. (C) 派生链 A→memo(B)→memo(C) 中，A 变了 B、C 一定都重算吗？
**来源**：memo 级联与短路题的转述。

不一定。A 变触发 B 重算，但若 B 的**结果按相等判断没变**（默认 ===），下游 C 不会被通知、不重算。memo 的短路让"源抖了但派生没实质变"的改动止步，这正是收敛传播、避免整链重算的关键。

### 10. (D) 设计：列表 1 万条，要展示"过滤后条数"和"过滤后前 20 条"，怎么组织 memo？
**来源**：派生分层设计题的转述。

一层 memo 算过滤结果 `filtered=createMemo(()=>list().filter(pred))`（贵、只算一次），下游 `count=createMemo(()=>filtered().length)`、`top=createMemo(()=>filtered().slice(0,20))` 都复用 filtered，不再各自重复 filter。pred 变了才重算 filtered，条数/前 20 随之派生，避免多处各扫一遍万级数组。

### 11. (B) 面试官写 `const m = createMemo(()=>{...}); setTimeout(()=>console.log(m()),1000)`，能拿到最新值吗？setTimeout 里读会不会建立订阅？
**来源**：memo 惰性求值与追踪窗口题的转述。

能拿到最新值——`m()` 每次调用都会确保反映当前依赖下的结果（必要时先重算）。但 setTimeout 回调不在任何同步追踪作用域里，**读它不会建立订阅**（呼应 solid-effect-tracking 的异步不追踪）：它只是取一次值，不会因依赖变化被自动再调。

### 12. (C) 不用 memo，用"组件每次重渲重算"的框架（如 React）来做派生，和 Solid memo 相比代价差在哪？
**来源**：派生重算模型对比题的转述。

React 派生随组件重渲而重算，靠 `useMemo` 手动缓存又受依赖数组约束、易失配；Solid 派生是一个常驻响应式节点，**只在真依赖变时重算、且不受任何组件重渲影响**（因为不重渲）。差别在"重算触发条件由谁定、粒度多细"：Solid 把粒度下推到每个派生值的实际依赖上（呼应 solid-overview 编译派心智）。
