# sig-mutability 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。覆盖可变/不可变两条哲学的机制、性能与工程账。

### 1. (C) 白板题：『MobX 改一个字段，React/Zustand 路线要复制一条路径』——把两边从写入到 UI 更新的完整链路各画一遍。

**来源**：转述自两家机制文档

MobX：写 `store.user.address.city=x` → observable property 的 setter 触发 → 该字段依赖表（computed+reaction+observer 节点）标脏 → 调度器批处理 → 只重跑读了 city 的表达式/组件渲染函数。Zustand：action 产新快照（immer 则复制 city→address→user→根的路径链）→ setState 换根引用 → 广播全部 listener → 每个订阅者跑 selector、产物 Object.is 比较 → 过闸者才重渲。差异一句话版：**一边通知按路径精确投递，一边广播后各自举证相关**——投递靠依赖图，举证靠比较函数，成本与风险跟着方式走。

### 2. (A) 结构共享（structural sharing）在不可变更新里省了什么、没省什么？

**来源**：https://zustand.docs.pmnd.rs/integrating-with-immutability 与 immer 文档

省：复制量（只到路径深 O(depth) 而非全树 O(n)）、比较量（未改分支同引用，selector/equality 直接短路）、内存（新旧快照共享绝大部分节点，GC 友好）。没省：**广播面**——根引用一变全体 listener 照样要跑 selector（每个订阅者至少一次函数调用+一次比较），万级订阅者场景这笔『醒来看一眼』的固定税仍在。答到『复制税可降、通知税照付』这一层，才算真懂两条路线的成本结构。

### 3. (B) 同事把 immer 产物 `state.user.address` 直接塞进第三方库并当场改了它的 city，说『反正是不可变快照安全』。指出两个错。

**来源**：转述自 immer 冻结语义高频误会

① 未 freeze 配置下 immer 产物只是『约定不可变』，运行时可写——改了之后旧快照被污染，时间旅行/diff 全失真；② 即便配了 `autoFreeze`，Object.freeze 只到这一层，address 以下深层兄弟节点仍可写（部分冻结假象）。正解：出境给会写它的库前 `structuredClone`/显式深拷，或全局开 `setAutoFreeze` 并测试期验证——金句：**不可变是纪律或冻结函数给的，不是 immer 白送的**。

### 4. (C) Vue 的响应式（可变+代理追踪）与 React 的不可变+浅比较，对『怎么知道该重渲』分别给出什么答案？各自的信任成本付在哪？

**来源**：转述自两家框架文档与 vue-reactivity-theory 呼应

Vue：渲染函数执行本身就是一次全量读取——proxy get 登记依赖，写入按 key 通知，答案=**读时证明**（我确实用到了这个 key）。信任成本付在运行时：代理层开销+隐式依赖（解构丢响应、裸对象逃逸不追踪——13 包 Vue 区的经典坑）。React：值不可自证，靠**引用供证**（新引用+浅比较），成本付在写法纪律：新引用铁律、memo/deps 人肉维护。两条路线没有免费，只有『把信任交给运行时』还是『交给语法』的口味之争——本关『两种税』总题的框架版。

### 5. (D) 编辑器类需求（画布对象图+撤销重做+协同）：可变建模派与不可变快照派怎么分工？给出边界协议。

**来源**：转述自两条哲学的混合架构实践（sig-capstone 预演）

分工：画布内对象图走可变（MobX/自研 observable——拖拽高频、对象图天然、细粒度通知收益大）；**撤销栈与协同日志走不可变语义**——不存全量快照（太大），存 onPatch 聚合的操作序列（patch 本身就是『不可变的事件账』），撤销=逆序应用逆 patch。边界协议：① 提交点（松手/命令完成）才从可变世界抽 toJS 记账；② 回放/对账时整树重建灌回可变域。这就是 L4『结果账 vs 事件账』的落地件——两条哲学各管各的时间观。

### 6. (A) Redux 早期『reducer 必须纯、state 必须不可变』的三条纪律各自防的是什么？immer 版 reducer 违反字面还是违反精神？

**来源**：转述自 Redux 官方风格指南与社区论战

防：① 纯函数防『replay/派生不确定』（同 action 双跑结果一致是时间旅行与测试的根基）；② 不可变防『引用相等失效』（组件比较、memo、selector 缓存全建立在旧引用不变上）；③ 单一出口（只有 reducer 能改 state）防『谁改的』审计失焦。immer 版 `state => { draft.a++ }` 字面可变、精神全守：产物仍是新不可变快照、仍是纯函数语义（无外部可见突变）、出口仍单一——**纪律约束的是可观察行为，不是语法形态**，这是理解 immer 被官方接纳的关键一层。

### 7. (B) `useMemo(() => heavy(props.a), [props.a])` 在可变上游下失灵，为什么？给出上游与本地两边的两种修法。

**来源**：转述自 React 引用比较高频事故

上游每次重渲传同一个可变对象（就地改内容不换引用），deps 浅比较判『没变』→ memo 永不重算——**引用是身份证，就地改等于换了人没换证**。修法：① 上游守不可变（每次产新引用，immer 最省事）；② 本地换身份证明：deps 改内容键（`[props.a.id, props.a.version]`）或深比较（成本回到浅比较想省的那笔账）。延伸金句：React 全家桶（memo/deps/useCallback）预设不可变，混进一个可变上游就是静默错值——比报错更难查。

### 8. (C) solid store 的 mutable 版（mutable + map 变更）在细粒度订阅下为何反而比 immutable 版省？它付出了什么？

**来源**：https://docs.solidjs.com/reference/store-comparison

省：无路径复制——就地改 map 键+按键订阅通知，复制税归零（细粒度图到位后，不可变剩下的主要成本就是复制）；付出：① 旧值即消失——撤销/diff/对账要另建账本（q5 同款的『看过去税』）；② 出边界危险——mutable store 的引用漏进普通比较世界就翻车，官方文档直接建议出境前 immutable() 转快照。**『性能粒度与值纪律可分开点菜』的标本题**，答出两笔付出才算看懂。

### 9. (D) 面试官追问：『所以到底哪个快？』——给出你的三段式回答：在什么维度、用什么量具、什么条件下谁赢。

**来源**：转述自 JS frameworks benchmark 与本关实验设计

维度：写入 CPU、通知 CPU、内存分配/GC 压力、渲染触发面——四笔分开量（bundlephobia 式『先测量再吵架』）；量具：benchmark 场景分档（小状态高频/大树小改/大改广域）；结论：大树小改+订阅者多→可变路线赢（通知精确）；高频小状态+需要历史→不可变+结构共享赢（复制浅+旧值白送）；广域大改→两边打平（通知面≈广播面，复制与代理都躲不掉）。满分段句：**问『哪个快』前先报场景参数，否则任何答案都对一半**。

### 10. (A) 为什么说『不可变让 bug 难写，可变让 bug 难查』各成立一半？给一个反向案例打破口诀。

**来源**：转述自两家调试体验讨论

成立：不可变下越界写入要么冻结报错要么引用不对齐立刻显形（防御性）；可变下写入无声、追查『谁改的』要断点/代理/devtools。反例（给口诀卸妆）：① 不可变的头号 bug『忘换新引用』既不报错也不显形（Zustand 就地改静默失败——za-core 铁律 1），完全符合『难查』；② 可变+严格模式（MobX enforceActions）把越界写变成即时 throw，『难写』也追回一城。结论段：**报错时机取决于围栏配置，不取决于阵营天性**——口诀是均值不是定律。

### 11. (C) 把『时间旅行』需求分别交给三家实现：Redux devTools、MobX+onPatch、Zustand 手写快照栈——各自存的到底是什么？

**来源**：转述自三家能力对照

Redux：action 日志+重放 reducer 重建状态（存**事件**，状态派生——纯函数保证重放确定性）；MobX：patch 序列+逆操作应用（也是存**事件**，但重放要逆序处理可变域，协同分叉更麻烦）；Zustand 手写栈：真存**快照引用**（结构共享让每份快照只多一条路径的内存——不可变阵营的看家本账）。同一个需求三种存法，账本体积与恢复复杂度完全不同：事件紧凑但重放要确定性（纯函数/可逆），快照奢侈但恢复 O(1) 查表——这题是『旧值还在不在』的工程显影。

### 12. (B) 团队从 MobX 投奔 Redux 全家桶后性能反而退化，火焰图里全是 selector 执行，给两条对症优化与一条治本架构项。

**来源**：转述自迁移性能社区案例

对症：① 重订阅者收窄 selector+reselect/结构化 memo（利用 immer 结构共享让未改分支引用不变、比较短路）；② 高频字段剥出独立 store/独立组件（缩小广播面，za-patterns 的频率分层同款）。治本：通知模型换血——细粒度订阅（solid/MobX 回去一个，或 React 侧引入 signal 层如 Legend-State/Preact signals），承认『大树高频细改』本来就是可变+点对点通知的主场。**迁移前先对场景账，别带着画布去表单的世界**。

### 13. (D) 设计题：给一个 200 字段的大表单库，选哲学并说理由（提示：字段级联动、需要 dirty-check 提交 diff、用户要撤销）。

**来源**：转述自综合选型题（sig-scenarios 预热）

主案可变/细粒度（MobX 或 solid store）：字段独立读写、联动=表达式依赖、订阅面天然字段级；dirty-check 用 onSnapshot/patch 对账或维护 touched 集合；撤销这项要补票——按提交聚合 patch 栈入撤销历史（q5 边界协议）。翻盘案：字段数实际可枚举+表单值要随请求整体快照出境、撤销要求高保真——不可变+结构共享（每版表单快照驻留，提交时对两棵引用树 diff 出 dirty 字段更省心）。满分点在：**三个需求逐条对账本，最后给出主案+翻盘条件**，而不是喊阵营。

### 14. (A) React Compiler 的自动 memo 建立在什么假设上？它对『不可变 vs 可变』之争构成什么影响？

**来源**：转述自 React Compiler 文档与社区解读

假设：**规则性可变不存在**——编译器依赖『props/state 在渲染期间不被就地改、跨渲染不可变』做记忆化推断（文档明言 mutate 渲染中创建的局部对象可以、mutate 传入的引用不行）。影响两向：① 加固不可变阵营（纪律被编译器强制，违反者产生错值——从最佳实践升级成编译前提）；② 削弱『人肉 memo 税』但没削弱『引用即身份』——就地改仍不可信，Mutable 派在 React 内的路更窄而非更宽。答出『编译器让守纪律的人受益、让破坏纪律的人暴雷』这句即到位。

### 15. (C) 收官辩论题：『信号的崛起宣告了不可变 vs 可变战争的终结』——你接不接？给出接三成与驳七成的完整论证。

**来源**：转述自全包横向（本关与 L2/L9 的合议题）

接的三成：signal 生态确实让『容器读写』取代了『要不要复制树』成为第一性问题——在细粒度图里，写入语义（set 替换 or 就地改）退化为局部实现选择，性能大头被依赖图接管；各家实现也确实都同时支持两种容器内容（signal(obj) 里改字段还是换对象皆可）。驳的七成：① 战争的真正战线是**通知模型**（广播+比较 vs 依赖图+投递），signal 只是给后者立了旗帜，MobX 早就住在这边；② 不可变的『旧值还在』红利（撤销/对账/结构化共享比较）不因换原语而消失——signal 里存可变对象，看过去照样瞎；③ 工程生态（React 全家桶的引用身份依赖）短期仍押不可变。终版判词：**signal 赢了『怎么通知』的辩论，没接管『要不要留旧值』的辩论**——两条战线别合并记账。
