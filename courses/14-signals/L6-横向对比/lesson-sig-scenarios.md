# sig-scenarios：选型决策树——什么状态放什么家

> 目标：把 L1 开的『状态分层』处方长成完整的决策树：组件局部态/跨组件共享态/业务域模型/服务端缓存态/URL 态各归谁管；给出四强+React Query+框架内置的分工矩阵；产出能直接写进团队规范的五条结论（呼应 sig-server、za-patterns、sig-map）

## 一、先把『状态』这锅粥分碗

前端语境里的『状态』至少混着五种东西，**选型失败的第一原因就是拿一把钥匙开五把锁**：

| 碗 | 定义 | 例 | 生命周期 |
|---|---|---|---|
| 组件局部态 | 只有自己和子组件关心 | 输入框焦点、下拉开合 | 组件卸载即弃 |
| 跨组件共享态（UI 态） | 多处读、客户端是事实源 | 主题、侧栏、弹窗队列、向导步骤 | 页面会话级 |
| 业务域模型 | 有行为与不变量的对象图 | 购物车+价格规则、播放器队列 | 随业务实体 |
| 服务端缓存态 | 事实源在服务端，本地只是缓存 | 用户列表、文章详情 | 随失效策略 |
| URL 态 | 要能分享/刷新/回退 | 页码、筛选器、标签页索引 | 随链接 |

五碗各有一个灵魂问题：局部态问『还有谁读？』；共享态问『谁同时读』；域模型问『行为跟不跟数据走』；缓存态问『谁是事实源』；URL 态问『这个状态要不要出现在地址栏』。**决策树就是这五个问题按顺序排队。**

## 二、决策树（主干两问加例外）

```
这份状态要活过刷新/被分享吗？
 ├─ 要 → URL 态（router searchParams / 序列化库），别进 store 再同步出去
 └─ 不要
    事实源在服务端吗？
     ├─ 是 → 服务端缓存态：React Query/SWR 托管，store 里只放筛选/游标等『请求参数』
     └─ 否 → 只有一个组件读？
              ├─ 是 → useState/useReducer，让它就地老死，进全局 store 才是技术债
              └─ 否 → 状态有行为与不变量、形状是对象图？
                       ├─ 是 → 业务域模型：MobX 类 store（或 Zustand+actions 的轻量版）
                       └─ 否 → 跨组件共享态：Zustand（或框架内置 signal，见 §四）
```

例外条款三条（树答不完的地方）：持久化偏好（主题类共享态+persist 落 localStorage——za-middleware 的边界：小、plain、非敏感）；高频瞬态（拖拽坐标——共享态但走 transient 通道，za-patterns 的形状）；SSR 全案（模块单例失效，走框架注入/请求级 store——L8 sig-server 专关）。**规范写到例外层才算能落地。**

## 三、分工矩阵：谁管哪段，谁不管什么

| 玩家 | 管这段 | 别让它管这个 |
|---|---|---|
| useState/Context | 组件局部/低频小共享 | 高频、粒度订阅、组件树外消费 |
| Zustand | 客户端共享态+持久化+跨边界总线 | 服务端缓存（双事实源三宗罪，za-patterns 面试 q7） |
| MobX | 行为丰富的业务域对象图 | 一次性脚本状态（四件套围栏白建） |
| RxJS | 事件编排/异步流程（管『生成状态的过程』） | 当状态容器（shareReplay 三宗罪，vs-streams q8） |
| React Query/SWR | 服务端缓存+失效+加载态 | UI 开关态（它不管你的抽屉） |
| 框架内置（signals/runes/ref） | 框架工程内的一切细粒度态 | 跨框架共享库（内置信号出不了自家框架） |

读表口诀：**RxJS 管过程、Query 管远端、MobX 管领域、Zustand 管共享、useState 管局部、内置管本家**——一格不重叠才是好架构，重叠处必有双事实源惨案。

## 四、框架内置信号的挤占：第三方 store 还剩多少地？

Angular signals/Svelte runes/Vue ref 在自家框架里已覆盖『共享态+细粒度』的多数场景（不引库、zoneless 友好、编译器优化）——第三方状态库的**保留地**收缩到四处：① 跨框架复用（一份 store 喂 React+Vue 微前端）；② React 的细粒度缺口（signals 提案未落地前，React 内置仍靠重渲）；③ 成熟中间件生态（persist/devtools/RTK 互操作）；④ 域模型的成建制方案（MobX 的对象图+patch）。选型时的诚实问法不是『哪个库好』而是——**『你的场景在保留地里吗？不在就用框架内置』**。

## 五、写进团队规范的五条（直接抄走）

1. **新状态默认本地**：进全局 store 必须在 PR 描述写『谁同时读』（答不出=不进）；
2. **服务端数据禁止复制进客户端 store**：组件从 Query 读，store 只存请求参数与 UI 态；违反者按 bug 修（双事实源零容忍）；
3. **URL 是共享态第一公民**：可分享/回退的状态先设计 query 参数，store 同步要写明理由；
4. **业务域模型集中一个 MobX 式 store（或等效），胶水 UI 态集中一个 Zustand 式 store，禁止互存对方字段**——出境走快照（toJS/getState），入境走构造/fromJS（L4 边界协议的规范条文版）；
5. **状态库选型按 §三 矩阵执行，迁移须过『三问』评审**（看过去？密更新？团队税？——sig-mutability 口诀的制度化）。

五条背后是同一个元原则：**工具跟着状态形状走**——先分类再选型，分错了类，四强谁都救不了你。

> 🚀 部署预告：本关练习=拿你手头真实项目开一张『状态户口表』：列出全部全局状态，逐条按五碗归类+标注当前归属与应然归属，红字写出三处最严重的错住——这张表就是你们团队的选型规范初稿。
