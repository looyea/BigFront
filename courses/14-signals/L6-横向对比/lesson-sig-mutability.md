# sig-mutability：可变与不可变——两条更新哲学

> 目标：把『MobX 代理可变+路径通知』与『Redux/Zustand 不可变+快照比较』两条路线的性能账、心智账、工程账各算一遍；看清 Immer 怎么成为两边的和事佬；回答『React 为什么历史上选了不可变』——并理解这个选择在 hooks 时代正在被动摇（呼应 mobx-core、za-middleware、solid-stores）

## 一、两条路线的机制回放（各三句话）

**可变路线（MobX）**：① 状态就地改，读写都经过代理（Observable）；② 变化按**路径**广播（这个字段的 setter 被触发）；③ 订阅者按路径认领（谁读过这个字段谁醒来）。派生与渲染的更新是**点对点通知**，粒度天然是字段/表达式级。

**不可变路线（Redux/Zustand）**：① 状态是冻结的快照树，改=造新树（至少新沿路节点）；② 变化按**根**广播（store 有了新快照）；③ 订阅者**自证**相关性（跑你的 selector 比较产物）。更新是**广播+各自过滤**，粒度取决于你切的 selector。

同一个 `user.address.city = 'Hangzhou'`：左边=改一个字段+通知读过 city 的人；右边=复制 city→address→user→根四节点+全广播+各自比较。**语义相同，账本完全不同**——本关就是来对账的。

## 二、性能账：三个典型场景的胜负手

| 场景 | 可变胜在哪 | 不可变胜在哪 |
|---|---|---|
| 大树改一叶（万行表格改一格） | 通知只达该格订阅者；复制成本 O(1) | ——（复制 O(路径深)，广播+万条 selector 比较是税） |
| 高频小状态（拖拽、计时） | 就地写零垃圾 | 结构共享+引用比较让『没碰的分支』免费跳过 |
| 时间旅行/撤销（回放、diff、协同步） | 要额外记账（onPatch 补票，L4 见过） | **天生白送**：历史快照都在（旧引用没被改过），diff/回放=引用互查 |

第三行是分水岭：不可变的『每个快照都还在』不是修辞，是**数学性质**（持久化数据结构）。撤销、重做、乐观回滚、状态 diff、跨端对账——这些『看过去』的需求在不可变路线是查表，在可变路线是自建账本。MobX 生态用 patch 监听补，redux-undo 对前者是原生——**两条哲学各自的功能天花板由『旧值还在不在』决定**。

## 三、心智账：调试与协作谁更贵

可变路线的心智模型贴近原生 JS（这就是对象！），上手零成本；代价是**隔空改状态（spooky action at a distance）**——任何拿着引用的代码都能改，『谁改的』要靠 devtools/约定（enforceActions 严格模式=给自由上围栏，围栏成本就是 L4 说的禁忌清单）。不可变路线反过来：上手先学『不能改，要造』（加上新引用陷阱、浅比较困惑——za-core 前六题全在这），但**改状态必须经过 set/dispatch 独木桥**，审计与调试天然简单：断点打在唯一入口，日志记的是引用不是值。

一句收拢：**可变把成本付在『协作纪律』，不可变把成本付在『语法学习』**——团队哪个税便宜交哪个，这就是 mobx-react『禁忌清单 vs 显式容器』对账本的哲学版。

## 四、Immer：两边语法层的一次和离

za-middleware 已拆过机制，这里只站队形：**Immer = 可变语法 + 不可变产物 + 结构共享**。它承认了『人们就是想直接改』（对可变阵营心智的让步），保住了『旧快照还在』（对不可变阵营性质的坚持）。于是出现有趣的合流：

- MobX 用户看 immer：『代理拦截写』的思想它也有，只是一个通知人、一个抄新账；
- Zustand/Redux 用户看 immer：语法上回到『直接改』，纪律上没破不可变——**教程里那句「用 immer 就不用想不可变」既是解药也是麻醉**（新引用铁律仍在，只是 immer 代守）；
- 两边共同的盲区：immer 产物结构共享意味着**深层节点可能是旧引用**——『不可变=全深冻结』直觉不成立，`s.a.b === prev.a.b` 未改动时为 true，这既是性能红利也是想当然的坑（sig-perf 挂号）。

Solid 的 store（createStore/immutable 双 API）是第三种标本：**同一状态源提供两种更新语义**，细粒度订阅下可变 map 反而更省（无整树复制）——它证明『性能粒度』与『值纪律』其实是可以分开点的两道菜。

## 五、React 为什么历史上选了不可变

三个历史铆钉：① **协调器需要可比较的 props/state**——reconcile 的判定是引用/浅比较（shouldComponentUpdate、memo 的默认浅比较、deps 数组），如果状态就地改，React 无从知道『该不该重渲』（Vue 系用『渲染函数即订阅者』解决，React 选择了『值不可信、引用才可信』）；② **更新是异步批量的**——事件里改了还在旧 state 对象上，必须造新的才能保证批内一致（`set(s => ...)` 函数式队列同款理由）；③ **生态假设**——时间旅行调试、Redux 中间件重放、SSR 快照序列化，全建立在『每个时刻的值都还活着』上。

当代的裂缝同样值得讲清：React Compiler 自动 memo（削弱铆钉①的『人肉引用纪律』）、Signals 提案走的是『容器+读订阅』（另一条路：不比较引用，靠依赖图精确定位）——**『React 必须不可变』是工程选择不是逻辑必然**，选择正在被侵蚀但还没翻案。面试答这题的最后一段拿这句收尾即满分。

## 六、选型三问（收尾成口诀）

1. **要不要看过去？**（撤销/回放/对账/乐观回滚）——要，不可变阵营（或愿意为可变自建 patch 账本）；
2. **更新多密、树多大？**——高频细粒度且状态形状是图/树混合，可变或 signal 细粒度占优（大表单、画布）；
3. **团队付哪种税？**——新人多、流动性大，不可变的『入口收敛』纪律护身；JS 老手多、业务建模重，可变的对象图建模顺手（mobx-stores 的建模红利）。

三问没有指向同一阵营很正常——那就是 mixed 架构的信号（域内 MobX 建模+全局快照出边界交 Redux 式 store），L6 sig-scenarios 与 13 包『混用边界』的口径一致：**边界协议（toJS/getState 快照出境）比站队重要**。

> 🚀 部署预告：动手实验：同一个万行表格组件，分别用『MobX observable 改一格』与『immer 造新树改一格』实装，React Profiler 数渲染次数、Performance 面板量单次更新耗时——两本账各记一次，胜过读本关三遍。
