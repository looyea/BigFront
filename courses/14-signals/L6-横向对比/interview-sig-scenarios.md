# sig-scenarios 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。覆盖状态分层决策树、分工矩阵与团队规范落地。

### 1. (C) 面试官扔出一句『我们项目用 Zustand 管所有状态』，你追问哪三个问题来评估这个决定？

**来源**：转述自本关决策树（反问式答题模板）

① 『所有状态里服务端数据占多少？』——Query 该管的我见你们 store 里有吗（双事实源探测）；② 『有没有撤销/回滚类需求？它们现在怎么做的？』——不可变补票或域模型错配探测；③ 『地址栏里看得见的状态（筛选/页码/标签页）谁在管？』——URL 态探测。三个追问覆盖决策树前三问，问完基本能给这个『一把梭』方案定位病灶——这题考的是你有没有决策树，不是黑不黑 Zustand。

### 2. (A) 『客户端状态 vs 服务端状态』的分界判据是什么？为什么说后者『默认过期』而前者『默认永久』？

**来源**：转述自 React Query 文档概念篇（sig-server 预热）

判据=**事实源位置**：服务端状态是远端数据的本地缓存，别的标签页/设备/用户可能随时改变它——所以它的正确默认是『新鲜度有限、会过期、要重取』（stale-while-revalidate 心智）；客户端状态（主题、抽屉）没有任何外部源会改它——默认永久直到你改。默认值相反导致两套工具：Query 的 staleTime/gcTime/invalidation vs store 的 set/persist。**把服务端状态当客户端状态管=手动同步地狱**（sig-server 展开），这题是其概念地基。

### 3. (B) 团队把用户偏好（主题/字号/侧栏）同时存在于三处：localStorage 手读、Zustand persist、一个 Context——刷新后偶发主题闪变，诊断并收敛。

**来源**：转述自多源状态并存的典型事故

诊断：三个事实源读写的时序不同（手读在模块加载、persist rehydrate 异步、Context 初值来自手读）——竞态下某帧拿到旧值即闪。收敛：偏好只归 Zustand persist 一家（partialize 白名单+version/migrate），Context 若保留只作注入通道不作存储，手读代码全部删除；首帧闪烁用 skipHydration+挂载后再渲（SSR 版方案同族）。金句：**闪变=多源竞态的显影，修法永远是消灭源不是对齐源**。

### 4. (D) 设计向导表单（5 步、中途退出要能恢复、最终一次性提交）：给出五碗分工。

**来源**：转述自综合设计题（za-patterns 面试第 6 题的完整版）

步骤索引+已完成步：URL 态或 persist 共享态（要刷新活→persist；要可分享→URL）；各步表单值：草稿 persist 进共享态（小、plain、非敏感达标——za-middleware 边界条款），步内联动用局部 useState+受控提升；已提交数据：提交成功后归服务端，Query 失效重取；提交动作：action 内 async 编排（简单 await 或 RxJS 管重试/取消）。陷阱项：**别把整棵表单树实时写进 Query cache 当草稿**（服务端缓存不是草稿箱）。

### 5. (C) MobX 域模型与 Zustand 共享态的『禁止互存字段』规范（第 4 条），防的具体事故是什么？各给一个。

**来源**：转述自本关规范与 L4 边界协议

存反方向（Zustand 里放 observable 引用）：不可变世界的 `Object.is`/JSON/immer 遇见 Proxy——比较、序列化、冻结三件套集体失灵（za-middleware q14 的镜像，L4『代理不过界』）；存正方向（MobX store 里存快照副本）：双事实源——UI 改了快照，域模型不认账，patch/撤销链断裂。合规通道：出境 `toJS()` 单向送、入境经构造器 fromJS 重建——**跨家只传值不传引用，传引用等于传事故**。

### 6. (B) 有人说『React Query 也能 setQueryData，我的列表编辑状态直接改缓存就行，不需要 Zustand』——指出两处分界错误。

**来源**：转述自 Query 与 UI 态边界高频论战

① 编辑态（草稿值、选中行、正在展开的抽屉）是客户端事实源，服务端并不认识『你草稿里的半成品』——塞进 queryKey 缓存等于污染远端镜像，invalidate 一来全蒸发；② setQueryData 的语义是『乐观更新远端真相的占位』，不是『顺便存点 UI 状态』——混用后失效策略不敢开（怕杀草稿）。正解：草稿进 Zustand/局部态，提交时 onSuccess→invalidate——**Query 的数据域只放『服务器同意过的事』**。

### 7. (A) 『URL 是共享态第一公民』在 SPA 路由与 RSC/服务端框架下各怎么实现？状态放 URL 的成本是什么？

**来源**：转述自 react-router 参数与框架数据方案（kit-load-universal 对照）

SPA：searchParams 为源+序列化库（nuqs 类）做类型化读写，store 顶多是缓存镜像；RSC/全栈框架：直接 searchParams prop 下传+服务器重渲，URL 态天然 SSR 安全（这正是框架数据方案吃掉一半客户端状态库的场景）。成本三条：长度上限（大数组进不得）、隐私（URL 会进日志/Referer——敏感筛选条件慎入）、表达力（对象图压不平）——**能序列化成短字符串的才配进 URL**，这是判据也是上限。

### 8. (D) 给一个 30 人前端团队的仓库写『状态管理目录结构与命名规范』，让分层规则物理可见。

**来源**：转述自规范落地题（本关第五条的团队化）

样案：`src/state/ui/`（Zustand 式共享态，一域一 store）、`src/domain/`（MobX 式模型+services，禁 import UI store）、`src/api/`（Query hooks 与 schema，禁 setQueryData 存 UI 态）、`src/url/`（searchParams 序列化）；import 规则：domain 不 import ui、api 不 import domain（数据出境到组件层才合体）——eslint boundaries/no-restricted-imports 强制；PR 模板加一栏『新状态的碗籍与同读名单』。考点：把决策树翻译成**目录+lint 规则**，规范才活得过长篇大论的 wiki。

### 9. (C) 框架内置信号挤压下，『新项目还要不要引第三方状态库』的完整回答怎么给？

**来源**：转述自本关第四节保留地清单

框架优先+保留地核查：React（无内置 signal、hooks 为主干）→ Zustand/Jotai 仍有结构性价值（粒度订阅+组件外消费）；Angular/Svelte/Vue 项目 → 默认内置信号，触发保留地四条件之一才引外库：跨框架复用、成熟中间件生态、重域模型成建制、团队既有资产；引库同时按分工矩阵划界（Query/RxJS 各管各段）。答出『先问框架、再问保留地、最后划界』三步流程即高分——纯立场输出（必须用/不许用）都是减分。

### 10. (A) 决策树把『只有一个组件读』判给 useState，但组件树里这个状态要透传五层 props——规则错了吗？

**来源**：转述自本关与 react-context 的衔接题

规则没错，暴露的是**透传痛与全局化的经典误判**：五层透传的解法梯子——① children/插槽重组件（多数场景到此为止）；② Context 仅作注入通道（低频整读可）；③ 组件级 store（Zustand vanilla+局部 Provider/zustand-traditional，粒度与局部生命周期兼得）；④ 最次才是全局 store。判据始终一以贯之：『谁同时读』——梯子前三级都在**不改变状态碗籍**的前提下解决传递问题，跳级到全局=为了省脚程把行李寄丢失。

### 11. (B) 审查 AI 生成的 dashboard 代码：每图表一个 Zustand store 存服务端数据、useEffect 里 fetch 后 set。按矩阵给三条重构。

**来源**：转述自 AI 代码审查场景（时代真题）

① 服务端数据整体迁 React Query（fetch+缓存+失效+竞态一并带走），store 三处清零；② 残留的图表交互态（brush 选区、图例开关）合并成**一个** dashboard-ui store——一图一 store 是『组件实例本地态』被错发全局户口，选区联动需要共享才升格；③ 刷新参数/时间范围改 URL 态（dashboard 的分享刚需）。考点：AI 常把『能跑的状态』全塞最显眼的 store——人的价值就在重跑决策树。

### 12. (D) 需求：多标签页编辑器，同一文档在两个 tab 打开，各自有未保存草稿，还要提示冲突。分碗并设计跨 tab 通道。

**来源**：转述自综合场景（za-middleware q10 的升版）

分碗：文档正文=服务端（Query+版本）；每 tab 的草稿=**会话级**共享态且不可互相覆盖（sessionStorage 按 tab 或 IndexedDB+tabId 键——persist 的 storage 工厂选型时刻）；冲突提示=跨 tab 通信态（BroadcastChannel 广播『我在编辑 docX+草稿指纹』，收方比对弹提示）。反模式：草稿走 localStorage 全局键——两 tab 互踩（persist 默认方案的粒度盲区）。金句：**共享态还要再分『页内共享』与『跨 tab 共享』，前者用对介质是后者的前提**。

### 13. (C) 用『状态活多久』给五碗排序，并说明为什么生命周期是比『谁读』更硬的分碗依据。

**来源**：转述自本关表格第四列的展开

排序（短→长）：局部态（组件生死）→ 高频瞬态（手势生死）→ 共享 UI 态（页面会话）→ URL 态（链接生死，可超会话）→ 持久化偏好（浏览器生死）→ 服务端缓存（远端数据生死，本地随失效）。『谁读』决定**放哪**，『活多久』决定**能不能放那**：读面小的状态错放进长命 store，比反过来更糟（局部脏数据永生+跨会话泄漏）；URL/persist 的寿命甚至是需求本体（刷新后向导步数必须还在）。两轴合判才完整——单轴论是新手选型的第二特征。

### 14. (A) 本关口诀『RxJS 管过程、Query 管远端、MobX 管领域、Zustand 管共享、useState 管局部、内置管本家』——抽掉库名复述一遍架构原则。

**来源**：转述自本关第三节矩阵

无库版：**过程与状态分离（编排逻辑不占状态户口）；远端数据以缓存+失效托管，禁手工复制；行为丰富的领域实体内聚成模型；跨组件共享集中管理且入口收敛；局部状态默认就地；平台能力优先于第三方抽象**。六条对六个工具——工具是原则的实例化，原则不随库更替失效；面试官要求『别聊库聊思想』时，交的就是这份翻译。

### 15. (D) 终面题：『给你全新项目，从零定状态架构』——用不超过十句话给完整方案。

**来源**：转述自全包收束（sig-capstone/sig-roadmap 的前置答案）

样卷：① 先开状态户口表分五碗；② 服务端数据全收 React Query，客户端 store 禁复制；③ 可分享/回退态进 URL；④ 局部态默认 useState，进全局须答辩『谁同时读』；⑤ 共享 UI 态一个 Zustand 式 store+persist/devtools 三件套；⑥ 重业务域建 MobX 式模型家，与 UI 家只传快照；⑦ 异步编排出 DOM 事件用 RxJS（或 fetch+Abort 薄封装），结果落状态层；⑧ 高频瞬态走 transient 订阅绕渲染；⑨ SSR 场景 store 请求级实例化禁模块单例；⑩ 规则以目录+lint 强制，按季复审。评分点在**闭环**：分类→归属→边界→例外→执行机制，一条不缺。
