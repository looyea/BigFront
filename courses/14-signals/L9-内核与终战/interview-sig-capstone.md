# sig-capstone 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。围绕『四实现对照实验』的测量学、归因纪律与把项目讲成证据链的面试表达。

### 1. (D) 面试官说『讲讲你做过的技术选型』——用本实验回答，前 30 秒必须出现的三个要素是什么？

**来源**：转述自本关 §二协议与 §五报告模板的口试化

三要素：① **受控设计**（同 UI 同剧本同测量时点，变量只剩范式）——证明你知道对比的前提是可比；② **带预测的测量**（测前写预期、测后 diff）——证明你测量是为了更新认知不是为了赢辩论；③ **形状归因结论**（每项成绩配一句『X 性质贴合/违背 Y 决策』+一条条件句『需求变 Z 就推翻』）——证明你产出的是可迁移判据不是站队宣言。90% 的候选人栽在只有结论没有仪器；先报『我的对照实验协议是……』的，面试官会自动把这道题升级为开放讨论——这局就赢了。

### 2. (A) 实验为什么坚持『同一份操作剧本脚本化』而不是四版各跑一遍『差不多的手动操作』？

**来源**：转述自本关 §二常量清单

渲染计数与耗时是**路径敏感**测量：手动操作四版必然差（这版多点一次过滤、那版拖拽距离不同），差异被操作噪声淹没——脚本（Playwright 录制或代码驱动 store 序列）保证四版吃进的输入序列逐帧相同，输出差异才能归因给范式。更深一层：剧本本身就是**需求形状的编码**——『拖 1 张卡 200px』编码高频段、『切过滤』编码派生重算，脚本评审即需求评审。顺带防一个作弊面：手测时人会无意识地对自己的实现温柔（快的那次多测两遍）。

### 3. (B) 你的 Zustand 版拖拽段渲染次数爆表（预测未翻车，实测爆表）。按 §四预告给三刀修法，并说明哪刀收益最大。

**来源**：转述自本关 §四 Zustand 预告与 za-patterns 频率分层

三刀：① **拆独立 store**——dragPos 从主 store 搬出，主 store 组件零感知（订阅面物理隔离，通常收益最大：一次 set 的广播域从全应用缩到拖拽层）；② **窄 selector+useShallow**——卡片只订自己那条 task，位置层组件订 dragPos；③ **落库节流**——pointermove 期间只写局部信号/DOM transform，pointerup 才 set 进 store（瞬态与事实分离）。收益排序按病灶广播面积定：多数项目①最大，但若列表组件都订了 whole-state 则②先救命。面试亮点：主动说『**先测再拆，顺序由数据定**』——恰好呼应本关『一次只改一处』纪律的实验版。

### 4. (C) 报告里 Solid 版 DOM 写操作数=12、Zustand 版 commit×组件=3400——把这两个数放进同一张表合法吗？

**来源**：转述自本关 §三第 2 栏与 sig-perf q6 量纲论

有条件合法，条件写进表注：两个数**都不能直接当『快』**，它们是『工作量』的两种计量——DOM 写 12 次意味着重工作几乎为零，3400 次 commit 里含大量『渲染但 DOM 未变』的白工；合法的比较要落到共同终点：**真实帧时间**（两版各录 Performance，拖拽段 fps 曲线同图对比）与**用户可感延迟**。表里并放三样：范式各自的原生工作量单位+统一的帧时间裁判——只放 commit vs DOM 写并宣称冠军，是本实验最典型的伪测量（选项 D『四版同数直接比』在 quiz q4 已判死刑）。

### 5. (A) 包体积栏实测：Zustand 版 1.1KB 增量的账一眼可认，RxJS 版却出现『同样是引库，有的版本只涨 8KB 有的涨 60KB』。给分辨方法与背后的摇树机制差。

**来源**：转述自本关 §三第 3 栏与 sig-size 摇树四环

分辨法：看 import 语句形态——`rxjs` 深路径/顶层具名导入（摇树友好：operator 各自独立模块）vs `rxjs/Rx` 全量补丁式导入（焊死 barrel，四环断在第一环）；build 报告（visualizer treemap）直接点名哪些 operator 进了包。机制差：RxJS 的体积是**用法价**（每个 operator 单独可摇，账单随管道复杂度线性走）而 MobX 是**硬账**（17KB 整块，代理机制无法按需拆），Zustand 几乎无账——三本账在体积栏的形态各不相同，所以表注要写『本栏测的不是库大小而是你的用法』。预测翻车高发区：有人以为『RxJS 很大』，实测只用三个 operator 时比某些『轻量』方案还小。

### 6. (D) 四版都完赛了，需求追加『协同编辑：别人的光标实时显示』。用 §五条件句纪律预判哪个版本最先推倒重来、哪个版本白捡便宜？

**来源**：转述自本关 §五结论模板与全包形状论的预测题

白捡：RxJS 版——远端光标=纯事件流（websocket 帧→throttle→按 user 分窗渲染），它的『第二种人格』区段天然覆盖，Zustand 版反而要给高频瞬态重搭分层。最先推倒：MobX 版最悬——每个远端光标一个 observable 对象+高频写，代理拦截与 reaction 调度在 60fps 写入下账单难估（协作税+通知税双付），且跨用户状态进域模型网的边界要先重画。Zustand/signals 居中：前者补拖拽期已有的分层设施，后者一个 signal-per-cursor 直白但要自管生命周期。**答题结构比结论重要：性质识别（高频/瞬态/外部驱动）→ 各家决策对照 → 条件句**——这份报告答辩时的必考题。

### 7. (B) 统计卡『先跳一下再归位』的现象在四版都出现了。这还算选型差异吗？给归因与『共性症状说明了什么』的两层回答。

**来源**：转述自本关 §三第 4 栏考题与其的全包收拢义

归因：完成任务 set 后，聚合统计走的是『先响应直接依赖、后响应间接依赖』的中间帧——本质是 §internals 验尸单第 3 条（glitch/缝合态）在应用层的显形：多数工业库对**同库内**有对策（MobX 两阶段、Solid 调度），但统计卡若跨了两个数据源（store+Query）或依赖了**未批处理的自定义 set 链**，中间帧照样漏出。共性症状的两层回答：① 它不稀释选型差异（各库治 glitches 的能力本就是评分项），② 但它是**需求单自带的照妖镜**——四版都栽说明测试用例命中了『多源聚合』这个所有库管不到的应用层缝隙，修它在架构不在库（同源化：统计改由单一派生源计算）。面试听到『四版都有就说明题出错了』的答法要扣分：题没错，**缝存在，选型就是选缝隙的位置和大小**。

### 8. (C) 胶水栏里 MobX 版被记了 RootStore 组装、observer 包裹两类，signals(Solid) 版记了什么？谁的胶水更隐蔽？

**来源**：转述自本关 §三第 1 栏与 §四 signals 预告

signals 版的胶水：跨页统计要**手搭模块级 signal 的组织规范**（谁创建、谁 dispose、页面间共享怎么接线——『重新发现 Jotai 解决的问题』那句的记账版），外加 Solid 特有的 Owner 生命周期胶水。更隐蔽的是 signals 版：MobX 的 observer 漏包裹**当场显形**（组件不更新，逼你修），模块级 signal 的退订遗漏**无声运行**（泄漏要等内存曲线说话，sig-perf 坑3 的换皮）。胶水分类学结论：**显性胶水收代码量，隐性胶水收运行时**——报告表注里给隐性胶水单开『何时显形』列，这栏的深意是『行数只是胶水的利息，纪律才是本金』。

### 9. (A) 有人质疑：四版性能差异一半来自『实现者对库的熟悉度不均』。实验协议怎么自证或认错？

**来源**：转述自本关 §二有效性前提的方法论审计

承认这是**学习曲线污染**，协议里三条缓解：① 实现前先过对应关卡+完成 homework（保证基线熟悉度对称——本包排序把 capstone 放最后正是为此）；② §四『预告即陷阱检测』的镜像用法：每位实现者写自己版本的『预期翻车点』，测后核对翻的是不是预期那个——熟悉度不足的症状（翻在没预期的地方）被单列标注而非混进总分；③ 结论纪律禁冠军句——本来就不许把『我版更慢』直接说成『此库更慢』。彻底消除需要多位实现者交叉写同一库（成本高），**报告如实标注残余偏差**：这是入门工程实验和真基准测试（benchmark harness 如 js-framework-benchmark）的分界线，说清这条线本身就是高分答案。

### 10. (B) size-limit 栏跑完：MobX 版超预算红了。直接动作是换 Zustand 吗？给三步决策链。

**来源**：转述自本关 §三第 3 栏与 sig-size 三本账、za-core 替换成本论

三步：① 先审**账记对没对**——超的是下载账还是执行账？低端机 MobX 代理初始化是执行账大头，光看 bundle 会漏（sig-size 三本账各查）；② 再审**这 15KB 买回了什么**——若域模型区段（任务依赖、子任务树）只有 MobX 顺手，换库=把体积账换成重写账+协作税账（sig-migrate §一的『凭什么迁』反向应用）；③ 决策档位：换（该页确无域模型需求）/缩（mobx-lite 手动 makeObservable 只给用到的字段，砍代理覆盖面）/拆（MobX 只管看板域、其余 Zustand——回到 sig-migrate §四共存分工线，体积按路由分包）。直接换库是拿 CI 报告当圣旨——**红绿灯是测量的开始不是结论**。

### 11. (D) 给报告加第五栏『重构安全性』：设计一个 15 分钟的机械操作当测试，并预言四版成绩序。

**来源**：转述自本关 §五模板的栏位扩展（za-patterns 演化成本的期末化）

操作：『把任务的 priority 字段从字符串枚举改成数字优先级，统计卡增加按优先级加权计数』——改动穿透：定义/持久化（旧数据兼容）/派生/渲染/过滤五层。预言序：**Zustand 最顺**（改 selector+迁移 version 处理即可，类型系统全程护航——不可变+纯函数的可 grep 红利）；signals 居中（派生链清晰但持久化字段的旧版兼容要手写）；MobX 中偏下（action 面散在对象方法里，改动要顺着实例图找调用方，可 grep 性差=sig-mutability 协作税的具体形态）；RxJS 垫底（管道里的字段变换散落各 map，改一个字段=全管道类型红点大扫除——它本来就不是为『字段演化频繁』选的）。成绩与『代码像图纸还是像机器』的隐喻挂钩，即演化成本栏的测量学表达。

### 12. (C) 四份实现跑完，有人说『其实差异没宣传的那么大，都是 set→通知→渲染』。用全包知识给这句话一个『对在哪里、错在哪里』的两段式反驳。

**来源**：转述自本关 §五与 sig-map/L1 世界观的期末合拢

对在：图元层面完全正确——值容器+订阅集+通知三件套四库同款（internals 关亲手写过），互相翻 API 一周上手，这支撑着『不必神话任何一家』。错在：把工程决策放在图元层，等于说『都是行列式的机器』后随便选台电脑——差异全在 §internals 验尸单的五条档位（批处理策略/粒度/惰性/契约/调试面）+ 范式税单（可变协作税 vs 不可变语法税 vs 流心智税 vs 框架锁定）+ 生态位（谁跟你的路由/数据层/团队栈咬合）。**记分卡测的正是『图元之下的档位差会不会露出应用表面』**——答案会（拖拽段两个数量级），所以这句话对一半、错的那一半是本包九成的篇幅。

### 13. (A) 实验协议里『不许混搭』和现实工程里『MobX+Zustand 共存、Query+store 双轨』矛盾吗？给两者的分工边界。

**来源**：转述自本关 §二与 sig-migrate §四、sig-server §三的三关缝合

不矛盾，差在**问题的位置**：实验是测量学——变量控制为『纯范式』才能产出归因干净的记分卡（研究用对照鼠）；工程是经济学——一个应用里不同状态区段形状不同，混搭是**逐区段选主场**（sig-scenarios 决策树的存在意义），此时协议换成共存纪律（跨边单向显式过值、清场协议、体积加总重测）。混淆两者的错误形态：拿实验结论说『所以生产必须二选一』，或拿共存现实说『所以实验无意义』。报告结论段的满分句式：**『实验答的是范式在纯种条件下的上限表现，生产答的是混合环境下各区段的形状匹配』**——L8 与本关合成的一枚双面币。

### 14. (B) 调试栏里只有 RxJS 版的『先跳一下』在 10 分钟内被归因成功。另三版各自超时卡在哪？给对应的本包补课点。

**来源**：转述自本关 §三第 4 栏与 sig-debug 工具链的对照审计

Zustand 版：卡在**没有现成的『谁改了』通道**——devtools 动作流看得见 dispatch 但聚合派生在 selector 里无栈可追，补课点=sig-debug 手写审计环（prev===next,deepEq 分型日志）；MobX 版：卡在 **spy 事件洪流**——action/reaction 全量事件里找不到统计卡那条派生链，补课点=spy 过滤+derivation 命名规范（mobx-core 的 debug 约定）；Solid 版：卡在**取证单位陌生**——没有 commit 可数，signals graph devtools 的读依赖追踪不直观，补课点=sig-perf q6 的 MutationObserver 定位术。反讽注记写进报告：RxJS 成功恰因『先跳一下』本质是**时序问题**，而 marble/时间轴是四家工具里唯一把时序当一等公民的——工具与病同形则归因快，这本身是『调试体验=工具链与故障形状的对齐度』的实证。

### 15. (D) 老板只给你 10 分钟汇报这次终战，不许带电脑。给一张口述提纲：四栏各一数字一归因、一句总结论、一个下一步。

**来源**：转述自本关全篇的输出化考核（面试与工程沟通的双重期末）

提纲样张（数字按实测替换）：① 代码量——『Zustand 核心 210 行最少，但 RxJS 胶水 60 行 vs MobX 胶水 90 行，分栏后差距从 3 倍缩到 1.4 倍』；② 渲染——『拖拽段统一裁判帧时间：Solid 60fps 全程、Zustand 未分层版 22fps——分层修法后 55fps，差距的主语是架构不是库』；③ 体积——『三本账口径下只有 MobX 版超预算，决策是拆分不是换库（附三步链）』；④ 调试——『一题故障四版归因时长 4/9/11/12 分钟，与工具和故障形状的对齐度相关』；总结论一句：**『没有冠军库，只有形状匹配度，各区段冠军不同』**；下一步一个：把拖拽段修法与统计卡缝合态修复落进主仓，配回归断言（sig-perf 流程终点）。评分点：每个数字带口径、每个归因带机制、总结论反口号——这份提纲同时就是你简历那条项目经历的 STAR 剧本。
