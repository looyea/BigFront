# sig-internals 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。从 60 行手写实现出发的响应式系统原理深水区，工业实现溢价清单的逐项验证。

### 1. (A) 白板题『写一个最小的 signal』——60 秒版本要出现哪三个零件？各自被省略后的症状？

**来源**：转述自本关 §一 §二的三件套直译

三零件：① **闭包盒**（`let value` + getter 函数）——省略退化成普通变量，无处挂订阅；② **订阅集**（`subs = new Set()`）——省略后写入无人知晓，变回轮询世界；③ **当前观察者指针**（`CURRENT`）——省略后要靠手工 declareDependencies（React 的 deps 数组就是这档：显式但会漏）。追问『写通知怎么写』答 forEach 直推——到这里全部面试官就知道你写过。**这题考的不是默写，是有没有把『读挂边、写广播』当成本能**。

### 2. (A) 为什么 computed 重跑前要先 `deps.forEach(d => d.subs.delete(compute))` 清旧边？给一个不清理会出错的场景。

**来源**：转述自本关 §二清旧边注释与条件依赖语义

场景：`compute = () => flag() ? a() : b()`。flag 为 true 时建立边 compute→a；flag 翻 false 后重跑，新边连到 b——**旧边 a→compute 若不删，a 以后再写仍然通知 compute**：它已经不读 a 了却在替 a 心跳，轻则白算（性能），重则 compute 里的副作用被幽灵触发（correctness）。订阅图是**最近一次执行的快照**不是历史并集——删除式重建（先全删后重连）vs 差分式更新是实现的两个档位，60 行版选删除式：正确但每轮全清，工业版（Fine-Grained Reactivity 论文）用版本号差分省掉清连开销。

### 3. (B) 你的 mini 实现里 `signal.set` 直接 forEach 通知，测出 effect 里再 set 同一 signal 会栈溢出。给两层修法并说明工业库选哪层。

**来源**：转述自本关 §三第 2 条环检测

修法一（检测层）：通知前把当前执行栈记入 running 标记，set 时发现『正在通知的订阅者就在我的调用栈上』→ 抛带环路径的报错（MobX reactivity-check 的做法：**宁可 crash 不可无声**）；修法二（语义层）：同轮重入合并——本轮结束前对同一 signal 的多次 set 只在末尾算一次（Solid 调度器的做法：不报错但改变语义，effect 看到的可能是更晚的值）。工业选层看场景：应用代码里的环 99% 是 bug（选报错），高频写入源（鼠标追踪、音频表）里节流合并是刚需（选调度）——**『检测报错』和『调度合并』不是谁高级，是治两种病**。

### 4. (C) Vue 早期静态分析依赖、MobX/Solid 运行时追踪、React deps 数组手工声明——三代依赖收集方案的取舍轴是什么？

**来源**：转述自本关 §二『图是跑出来的』与 quiz q4 展开

取舍轴=**正确性与成本的错开位置**：手工声明（React）零运行时成本、条件依赖要人肉维护（漏一个字段=闭包读旧值的经典 bug）；静态分析（早期 Vue 模板编译）无运行时追踪成本、但只能看到模板语法层，条件依赖与跨函数追踪直接放弃（`_.get` 类调用是盲区）；运行时追踪（MobX/Solid/本实现）正确性最高（读即依赖天然精确）、代价是每次读带 `if (CURRENT)` 分支+清边重建。判词三代：**声明式把债给人、分析式把债给编译器、追踪式把债给性能**——面试说清『没有免费档，只有债搬去哪』即过线。

### 5. (D) 给 mini-signal 加批处理：要求 `a.set(1); b.set(2)` 之间 effect 一次不跑、set 全部返回后统一跑。写伪代码并说明引入的新问题。

**来源**：转述自本关 §三第 1 条的动手展开

伪代码：`let QUEUE = null; function batch(fn) { QUEUE = new Set(); try { fn(); } finally { const q = QUEUE; QUEUE = null; q.forEach(run); } }`；set 时 `QUEUE ? QUEUE.add(subs...) : 立即跑`。新问题三个：① **读旧值悖论**——batch 内 `signal()` 读到的是新值还是旧值？（答新值：写即改 value、只是通知延迟——但要向用户讲清）；② 嵌套 batch 的队列归属；③ **忘记关 batch 的异常安全**（finally 清队列，同 §二命门教训）。MobX 的 `transaction`、Solid 的微任务调度各是这三问题的工业化答案——**批处理省掉的是中间态，引入的是时序语义题**。

### 6. (A) glitch-free 的『先集齐、再拓扑跑』——用菱形依赖（a→b、a→c、b+c→d）说明 forEach 直推为什么必然 glitch，拓扑跑怎么救？

**来源**：转述自本关 §三第 3 条（13 包图语言的压轴回收）

直推路径：a.set → 按注册顺序通知 b、c → 假设 b 先跑，b 新 c 旧时 d 被 b 的通知链拉起来跑一遍（**glitch 帧**），c 跑完 d 再跑第二遍——d 在中间帧读到不一致世界。拓扑方案：两阶段——标记阶段沿订阅集把所有可达者标脏（不跑），执行阶段按**依赖深度排序**跑（b、c 同层先跑完，d 下一层）——d 每次醒来看到的世界都是本轮全貌。成本：每轮多一次全图遍历+排序（或用维护好的链表近似拓扑序，Solid 的版本链表）。一句话判据：**glitch 是『通知的执行序』与『数据的依赖序』不同流的必然产物**——批处理治『同轮多跑』，拓扑序治『轮内半新半旧』，两味药不治同一种病。

### 7. (B) 线上报『Maximum call stack』且栈里全是 run/notify 交替，你确认代码里没有显式环。两个暗环来源怎么查？

**来源**：转述自本关 §三第 2 条的实战变体（环不总是你写的）

暗环一：**间接读**——effect 调了个工具函数，函数深处读了这个 signal（栈太长看不见那层），排查：给 CURRENT 记录注册栈（interview-sig-debug q15 钩子一的实战价值），报错时把『这条边的建立栈』一起 dump；暗环二：**computed 链回边**——A 依赖 B 的派生值、B 的派生表达式里不知何时被加了读 A 的下游缓存值（代码演化长出来的环，写它的人不知道）。通用工具化：每次 set 前沿 subs 走 BFS 看能否回到正在执行的节点（debug 模式限深 50）。教训句：**依赖图是运行时建立的，所以环也是运行时才出现的——review 代码看不出你，跑一次才炸**。

### 8. (C) 惰性 computed（dirty 标记+读时重算）对急切版省了什么、赔了什么？给一个两档表现反转的场景。

**来源**：转述自本关 §三第 4 条的双面账

省：无人读的派生全链路不计算（`heavy = computed(() => bigList().filter(...))` 定义了不用=零成本）+中间层可短路（a 变但 b 的谓词没变，c 读 b 不触发重算）。赔：① **首次读延迟尖峰**——一串惰性链在一次读里全部展开，UI 帧里凭空多一坨同步计算；② 实现复杂度：每节点要『当前值/脏标记/依赖版本』三态一致（Fine-Grained Reactivity 论文那套）。反转场景：**报表页**——用户点开折叠面板前没人读那 20 个派生，惰性全赢；面板展开瞬间读 20 个，急切版（早已算好）零延迟、惰性版一次集中重算掉帧——**急切赌『都会被读』，惰性赌『没人读』，流量形状定档位**。

### 9. (D) 给 mini-signal 做内存治理：subs 强引用导致 effect 永不销毁。在不引 WeakRef 的前提下给两条工程修法，并说明工业库为什么可以理直气壮用强引用。

**来源**：转述自本关 §三第 5 条与 L7 坑3 层级化拥有

修法一：作用域树——effect 挂到当前 Owner（创建它的组件/批次），Owner 销毁时批量断开其下全部订阅（Solid 的 `onCleanup`+Ownership 正是此物）；修法二：引用计数终版——节点 `subs.size===0 && 无人可读` 时自杀（signals 库的 GC 策略）。工业库理直气壮的原因：**它们把『谁负责 dispose』写进了框架生命周期**（渲染树即订阅树，组件卸载=批量退订），泄漏的前提（忘记 dispose）被结构消灭——60 行版没这个结构，所以只能纪律提醒（往上看三行找配对退订）。**同一问题在库层叫生命周期设计、在应用层叫使用纪律——档位差又一次现形**。

### 10. (A) 本包的『untracked 逃生舱』（Solid untrack、MobX untrackedAction）在 60 行实现里要怎么写？它反证了追踪机制的什么本质？

**来源**：转述自本关 §一 `if (CURRENT)` 与 tc39-control/mobx 相关关节

写法：`function untracked(fn) { const prev = CURRENT; CURRENT = null; try { return fn(); } finally { CURRENT = prev; } }`——三行，本质就是把指针摘出去一圈。反证的命题：**依赖收集的唯一机制就是『这次读被谁捕获』**——不想被捕获只要让捕获者暂时不存在。所有库的 untracked 都是这个栈技巧的马甲（有的加一层『当前批次』判断）。顺手连回 L2：tc39-control 里 untracked 读用来打断 console.log 建边（sig-debug q9）——当年是 API 用法，今天知道底下真就是一个 null 赋值。

### 11. (C) 手写实现与工业库的差距清单（本关五条）里，哪条 tc39 提案明确不管、哪条基本已成共识？说理由。

**来源**：转述自本关 §三清单与 tc39-frameworks 的标准边界

明确不管：**调度/批处理与 glitch-free**——提案只定 signal/computed/effect 的图元语义，把『一轮变更怎么组织执行』留给框架（这正是各框架还离不开自己 signal 实现的原因，tc39-frameworks 的标准边界论）；基本共识：**惰性 computed+可关闭的写通知合并**——各家独立演化到同一形态（脏标记+版本号），Fine-Grained Reactivity 系论文与实战双向收敛，行业已认『急切纯直推』是玩具档。加分句：提案连 `equals` 语义都留了钩子（equals 选项进提案 API）——**对『值→变化闸门』的共识比对调度器的共识更靠前**，因为闸门是数据语义、调度是渲染性能，前者跨场景后者分场景。

### 12. (B) 你面试手写完 60 行，面试官问『为什么你的 effect 首跑在 createEffect 里立即执行，有些库却要等一帧』？两档各自服务的目标？

**来源**：转述自本关 §二 `run()` 立即调用与 §五调度关联的延伸辩

立即跑服务**正确性直觉**：effect 的依赖集要靠首跑建立（不跑就不知道读了谁——运行时追踪的鸡生蛋问题），且『副作用与状态同帧发生』符合 React useEffect 之前的心智；延迟一帧服务**合并窗口**：同帧内多个 effect 的写入风暴合一次 DOM 刷新（Solid 的 render 批次语义），且首跑延迟能避开『初始化还没跑完 effect 先炸』的装配顺序坑。工业选立即+批次补偿（首跑立即建边、DOM 写入进微任务）——两档并不矛盾，差在**把『建依赖』和『执行输出』当不当两件事拆**。能把这刀切开的候选人，这轮基本结束面试。

### 13. (D) 用 13 包依赖图语言给 MobX 画一张『它比这 60 行多出来的东西』架构图：三层各一件代表物。

**来源**：转述自本关 §三 × mobx-core 的架构合拢

记录层：Proxy/annotate 的属性级拦截（60 行只有函数级——读整个 signal；MobX 读到 `user.name` 这一个键）——**依赖粒度从节点细到属性**是它性能账的本钱；调度层：derivation state（UP_TO_DATE/CHECK/POSSIBLY_STALE 三态机）+action 事务——§三第 1、4 条的工业答案合体（先标脏后执行的拓扑变体）；契约层：enforceActions/reaction 报错/spy 事件流——把 §三第 2 条的裸路装上护栏并对外开口（调试钩子官方化）。面试用法：背这三层=给『MobX 是不是黑魔法』的终结回答——**每层魔法拆开都是一张 60 行级别的零件图，只是拼装精度不同**。

### 14. (A) 版本号 `bump` 在本实现只是调试挂件，但工业系统里它是主角——给两个『版本号替代订阅集』的机制名与动机。

**来源**：转述自本关 §一挂件注释与 solid-internals/Fine-Grained 论文的转述

机制一：**global version + lastRunVersion**——computed 记住『我上次跑时全局版本是几』，被通知时先看版本：链路上没人动过就直接返回缓存，省掉清边重跑（pull-based validation，React 生态的 WeakMap 版本表同理）；机制二：**版本链表/依赖图节点版本号**——用『读到的源版本 ≤ 我的快照？』做惰性校验，把『通知』从函数调用降级成整数比较（Solid 的 Source/Compute 状态位）。动机一句话：**订阅集是 O(边数) 的指针游戏，版本号是 O(1) 的整数比较**——60 行不需要它因为图小到无谓，1500 行的世界每条边都在抢帧预算。

### 15. (C) 收官辩题：『人人都该手写一次 mini-signal』——用本关体验给正方两条、反方两条，最后裁决适用人群。

**来源**：转述自本关全篇的立场自反（§三/§四的合题）

正方：① 闸门/批处理/拓扑/惰性四条从『API 名词』变『自己欠的债』（§三验尸单的说服力来自写过的疼），调试时对这些概念的调用顺序有体感；② 三行 untracked、finally 恢复栈这类『逃生舱与命门』只在手写后才会主动去找。反方：① 工程时间贵，多数人不写调度器也能用好库；② 危险的正迁移——手写版认知会让人在应用代码里炫技（自造订阅系统替代库），或高估自己『懂 MobX 了』而跳过其真实契约（action 纪律/enforceActions）。裁决：**面试准备度高的中高级前端与框架兴趣者必写一次（90 分钟+三个事故复现），业务冲刺期的人把这关当读物**——本关的价值不是造轮子，是 §四那句直觉：信号廉价、一致性昂贵——带着这句回去用四大库，每一关的重读都回本。
