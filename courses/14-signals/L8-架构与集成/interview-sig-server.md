# sig-server 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。覆盖服务端状态的缓存模型、两条状态的边界协议与框架数据层的行业终态。

### 1. (A) 面试官问『服务端状态和客户端状态的区别』——不给定义，给三个可判定的性质。

**来源**：转述自本关 §一『图书馆借来的书』的判据化

① **事实源归属**：真身在别人机器上，你只有 copy——所以一切本地修改都要经过『回源确认』环节；② **过期是常态**：别的标签页、别的用户、别的部署随时让数据旧掉，『新鲜』只是两次失效之间的暂态；③ **改法不同**：客户端事实直接 set，服务端状态只能『表达意图+等回执』（mutation）。三性质直接推出管理模型：cache + invalidation，而不是 state + setter。能报出『你的 store 里哪几个字段其实性质①』的候选人罕见——这是本题的加分层。

### 2. (B) 『用户刷新后看到了上一个账号的头像』——生产事故，用本关语言完成归因与修复。

**来源**：转述自本关 §二三段式堕落史第 3 段与 §三登出清场协议

归因：头像数据被当客户端事实塞进模块单例 store（Zustand 的 create 在 SPA 里活在整个页面生命周期），登出只清了 token，store 里的 user 字段成残留——新会话首帧读到旧值。修复三层：① 即时修——logout 函数里 `queryClient.clear()` + 各 UI store `reset()` **成对出现**（清一边=事故标配成因）；② 结构修——user 这类服务端缓存迁去 Query/框架数据层，per-request/per-session 生命周期由库托管；③ 制度修——『字段进全局 store 评审』问一句『它是传家宝还是借来的书』。顺带能讲 za-core『模块单例=SSR 负债』同根异构（一个是跨会话残留、一个是跨请求串数据）为顶格。

### 3. (A) 失效（invalidate）为什么设计成『标脏』而不是『删除』？给 UI 层的直接收益。

**来源**：转述自本关 §二四职责表失效行

删除让订阅者立刻拿到 undefined——UI 掉进空态/骨架屏，一次无关操作引发全页闪烁；标脏（stale-while-revalidate）保留旧值先顶着渲染、下次读/到时机再后台重取，拿到新值原子替换。收益链：**零闪烁、请求可合并（多个组件同时读一份脏数据只触发一次重取）、keepPreviousData 这类翻页体验有了地基**。手塞方案常做的『删掉+广播刷新事件』恰好集齐三个反面教材：闪烁、N 组件 N 次请求、漏订阅者旧数据永生。

### 4. (C) React Query 的 onMutate 回滚和 MobX 里手写的『乐观更新+失败还原』，本质上谁替谁管了哪笔账？

**来源**：转述自本关 §二乐观更新行与 §三协议第 2 条

Query 接管的是**快照账**：onMutate 里 `cancelQueries + setQueryData` 改缓存、返回值自动成为 onError 的还原快照——『存旧值、catch、还原』三步样板被吸进库。MobX 手写版这笔账全自担，且多数人只写了『改』没写『还原』（失败路径没测过）。归属判据背 §三那句提问：**服务器拒绝这次更新后 UI 该不该退回？该退的归 Query（远端会接受的值），不该退的归 store（本地草稿、已读即时反馈——本地值+异步落库）**。答出『不是所有乐观更新都属于服务端状态』即区分了背题者和懂题者。

### 5. (D) 设计一个文章列表页的完整状态分层：筛选条件、列表数据、页码、收藏按钮的乐观态、侧边栏折叠。五样各放哪？

**来源**：转述自本关 §三边界协议的合体应用

筛选条件+页码=客户端事实→URL 或 Zustand（要可分享进 URL，纯 UI 游标进 store）；列表数据=服务端缓存→Query，`queryKey: ['articles', filters, page]` 引用条件——参数变 key 变自动重取，同步方向永远客户端→服务端；收藏乐观态=『远端会接受的值』→ onMutate 归 Query；侧边栏折叠=传家宝→Zustand（或不进全局）。评分点在于**没有一样东西进『一个大一统 store』**，且能解释『queryKey 引用条件』就是协议第 1 条的实现形态。

### 6. (A) 竞态（后发先至）在手塞方案里为什么容易漏？Query 的丢弃发生在哪一层？

**来源**：转述自本关 §二第 2 段『手搓 requestId 比对』

手塞方案的 fetch→setState 是**单向裸奔**：响应回来时无条件写 store，两次请求乱序返回时旧响应覆盖新响应。漏的原因是『写通道上没有身份概念』——setState 不知道自己写的是哪次请求的合法结果，除非你手工造 requestId 并每次比对（每处三行样板，总有一处忘了写）。Query 把丢弃下沉到 **observer 层**：每个 query 实例追踪自己最新的 fetch 序号，过期请求的响应在写入缓存前就被判废弃——**一处实现覆盖所有调用点**。这正是 sig-mutability『闸门收拢』思想的实例：竞态防护是一个该被库收走的闸门。

### 7. (C) SvelteKit 的 load、Solid 的 resource、Next 的 RSC fetch 都在解同一题——它们和 React Query 是替代关系还是互补关系？

**来源**：转述自本关 §四『框架数据方案终态』

分层答：框架数据层接管『首屏/路由级』的取数与序列化（服务器取好→进 HTML→客户端 hydrate 成响应式源），React Query 类库擅长『交互驱动』的取数（翻页、搜索输入、弹窗详情）——同一份数据往往两者都要（load 出初值、Query 接管后续生命周期，dehydrate/hydrate 对接）。关键判断句背下来：**失效/竞态/乐观这些问题跟着数据进了新层，只是换了 API（invalidateAll/+revalidate/rerun）——Query 模型是思想不是那个包**。宣称『框架内置了所以 Query 退场』和『Query 通吃所以 load 多余』都是半句。

### 8. (B) 你的项目里有个『登录后写入、登出前不清』的用户信息 store，且用了 persist 中间件——指出双重风险与各自动机。

**来源**：转述自本关 §三协议 3 与 za-middleware 持久化边界

风险一（内存残留）：同页签登出再登录，旧 user 闪现——登出清场协议缺失；风险二（磁盘残留）：persist 把 user 写进 localStorage，**用户关掉浏览器再回来，即使从未登录，上一人的数据从磁盘直接水合进 store**——比内存残留严重一档，因为它跨会话跨标签页存活。自动机各修：协议一在 logout 成对 clear+reset；协议二给 persist 配 partialize 白名单，把服务端缓存类字段挡在持久化之外（『存储只过值』的升级版：存储不但只过值，还只过**该存的价值**）。这题考的是两个中间件/库叠加时的边界盲区。

### 9. (A) 为什么『从 useQuery 读』和『从 store 读』代码一样短，架构意义却完全不同？

**来源**：转述自本关 §二末句『组件从 useQuery 读，和从 store 读一样短，但生命周期完全不同』

API 形状趋同（都是 hook 返回值），差异全在**数据的所有权与生命周期**：store 的字段你写你负责（setter 触发、persist 冻结、跨页手动同步），是本地事实源；useQuery 的返回值是一段缓存的**当前视图**——它有出生（首次 fetch）、变质（stale）、回源（revalidate）、死亡（gc）的完整生命周期，且这些阶段库在管理、组件根本不拥有它。把这句话说完整即证明理解了『服务端状态=缓存』：**接口相同，治理不同**——就像租房和买房的门是同一款，产权证不是。

### 10. (D) SSR 应用选型评审：团队想『Zustand 一把梭管所有状态』，你作为反对者给出三条 SSR 专项论据。

**来源**：转述自本关 §五 SSR 特供三条

① 独家债：模块单例 store 在 Node 里跨请求共享，必须请求级 `createStore`+Context 注入才有正确性——这套样板 Query/框架数据层自带 per-request client，直接免疫；② 序列化墙：store 里放 class 实例/Proxy（MobX 化域模型）过不了水合，『只过值』在数据层被强制执行——手塞方案会诱导你把行为对象塞进要跨界的字段；③ 失效级联：服务端 mutation 后哪些 load/queries 要重跑是显式命题（+revalidate），store 方案里你等于在 SSR 里手工同步两份缓存（服务端一份、水合后客户端一份），竞态与一致性全裸奔。三条合讲：**SSR 把『复制+手同步』的成本放大约三倍**。

### 11. (C) 本关说『多数项目全局 store 里一半数据错位』——给一个快速审计法（不动代码，5 分钟内出结论）。

**来源**：转述自本关 §一的操作化

把 store 的初始 state 逐字段过一遍，每字段问三连：① 它的真身在不在我们后端？② 刷新页面后它的正确值从哪来（若答案『还得再拉一次接口』即错位）？③ 有没有别人（别的标签页/管理员改配置/别人的下单）会让它过期？三问全是→服务端缓存，迁移候选；三问全否→传家宝，留在 store；半是（如 user 权限：服务端真身+客户端强依赖渲染）→ 进 Query/数据层但配 keepPreviousData 与首屏预取。产出一张『字段 × 三问』表就是重构工单——**审计的价值在清单不在比例**。

### 12. (B) 团队把列表数据迁去 React Query 后，搜索框每次按键发一个请求。给三层对策并说明各层归属。

**来源**：转述自本关 §三协议 1 与 rx-inapp 的闸门家族

① 输入层（组件）：debounce/beforeIdle——把『每个按键』变成『每次意图』，这是事件语义问题归输入处理；② 参数层（store/URL）：filters 对象整体更新而非逐字段，queryKey 只依赖参与请求的字段子集（对象做 key 要稳定序列化，否则 key 永变=缓存永 miss）；③ 请求层（Query 内置）：新请求发出即废弃旧响应（§六的 observer 层丢弃）+ staleTime 给短窗口免重取。三层各挡一部分压力，**只靠 debounce 是单闸门思维**——网络抖动时按键间隔再长也可能叠加请求。能点出『queryKey 里放现造对象=缓存版坑1』为加分。

### 13. (A) 『同步方向永远是客户端→服务端』这条协议为什么容不下反向例外？草稿自动保存算不算反例？

**来源**：转述自本关 §三协议 1 与 §三协议 2 的缝合考察

协议说的不是网络方向而是**数据流方向**：客户端事实（参数/游标/UI 态）单向流入请求描述；服务端真身的当前视图单向经 Query 流出——两股流各自单向，交汇在 queryKey 与 mutation 变量处。若允许『把响应 setQueryData 之外再复制进 store』，第二条 store 副本开始独立过期，回到三段式堕落史第 2 段。草稿自动保存不是反例而是协议第 2 条的正主：草稿=『只有 UI 在乎的值』→ 本地 store 是它的**真身**（客户端事实），异步落库只是备份——服务器拒绝草稿不回退本地值。判断句：**谁是事实源，谁就有写通道的所有权**。

### 14. (C) TanStack Query 之外，RTK Query/Apollo/SWR 与框架 load 层各占什么生态位？选型一句话各给一条。

**来源**：转述自 §四的行业终态论述扩展（官方文档定位转述）

RTK Query：与 Redux Toolkit 同族，团队已有 RTK 心智则零额外概念；独立项目引它=请进一整套 store 范式（本包 za-core 的 RTK 论辩直接复用）。Apollo：GraphQL 专属，归一化缓存是核心卖点——REST 项目用它=用航母送快递。SWR：极简 cache-then-fetch 哲学，缓存共享/失效工具比 TanStack 薄——中小站够用、大项目会摸到天花板。框架 load：路由级数据+SSR 序列化零胶水，但跨路由缓存共享与 mutation 回滚需配库。一句总括：**四强在『服务端状态』赛道的差异不是有没有缓存，而是缓存治理的深度与上移程度**——和 sig-scenarios 五碗决策树里『Query 管远端』的格内细分。

### 15. (D) 让你给一个 20 万行的『store 一把梭』老项目立迁移方案：不重写业务，只治数据错位。给分期路线与每期的止损验证。

**来源**：转述自本关部署预告『统计删行数』的制度化

一期圈地：审计法（q11）产出错位字段清单，按『读写次数 × 症状频率』排序，先治事故名单上的（user/列表数据）；二期立规：新代码禁把接口响应写进 store（lint：action 里的 fetch→setState 模式告警 + code review 三问清单），存量不动——**先止血再手术**；三期逐 feature 换血：接口数据切 Query，store 里该字段退役为只读缓存或删除，每切一个跑『删行数统计』——删掉的 loading/竞态/同步代码数即该期的量化验收；四期补协议：logout 成对清场、水合白名单、key 规范进模板。全程双写过渡期不超过一个迭代（拖长=双事实源复活）。本题与 sig-migrate 直接对口，答出『量化收益驱动排期』即摸到迁移课的门。
