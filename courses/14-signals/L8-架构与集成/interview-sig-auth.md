# sig-auth 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。以登录态为标尺的四实现贴身对比，兼及会话安全与库选型的工程判断。

### 1. (A) 面试官出题『设计一个前端登录态管理』——别急着写代码，先把需求拆成几层？

**来源**：转述自本关 §一两轴拆解+kit-auth-session 包的安全/存储轴对照

拆三层：① **状态层**（本关主场）：跨页共享/路由守卫/登出清理三件事各自的读写订阅要求；② **存储层**（kit-auth-session 的主场）：token 放内存/localStorage/HttpOnly cookie 各有 XSS/CSRF 暴露面——状态层的『刷新后恢复』策略由它派生（HttpOnly cookie 方案里前端根本不需要持久化 token）；③ **协议层**：过期刷新（401→refresh→重放）、并发请求的刷新去重、多标签页同步。多数候选人死在只答①——登录态看着是状态管理题，实际一半篇幅在另两层。能主动问『用几层』的面试官是在等你拆。

### 2. (A) Zustand 版 logout 里 `queryClient.clear()` 和 `useUIStore.getState().reset()` 成对出现——为什么在 action 里用 getState 而不是 hook？这个旁路的安全边界在哪？

**来源**：转述自本关 §二 Zustand 版与 za-core getState 旁路

action 不在组件树里，没有渲染上下文可挂 hook——命令式代码要拿状态只剩两条路：参数注入或模块级旁路，getState 是后者的官方形态。安全边界两条：① **旁路读=无订阅读**，拿到的是瞬时快照，拿完就走——在组件渲染体里用 getState 代替订阅就是滥用（UI 不会跟着变，sig-perf 漏订的镜像症状）；② action 之间的互相调用形成隐式依赖网，store 多了要显式化（RootStore 式组装或事件单向），否则『谁 clear 谁』半年后没人记得。

### 3. (C) 四份答卷里 RxJS 版行数最多且心智最重，但 §二说它在『登出清理』上反超——给一个具体场景证明这个长板不是硬凑的。

**来源**：转述自本关 §二 RxJS 版与 §四形状滑动

场景：企业 IM 的登出=断开 WebSocket + 清 Query 缓存 + 停三个定时器 + 未读草稿落盘 + 跳转登录页，且要求**部分失败也要走完清场**（不能因草稿失败残留半登录态）。RxJS 表达：`logout$.pipe(switchMap(() => forkJoin([ws$, clear$, ...]).pipe(catchError(allSettled))))` 一行编排带超时/重试/兜底。另三份写成 async 函数要手搓 Promise.allSettled+取消逻辑——能写，但每家的取消姿势不同（AbortController/reaction dispose/observable 退订），四种知识各会一遍才能拼齐；RxJS 把它们归一成一个 Dispose 概念——**抽象税在这里换回了复利**。

### 4. (B) 用 localStorage 存了 Zustand persist 的整颗 auth store，安全评审打回。给两条修改意见与一条原则。

**来源**：转述自本关部署预告、za-middleware partialize 与 kit-auth-session 存储矩阵

意见一：**token 不落 JS 可读存储**——迁 HttpOnly cookie（浏览器自动带、XSS 偷不走），或至少后端签发短命 access token+refresh 轮转；意见二：persist 加 partialize 白名单，只留『非敏感偏好』（主题、侧边栏状态），user 信息改每次启动从接口重取（它是服务端缓存！sig-server q11 三问全中）。原则一句话：**persist 存的是『客户端事实』，登录态的每一项都要先过『它是借来的书吗』这道闸**——把整颗 store 冻进磁盘等于把图书馆的书全复印锁进自家柜子。

### 5. (D) 多标签页场景：用户在标签 A 登出，标签 B 还开着。四份实现各要怎么处理？谁天生占优？

**来源**：转述自本关 §一要求 3 的四实现延伸（广播通道为库外公共件）

共同底座：`storage` 事件或 BroadcastChannel 监听（哪个库都不内置，除……）——收到 logout 事件后各库动作：Zustand `setState(初始)`+跳登录页；MobX runInAction 里 reset+reaction 驱动跳转；Solid signal set(null)+绑定的 effect 翻转；RxJS 把外部事件直接 `fromEvent → merge(logout$)` **并进既有清场管道**——RxJS 天生占优就在这：对它而言『另一个标签页的登出』和『本页按钮的登出』是同一条流的两个 producer，零新增代码；其余三家要把外部事件『伪装』成本地 action 调用。但记住 §三评分表：这一票改变不了它在共享/守卫两项上的税——又是形状题。

### 6. (B) code review 抓到一行守卫代码 `const user = useAuthStore().user`（在 react-router 的 data 路由函数里）。指出双重错误。

**来源**：转述自本关 §一『守卫等不了 hook』与 za-core 旁路纪律

错误一：hook 只能在组件渲染期调用，守卫/路由函数里调用直接违反 Rules of Hooks（运行时抛 invalid hook call 或拿到假上下文）；错误二：即使换成 `useAuthStore.getState().user` 修好语法，也要追问第二层——守卫要的是**同步无订阅读**，getState 正确出口；但若在组件里也这么写（用 getState 代替订阅），UI 就不跟登录态联动了。一行代码两种病：环境非法+出口选型问题，面试官考的是你对『同一状态的两种读法』的条件反射。

### 7. (A) MobX 版说『组件 observer 包裹后解构都敢用』——这句话对登录态成立、对域模型未必成立，边界条件是什么？

**来源**：转述自本关 §二 MobX 版与 sig-perf 坑2 漏订三式

成立条件：**解构后仍然在渲染期重新读取**——`const { user } = auth` 后 JSX 里写 `{user?.name}` 没问题（读发生在 observer 的追踪窗口内，因为解构本身发生在渲染体首行）；但两个场景破功：① 解构后把值存进闭包变量延迟到事件回调里比较（读订阅已失效，回调拿到的是过期快照）；② 域模型里解构的是**实例引用**（`const { orders } = user` 后对 orders 做过滤派生）——派生发生在解构出来的裸引用上，脱离 observable 代理树（mobx-react 面试的实例解构案）。登录态是纯值快照所以安全；『敢用』的边界=解构对象是不是 observable 本身。

### 8. (C) Solid signal 版 12 行拿下最小代码，但 §三给它标了唯一一个『反向锁定』——这单生意到底划不划算？分两种项目回答。

**来源**：转述自本关 §三三角评分与 za-core 框架内置论辩

划算的答法（新建中小型 SPA、技术栈未定）：12 行白捡框架原生响应式，无第三方库供应链风险（sig-size 的账：依赖数减一），锁定『框架』在 Solid 这种全栈一体框架里迁移成本≈整个前端重写——但反过来说选 Solid 那天你已经接受了这条锁链，登录态不是新增的债。不划算的答法（React 存量团队）：为 12 行的诱惑上 Solid=重写全部；在 React 里引 signal 库复刻（25 行+胶水）**既付了锁定库的钱又没拿到框架内置的免息**——两头税都交，本关表里最差的格子。一句话：**反向锁定的价值取决于你是否本来就在这个框架里**。

### 9. (D) 给一个 Next.js SSR 应用选登录态方案：框架有 load/RSC，四强还上场吗？给分层裁决。

**来源**：转述自本关 §二四答卷与 sig-server §五四框架数据层的合体题

裁决三层：① **服务端侧**：HttpOnly cookie 里的 token 根本不进任何状态库——RSC/server action 里直读 cookie，四强在这一层全体缺席（框架数据层『拉数据放哪』答案的上移版）；② **客户端镜像**：`user` 展示态由 RSC 序列化进 Initial Proposal、水合后进 **Zustand**（低频、纯值、需要 getState 旁路给客户端守卫）——四强里只有它为『镜像+旁路』这个最小需求定价，MobX 太重、RxJS 太弯、signals 库在 React 里是两头税；③ **守卫**：服务端 middleware 读 cookie+客户端路由守卫读 Zustand getState，两道闸各查各的（客户端守卫是体验不是安全）。本题陷阱：把『选哪个库』当全题——SSR 下登录态问题一半不在客户端库里。

### 10. (B) 线上偶发：用户刷新页面瞬间闪一帧『请登录』按钮，随后又变成用户名。四实现里哪些会得这个病？根因与通用修法？

**来源**：转述自本关部署预告实验（跨用户残留的近亲：未就绪态闪现）

病根相同、家谱不同：persist 水合是异步的（ZA 的 skipHydration/rehydrate 时机）、MobX 的 RootStore 从 localStorage 恢复发生在首个 effect、solid 的 signal 初值同步但接口验证在 effect、RxJS 的 BehaviorSubject 初值 null 而恢复逻辑在订阅回调——四家全可能得。通用修法两条：① 状态加 `status: 'unknown' | 'authed' | 'guest'` 三值，unknown 渲染骨架而非任何一极（**消灭布尔两难**——根因是把『还没查清』错误编码成『没登录』）；② 有 token 时首帧直接从存储同步恢复渲染，接口验证失败再回退（乐观显示）。此题的分数在『说出 unknown 这个第三态』，不在背某库 API。

### 11. (C) 本课给登录态排名（React 语境）Zustand 居首；但 sig-scenarios 五碗口诀说『Query 管远端』——user 信息明明是远端数据，为什么没判给 Query？

**来源**：转述自本关 §二与 sig-server §三协议 1 的边界缝合题

精细切分正解：『当前 user 档案』确实是服务端缓存，**该进 Query**（`queryKey: ['me']`，登出随 queryClient.clear 一起清）；留在 Zustand 的是它的两个近亲——token（凭证，不参与渲染的客户端事实，persist 白名单另议）与 `status` 三态（UI 状态机）。§二示例把 user 简化进 auth store 是教学压缩，生产代码按此三线拆分。本题考的是**状态颗粒度**：一个叫『登录态』的东西至少含凭证/缓存/状态机三种性质——面试官问登录态设计，听到你把一个词拆成三样归属的，可以直接进二面。

### 12. (A) RxJS 版守卫要手写 `getValue()` 被记了一笔『手工税』——但 BehaviorSubject 的 getValue 和 Zustand 的 getState 机制地位不同，差在哪？

**来源**：转述自本关 §二与 sig-vs-streams 海关论辩

机制上都是『流的当前值同步快照』，地位差在**谁是第一公民**：Zustand 的状态本体就是那个对象，getState 是正门、hook 订阅是同一个对象的响应式出口——两种读法读的是同一份事实；RxJS 的本体是流（过程），getValue 是对流『冻结取帧』的旁路——用得多说明你的需求根本不是流（低频、当前值语义），你却在流范式里生活。海关论辩的落地：**signal 状态是『现在是什么』，stream 的 getValue 是『把过程偷拍成照片』**——税不在代码行数，在范式错位的认知开销。

### 13. (D) 需求变更：登录态要支持『同端互踢』（新设备登录旧设备下线）。在四份实现的架构上各加多少东西？

**来源**：转述自本关 §四形状滑动的预演应用

机制统一：服务端推送下线事件（WebSocket/SSE）→ 客户端触发登出编排。差异在『事件进来后』：RxJS 版几乎免费——`serverKick$.pipe(switchMap(logout$))` 又一个 producer 并入现有管道（§五的形状反超现场）；Zustand 版写一个 `logout(reason: 'kicked')` action，由推送回调 getState 旁路调用，免费程度第二；MobX 加 action+联动 reaction 若干；Solid 加 signal set+effect。但注意暗坑三家共有：互踢和主动登出**共享清场逻辑但 UI 文案不同**（『账号在别处登录』）——登出要参数化成单一入口，否则两套文案两套清理必分叉。本题真正考点：需求形状从『低频状态』向『推送驱动事件流』滑动时，评分表如何跟着翻转。

### 14. (B) 安全审计问：『你们的路由守卫在前端，绕过它只要手敲 URL+改内存』——怎么答才算懂行？

**来源**：转述自本关 §一定位与 kit-auth-session 信任边界（本关语境转述）

标准答案三句：① **客户端守卫是体验不是安全**——它挡住的是误入的正常用户，挡不住攻击者；② 安全边界在服务端：每个接口校验 token/session，越权在服务端 401/403，前端的职责是**把 401 转译成路由动作**（弹登录）；③ 所以本关四份实现的真正安全权重在登出清理与失效处理是否完整（残留比绕过更危险——绕过只看到公开壳页，残留会把上一用户数据递出去）。能把『前端权限管理』的热题冷答成信任边界题的，此题满分。

### 15. (C) 收官讨论：本课结论『排名是背答案，形状才是考纲』——用登录态需求本身反推：它为什么恰好是个『形状温和』的题？找一个形状暴烈的对照需求。

**来源**：转述自本关 §四方法论的自反考察

登录态温和在它同时踩中四家的公约数：低频变更（流范式不吃亏也不占优）、纯值快照（不可变派生）、全局单例（无实例图需求）、同步读刚需（各家旁路方案都廉价）——四份卷都能及格，差异只是税单厚薄。暴烈对照：**协同编辑器光标位置**——高频（每秒十几次）、必须丢帧（debounce/throttle 内建需求）、跨组件细粒度订阅（每个 remote user 一个信号）——Zustand 版当场解体的地方（通知风暴）恰是 signals/Jotai 原子化主场，MobX 类实例网反而顺手。面试配方：**先说需求三条形状特征，再说这些特征给哪家的公约数加分/减分**——本关教的是这个动词，不是四行代码。
