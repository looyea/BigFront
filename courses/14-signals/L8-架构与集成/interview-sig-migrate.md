# sig-migrate 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。覆盖渐进迁移工程学、多库共存边界与验证安全网。

### 1. (A) 『把 Redux 迁到 Zustand』——开口先说什么？给迁移立项的三个正当理由与一个不成立理由。

**来源**：转述自本关 §一

开口先算『凭什么迁』：正当理由①重渲风暴治不好（Redux 订阅面默认整 state 粒度，useSelector 补救有天花板）；②样板债重到 RTK 也压不住（动态 reducer、typed middleware 连锁）；③团队主动换范式（往 signals/细粒度走，Zustand 是中间站）。不成立理由：『Zustand 更时髦/star 增长快』——sig-size 的先测量再吵架在此复诵：先拿自己项目的订阅面事故单和 bundle 报告说话。第二句才是总纲：20 万行重写=用新 bug 兑换旧 bug，渐进、可回滚、每步可验证。

### 2. (B) 双写桥运行两周后，发现同一个 slice 在新旧 store 里数值分叉了。给排查路径与最可能的两个成因。

**来源**：转述自本关 §二双写桥三纪律

路径：① 先定分叉方向——打两份 getState 快照 diff，看是旧有新无（漏同步）还是两边各有对方没有的（双写入口失守）；② 漏同步查桥的触发点：桥挂在 subscribe 上但某些更新走的是 `store.setState` 直改（Redux 里等价于绕过 dispatch 改 state）或异步 action 完成后的补偿写入没经过 reducer 广播；③ 各有分叉查是否违反纪律①——有组件同时写两家。最两成因：**写入口没收敛**（新组件『顺手』也写旧家）与**桥只过值漏了派生字段**（旧家的 reselect 派生没镜像）。修完把『写入口收敛』做成 lint：迁期中 grep 到对门 import 即报警。

### 3. (A) 『桥只过值不过行为』——为什么不许把 dispatch 转发给 Zustand？传 action 对象算行为吗？

**来源**：转述自本关 §二纪律②与 za-middleware 存储边界

转发 dispatch=同一次意图在两家 reducer 各重放一遍：两家状态更新逻辑从此耦合，改一处忘另一处→分叉；更坏的是一次 UI 操作触发两次『状态变更事件』，审计环/devtools 里双倍记账（za-middleware 时间旅行事故的跨库版）。传 action 对象**作日志载荷**（只读、不参与对门决策）不算行为——判据是**对门拿到它是『存起来/看一眼』还是『执行它’**：执行即行为。这条边界和 persist 白名单、水合序列化是同一原则（只过值不过行为）在迁移场景的分册。

### 4. (C) saga 的迁移为什么单列『最难啃』？给三档处置与各自的适用信号。

**来源**：转述自本关 §二中间件对号入座

难在 saga 不是『发请求的中间件』而是**副作用编排语言**（takeLatest、race、fork、channel——语义对标的是 RxJS 管道），翻译错=并发行为悄悄变了且没有类型系统兜底。三档：① 降级为 async 函数+ AbortController——多数 takeLatest/race 场景，请求编排简单时首选；② RxJS 化——channel/takeEvery 等真流语义，搬进 rx 而不是塞进状态库（sig-vs-streams 海关的位置）；③ 保留 saga 暂不迁——编排复杂度高且该 feature 稳定运行，**不动它比译错它便宜**。适用信号看该 saga 文件的 effect 组合深度，不看行数。

### 5. (D) 一个 30 万行 Redux 应用的 state 树迁移分批方案：给出排序模型与首批选择。

**来源**：转述自本关 §二、§五的排期化应用

排序模型=两轴四象限：横轴『改动频率』（近期迭代多的先迁，反正要动代码）、纵轴『事故/性能症状分』（订阅面重灾区先迁）；**双高象限为首批**（通常是列表页/编辑器这类高频+风暴区），双低象限（稳定的低频 slice）最后甚至永久保留——迁移预算花在收益上。切流维度用 feature 而非目录层级：一个 slice+它的读写组件是一个搬迁原子。首批外先做两件地基：共存规则 lint（新代码禁进 Redux reducer）+渲染计数基线跑全页（给后续每个 PR 对账）。加分句：给整个项目预设『终点快照』（哪些永远留在 Redux 也算完成），无终点迁移=烂尾工程。

### 6. (B) 迁到 Zustand 后功能全对，但低端机上列表页比 Redux 版慢 40%。按本关 §五与 sig-perf 给归因链。

**来源**：转述自本关 §五兜底 2 与 sig-perf 坑1 的合体案

迁移翻车的典型不是坏而是慢——归因链：① Profiler 数 commit：Redux 版每更新 N 组件重渲、Zustand 版是不是反而更多；② 若是，抽组件看 selector——迁移时的机械翻译最常写 `useStore(s => s.articles)`（对应旧版 mapStateToProps 整段），而 Redux 版里 connect 的浅比较兜住了数组引用不变的情况，Zustand 版同款写法直接全列表重渲；③ 查派生：旧版 reselect 记忆化选择器搬家时变成组件内现造 filter（坑1 的『产物现造』）。修法背 za-patterns：窄原子 selector+派生进 store 算好。教训制度化：**渲染计数基线本该在 PR 阶段拦住这类翻译**——安全网第 2 条存在的全部理由。

### 7. (C) Context→外部 store 的引入判据里，『订阅面=整棵树』说是结构缺陷——给一个不用换库也能续命的缓解手段与其天花板。

**来源**：转述自本关 §三判据①与 react 基础包的 Context 优化常识

缓解：Context 拆分（读多写少的值与频繁变的值分两个 Context）+消费组件 React.memo+把 setState 下推到叶子组件本地——能把『集体重渲』压成『局部重渲』。天花板两处：① memo 靠 props 引用比较，Context 值一旦是现造对象（`{{a,b}}`）全部失效——纪律成本随组件数线性涨；② **出树不可达无解**：拦截器/守卫/回调里拿不到 Context，这是 §三判据②存在的根因——结构缺陷只能缓解不能消除，两条天花板各对应一类项目：组件树浅而稳的续命够用，树深+跨界读取多的该引库。

### 8. (A) MobX+Zustand 共存为什么『glitch 出现在库的接缝上』？用一个 10 行内的事故脚本说明。

**来源**：转述自本关 §四反模式①

脚本：MobX action 改 `order.status` → reaction A 里 `useUiStore.setState({ badge: toJS(...) })` → Zustand subscribe B 里又 `order.touch()` 改回 observable。两次通知各自库内合法（MobX 批量结束、Zustand set 完成），但**跨库没有统一事务**：subscribe B 触发时 MobX 已进下一批、reaction A 尚未跑完的中间值被 B 读到——组件在这 0 帧窗口渲染出 status 旧+badge 新的缝合态。单库内各家自研的一致性算法（MobX 推导状态机、signals glitch-free）保护不了跨库边——**接缝无主权**。这就是合规接口必须『单向、显式、过值』的机理版答案。

### 9. (D) 老板问『MobX 域模型团队和 Zustand 平台团队要不要统一成一个库』——用本关框架给决策报告提纲。

**来源**：转述自本关 §四分工线的组织化应用

提纲：① 先破『统一=更好』默认值——分工线本身成立（网→MobX、树→Zustand，sig-scenarios 五碗各归各位），为组织清爽牺牲架构正确是反模式 2.0；② 共存的真实成本清单：接缝协议（单向显式过值+文件头注释）、两套 devtools 的心智、招聘培训面——逐项给缓解方案而非删除方案；③ 判『要不要统一』的唯一硬指标：**过去 4 个季度跨库接缝出过几起事故**——≥3 起说明边界没划死（先修协议再谈统一），0 起说明共存已工程化（统一纯属烧钱）；④ 若必统一，给出迁向哪边的理由（域模型复杂度是搬不走的那座山，通常向 MobX 收敛成本更高——用 sig-mutability 两税账说话）。

### 10. (B) 迁移收尾评审发现：桥全拆了，但 tech-debt 看板还挂着『某组件仍读旧 Redux 死 slice』。给两种处置与选择判据。

**来源**：转述自本关 §二第 3 段的收尾变体

处置甲：该组件补迁——若它读的死 slice 还剩别的活消费者，说明拆slice不彻底，按 feature 原子性原则回去补完；处置乙：接受孤儿——Redux 整树留着一个只读 slice+最小 store，登记永久例外。**选择判据=孤儿面积的延伸速度**：还有写入路径（哪怕间接）→必迁（写入=双事实源复燃），纯只读且数据来源已断（reducer 不再被任何 action 触达）→可留。加分点：能问『这组件为什么在最后一批』——通常是跨 feature 的公共壳（布局/导航），它读多个 slice 导致原子切流时无法归属——这正是按 feature 切流的已知盲区，解法是把壳依赖的字段投影进 Zustand（过值、单向），而不是壳迁就全家桶。

### 11. (C) 12/13 包的迁移课（路由迁移/框架迁移）与本课状态迁移共享的方法论内核是什么？状态迁移特有的新增难点在哪？

**来源**：转述自本关 §一总纲与全仓迁移课的横向收拢

共享内核五件：渐进切流（strangler pattern）、双写/适配层、开关回滚（flag 在手）、等价性验证（对拍/快照）、终点定义（防烂尾）。状态迁移特有难点两个：① **切流粒度被运行时耦合绑架**——路由可以按 URL 前缀切（请求级隔离），状态的消费者关系是编译期+运行时双重网状，一个组件读两个 slice 就没法原子切（q10 的孤儿即此症状）；② **性能回归无功能症状**——路由迁移错了立刻 404，状态迁移错了是 commit 数悄悄涨（§五基线的存在理由）。能答出『状态层的 strangler 没有天然的流量入口可挂 flag』即抓住本质差异。

### 12. (A) 对拍比对器为什么写成『reducer-of-states』而不是逐字段 assert 的测试用例集？

**来源**：转述自本关 §五兜底 1

逐字段 assert 是**枚举式**证据：只能证明你想到的字段；对拍是**全射式**证据：同一操作序列→两个终态对象→深度 diff 自动暴露你没想到的分叉（迁移中最怕的恰是没想到的）。reducer-of-states 指比对器自身是纯函数（操作序列进、diff 报告出），因此可以：录制生产/预发的 action 日志回放、CI 里跑随机操作序列（property-based 味）、同一剧本对拍多版本。成本 50 行——性价比来自『不用想该测哪些字段』。

### 13. (D) 给你一个新项目定『状态架构宪法』：三条条款内同时覆盖服务端数据、Context 使用、多库共存。各写一条并注来源关卡。

**来源**：转述自本关 §三§四与 sig-server §三的本关合体立法

条款一（数据归属，源 sig-server §三）：接口响应一律进 Query/框架数据层，全局 store 收单禁——store 里只准放『刷新后还需要从接口重新确认的东西除外项』；条款二（共享分级，源 §三）：Context 只服务低频全局配置，出现『高频变化值进 Context』或『出树读取需求』即申请引入轻量 store；条款三（跨边协议，源 §四）：任何两状态系统间的数据流动必须是单向、显式调用、过值不过行为，且这条边写进两端文件头注释——评审看注释，无注释的跨边按事故处理。宪法的共同内核：**每一条都在给『隐式』定罪**——隐式双源、隐式订阅、隐式跨边。

### 14. (B) 迁移期中途要 hotfix 一个『两条阵地都有』的字段 bug，流程上怎么办才不开双写口子？

**来源**：转述自本关 §二纪律的临场应变版

流程：① 定性——该 slice 当前处于桥的哪一段（旧为源？新为源？），**唯一写入口在哪边，fix 就只在那边改**，桥负责把修复后的值带过界；② 若两边都在写（桥设计失误已被现实抓住），先临时冻结新侧写入（flag 回退读旧），fix 旧侧，热修复走稳态通道；③ fix 合入后补一条对拍剧本锁该字段（防『修好又分叉』）。反模式：同一个 fix『两边都改一遍保险』——手写双份逻辑是桥失效的开始，两处 diff 会随后续迭代指数漂移。这题的分不在 fix 本身，在**有没有把『唯一写入口』当成迁移期最高宪法**。

### 15. (C) connect→useSelector、Redux→Zustand、类组件→函数组件三件事都堆在一个季度——用本关语言给排期裁决与理由。

**来源**：转述自本关 §二第 3 段『两件事别捆一起上』的组织应用

裁决：拆成三条串行线，顺序=**Redux→Zustand 的 slice 迁移打头，connect→useSelector 随迁的组件顺手做（同一 PR 里两件事天然耦合：反正要改这个文件），类组件→函数组件最后且可永久部分豁免**。理由用验证语言说：每件事都会弄脏『渲染计数基线』这条证据线——捆一起跑，commit 数变了无法归因给谁（sig-perf『一次只改一处』的排期版）；slice 迁移放最前因为它对基线冲击最大（订阅面重划），先动大刀再看小刀漂移。一句话总纲：**并行的是代码区（不同 feature 互不相干），串行的才是风险线**——这是『按 feature 切』升到项目排期层的同构应用。
