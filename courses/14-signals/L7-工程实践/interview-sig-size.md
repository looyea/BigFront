# sig-size 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。覆盖前端状态库体积账、tree-shaking 与预算治理。

### 1. (A) Tree-shaking 生效需要哪些环节配合？缺一环时用户看到的现象分别是什么？

**来源**：转述自 rollup/webpack 文档与社区通识

四环：① ESM 静态导入（CJS require 混入→整包难摇）；② 库侧 sideEffects 标注正确（包没标或误标→打包器不敢摇）；③ 生产模式+压缩器 dead code 移除（dev 构建看着没摇以为坏了）；④ 导入方不写坏 import（barrel/重导出层把图焊死）。现象各不同：②不摇出全家桶、③dev 体积吓人到 prod 才缩、④单文件复发全项目沦陷——体积排障先定位缺哪环再骂库。

### 2. (B) 同事说『Zustand 才 1KB，上三个中间件能贵到哪去』，用体积账驳（给量级不给精确数）。

**来源**：转述自本课 §二与 Bundlephobia 口径

三件套真账：persist+devtools+subscribeWithSelector 各 ~1KB 级，但 immer 中间件连带 immer 本尊 ~5-6KB gzip——全开 ≈8-10KB，核心价的 8 倍量级。更隐蔽的『贵到哪去』在依赖面：immer 同时被 Redux Toolkit 复用（同版本共享则递减，版本分裂则翻倍）。金句：**按支计价的前提是你数清了每支的价格**。

### 3. (C) MobX 摇不动树、『入场即全家桶』，而 RxJS 能摇到用法价——两家源码结构差在哪？

**来源**：转述自两家包结构与 bundle 讨论

MobX：observable/action/computed/reaction 共享同一反应内核（derivation/atom/prop_ 互相 import），功能面耦合进一张图——摇掉任何一角都可能断链，打包器只能保守全留；RxJS：操作符是独立纯函数（各自 import 核心类型），使用面=依赖面子图，天然可摇。结构决定体积行为——顺带给『17KB 买全』正名：耦合紧也是运行期内存共享与行为一致的原因，**体积账与架构账同源不同向**。

### 4. (D) 给一个低配安卓 WebView 内嵌页做状态层体积预算：给流程与三档结论模板。

**来源**：转述自弱网/低端设备实践

流程：列功能必用清单→三方案凑齐各报真实构建价（visualizer，含传递依赖）→低端机实测运行账（内存/首渲，sig-perf 工具）→预算分档：① <5KB 硬约束→框架内置信号或 Zustand 核心+手搓必要件；② 10KB 级→Zustand 三件套或轻量 signal 库；③ 不设限→按需选型，体积降参考项。关键点：**低配场景体积升回决定项是本关口诀的反例运用**——口诀服务场景不是反过来。

### 5. (A) `sideEffects: false` 标错（其实有副作用）与漏标（其实没有），各会造成什么事故？

**来源**：转述自 webpack 文档与库翻车案例

标错：打包器摇掉『看起来没人用』的 polyfill/注册代码——运行时 undefined 炸且只在 prod 复现（最难查的一类）；漏标：不敢摇、体积虚胖——只是钱的问题。库作者视角：标注是**契约**，测试要含摇后 smoke（bundle 产物 grep 关键副作用码）；用户视角：怀疑被错标时查 issues 并临时 `optimization.sideEffects` 排除该包保命。

### 6. (B) CI 体积门禁上线后，PR『size +3.2KB 红』，本次改动只是把某组件从 Context 迁到 Zustand。可能原因列三个查证动作。

**来源**：转述自 size-limit 实践事故单

① 新 store 文件顺带 import 了重件（该页首次拉进 immer/lodash）——查 visualizer diff；② 迁移让原本可摇的旧路径失效（新 barrel index.ts 把全家桶带进图）——查 import 链；③ vendor 分块策略变化（新依赖改变了 chunk 归属，数字搬家不是新增）——对比分包 manifest。门禁的红只是报警器，**三个查证动作把『谁贵了』变成一句话结论**——这题考的是读体积报告的基本功。

### 7. (C) 把 gzip/min/brotli 三个口径混着比较是常见错误——说清各自含义与正确比法。

**来源**：转述自传输编码通识

min=压缩去空白（未传输量）、gzip=老通用 deflate（Bundlephobia 默认）、brotli=现代字典压缩（对 JS 普遍再省 15-25%）。比法三纪律：同口径比（gzip vs gzip）、同构建比（都 prod+同打包器）、看真实响应头（`content-encoding` 确认 CDN 实际用了什么）。选型表里混口径=把对手的数字偷换成自己的假设——面试里能主动纠偏『我们刚才是拿谁跟谁比来着』即加分。

### 8. (D) 面试官问『我们的 app 首包 2MB，状态库换小能救吗』——给排查剧本与回答话术。

**来源**：转述自性能治理咨询场景

剧本：visualizer 先归因（2MB 里 state 层占比通常 <2%；大头常在图表/日期/编辑器类重依赖、未懒加载路由、polyfill）→按占比给话术：『换 Zustand 省 ~15KB 占 0.7%，聊胜于无；真正的三刀是路由级代码分割/重库替换或按需/图片与依赖预算』。**状态库体积在 99% 的项目里不是战场**——敢当着面试官说『这一项不重要，重要在那三项』比背出 1.1KB 高级得多。

### 9. (A) 同一库多版本共存（monorepo 里 rxjs 6/7、immer 9/10）对体积与运行时的双重代价？

**来源**：转述自 monorepo 依赖治理实践

体积：打包器视不同版本为不同模块，两份全进包（vendor 翻倍区）；运行时：跨版本类型不认亲——rxjs6 的 Observable 不被 rx7 操作符接受、immer 双份导致 draft 标记Symbol 不同产错值。治理：根 resolutions/overrides 锁单版本+`npm dedupe`+CI 查重复包（depcheck/duplicate-package-checker）。这题把 za-middleware q10『版本时钟』从开发期账延伸到产物账。

### 10. (C) React Query ~13KB 对比 Zustand ~1KB：为什么『不贵反而省』的论证成立？

**来源**：转述自分工矩阵（sig-scenarios q7 的体积版）

同一项目若用 Zustand 手搓服务端缓存：失效、竞态、去重、轮询、加载态的自研代码+各自引的 debounce/equals 小件，累计轻易超 13KB 且带 bug 面积；Query 一挂功能打包 13KB 且消灭手写同步代码的隐性体积（代码也是包的一部分——删掉的行不占字节但占维护）。体积换算的另一面：**买功能是买『替代你自写的量』**——这题的通用版适用于一切『库好大』的争论。

### 11. (B) 上线前压体积，同事把 zustand 换成 jotai 再换成 use-context-selector『哪个小用哪个』，两轮后包只小了 2KB、bug 涨了仨。给方法论总结。

**来源**：转述自过早优化反面教材

教训两条：① 状态库间体积差（KB 级）在整包占比通常不值得迁移成本——先测占比再立项；② 体积优化 ROI 排序：删未用依赖>代码分割>替换重库>换状态库——他从列表最后一项开干。正确姿势：visualizer 照一遍，按『占比×替换成本』选前三刀，状态库换题留给架构评审——**优化要按钱办事，不是按焦虑办事**。

### 12. (A) 为什么框架『自带信号』（Solid/Preact+signals 插件）的体积故事是『零边际』？给一个例外。

**来源**：转述自本课 §二末条与两家打包文档

零边际：信号运行时是渲染器的实现内脏（反应图即渲染图），不存在『另购层』——用 Solid 就用了它的 signals，账单全在框架价里。例外：框架『可选插件』形态（@preact/signals 对 Preact 是独立依赖、Vue 的 reactivity 在 @vue/reactivity 包里被生态各取）——插件/拆分件是真增量，且多库各引一份时可能多份。边界意识：**『内置』与『官方相邻包』两种形态，体积账完全不同**。

### 13. (D) 设计一场 30 分钟的『体积工作坊』：让团队学会用工具替代嘴炮，列议程与产出物。

**来源**：转述自本课 §五流程的教学化改写

议程：① 现场 build+visualizer 出当前包图（5'）；② 每人认领一块 treemap，找『意外进包 Top3』并查 import 链（10'，经典猎物：barrel、dayjs/moment、重复版本）；③ 现场做一刀（删或换），diff 数字（5'）；④ 定 size-limit 预算与豁免流程（5'）；⑤ 归档：本包 Top3+下季目标（5'）。产出物：团队自己的『体积报告句式卡』（q10 模板的团队化）——工作坊的价值不在那次省了多少，在把『先测量再吵架』装进肌肉。

### 14. (C) 有人主张『现代 HTTP/2+缓存时代体积不重要了』，指出他对的一半与错的两半。

**来源**：转述自性能社区长期论战

对：HTTP/2 多路复用消解了并发请求数瓶颈、长缓存让二次访问接近免费。错两半：① 首访仍付全额——新用户/低端网下带宽与解析耗时线性相关（3G 低配机 100KB≈秒级）；② 体积≠只有下载：**执行与解析税**（大 JS 在主线程吃帧率）、内存税（WebView 低配机直接杀进程）——这两笔缓存救不了。判词：重要性从『唯一 KPI』降为『KPI 之一』，把『不重要』当豁免牌才是错的。

### 15. (A) 收官：把『体积账』在本包的三处引用串成一句完整的选型观。

**来源**：转述自 za-core/sig-size/sig-capstone 三关联动

sig-size 给量级与测量方法（下载账）、sig-mutability/solid-stores 提醒 Proxy/immer 的运行时账不在字节里、sig-capstone 要求以真实项目构建+Profiler 出双账对照报告——收拢一句：**体积要量、要换算功能、要分开下载账与运行账三件事各归各位，谁替谁说话都是耍流氓**——面试答状态库选型时以这句开场，后面的每个数字都有了坐标。
