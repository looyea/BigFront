# 四强定位图：各自解决什么问题

> 目标：一张定位图说清四位选手**各自的第一性产品**——TC39 Signals 是语言原语标准化尝试（不是状态库）、RxJS 是事件流的代数系统（不是状态库）、MobX 是业务域对象建模框架、Zustand 是 React 的最小共享 store；顺带划清常见误用边界（把 RxJS 当 signal 用、把 Zustand 当服务端缓存用），并发出本包 27 关的学习地图（呼应 sig-paradigms、sig-scenarios）

## 一、先破一个混淆：四家不在同一个赛道

把四家摆上"库的野心"光谱，误会立即消解：

```
语言原语 ←──────────────────→ 应用框架
TC39 Signals      RxJS      Zustand      MobX
(定义积木)     (流处理库)  (React 状态库)  (完整状态解决方案)
```

- **TC39 Signals 不是库，是提案**：它只规定 `signal()/computed()/effect()` 的语义标准，不含 store、不含 devtools、不含 React 绑定。它的用户是**库作者**——目标是 @vue/reactivity、solid-js、preact/signals、MobX 的追踪内核将来能说同一种语言。日常业务开发者"用"它，目前多半是通过实现了它的框架间接用（L2 详谈）。
- **RxJS 不是状态管理库，是工具库**：官方定位就是"使用异步集合编程的工具"。它能兼职做状态（BehaviorSubject 存最新值），但那是在用螺丝刀敲钉子——能用，但不是它的设计目标。它的核心资产是**上百个操作符构成的事件代数**和类型安全的组合能力。
- **MobX 和 Zustand 才是真正的"应用状态管理库"**，只是哲学相反（可变自动追踪 vs 不可变显式订阅）。

## 二、四位选手的一句话档案

### TC39 Signals：响应式的"普通话"

**解决**：每个框架自造一套响应式原语，库作者要发 N 个适配包的碎片化问题。**产品形态**：signal/computed/effect/watch 五个原语的标准语义 + 一份参考实现。**现状一句话**：提案 Stage 1 推进中，Angular/Preact/Solid 语义高度同源但都未直接采用其实现——标准化的是概念，还不是代码（L2 整关展开）。**选它的理由**：你在写的库想一次适配多框架，或你想学"最纯粹的 signal 语义"再横向理解各家变体。

### RxJS：时间轴的代数

**解决**：手写事件流逻辑（去抖+竞态丢弃+重试+组合）命令式代码不可维护的问题。**产品形态**：Observable + 操作符 + Scheduler，一套对"带时间的序列"做 map/filter/switch 的函数代数。**现状一句话**：7.x 稳定、体积大幅可摇树化；热度相对峰值回落，但"复杂事件处理"领域仍是事实标准，Angular 全家桶把它锁为默认依赖。**选它的理由**：WebSocket 消息流、复杂搜索竞态、拖拽手势、事件编排——凡是"事件间关系"多的场景。**不选的理由**：只是存个共享状态——那是另外两位的活（L3 整关）。

### MobX：给业务对象装上响应式神经

**解决**：复杂业务域（编辑器、看板、ERP 单据）里对象图之间大量派生与联动，Redux 式扁平化建模写不动的问题。**产品形态**：observable 自动追踪 + action/computed/reaction 纪律 + 对象图建模，一个完整的状态解决方案。**现状一句话**：6.x 起默认要 observer 包裹组件，性能与心智都稳定，企业级应用（尤其复杂交互后台）基本盘稳固。**选它的理由**：你的状态本质是**有行为的对象图**（Order 有 customer、lines、totals，还要互相联动）。**不选的理由**：状态只是几个共享标量——重了（L4 整关）。

### Zustand：React 共享状态的最小可行解

**解决**：Redux 的样板税 + Context 的粗粒度重渲 + 组件外读写订阅的需求，三者交集。**产品形态**：`create()` 出一个组件外的 vanilla store + `useSyncExternalStore` 绑定 + selector 细订阅；中间件生态（persist/immer/devtools）按需拼装。**现状一句话**：5.x 稳定，React 社区新增项目的默认选项之一；与框架绑定但 store 本体可脱离 React 用。**选它的理由**：跨组件共享的是**扁平快照型状态**（用户偏好、弹窗开关、购物车摘要），你要的是十分钟上手。**不选的理由**：深度对象图联动（MobX 的地盘）或需要事件时序代数（RxJS 的地盘）（L5 整关）。

## 三、需求语句→工具的反查表

面试和工作里最快的选型沟通法，是把需求翻译成一句话再看表：

| 需求原话 | 首选项 | 为什么不是别人 |
| --- | --- | --- |
| "三个组件共享一个侧栏开关" | Zustand（或干脆 Context） | MobX 重、RxJS 绕、Signals 没 React 绑定 |
| "搜索框：去抖+竞态丢弃+失败重试" | RxJS（或 fetch+AbortController 手写） | signal 表达"时间关系"要写不少命令式代码 |
| "订单对象改一处、五个面板联动刷新" | MobX | Zustand 做深层对象图的派生联动会很累 |
| "我要写一个跨 Vue/React/Solid 的响应式动画库" | Signals 语义（或各家适配） | 原语层标准化正是为此而生 |
| "接口数据缓存+失效" | **都不选**：React Query/SWR | 服务端状态不该塞进客户端 store（L8 专关） |

第五行故意留个"都不选"——**状态管理选型的最大失误率不在四强之间，而是把服务端缓存状态错放进任何一家客户端 store**。这条边界 L8 sig-server 整关处理。

## 四、本包学习地图

- **L1（本关所在）**：全景与坐标系——已就位。
- **L2 Signals**：提案语义三关：核心 API → 订阅控制 → 各框架现状。它排最前，因为 signal 概念是读懂 MobX/Solid/Svelte 响应式的通用语言。
- **L3 RxJS / L4 MobX / L5 Zustand**：三家各三关，主流用法为限（"不用整的太复杂"是本包纲领导向）。
- **L6 横向对比**：signal vs stream、可变 vs 不可变、选型决策树——把 L2-L5 的样本抽象成判断力。
- **L7 工程实践**：体积、调试、性能坑——生产环境里真正咬人的三件事。
- **L8 架构集成**：服务端状态边界、迁移共存、登录态四实现。
- **L9 终战**：手写 mini-signal 内核 + 四实现对照大题 + 复盘。

> 🚀 部署预告：库的选型还会影响构建产物布局——Zustand store 模块若被大量页面 import，会进入共享 chunk；MobX 领域对象图常与业务组件强耦合，代码分割时容易形成循环依赖。L7 sig-size 用真实构建产物演示怎么看待这些边界。
