# sig-map 面试题精选

> 共 15 题。A 类=原理机制；B 类=实战排坑；C 类=横向对比；D 类=场景设计。来源为一线面试与社区答疑的高频主题转述。

### 1. (C) TC39 Signals、RxJS、MobX、Zustand 四者能互相替代吗？给出你的定位模型。
**来源**：本包开篇定位题的面试化转述。

不能互替，因为不在同一层：Signals 是**原语标准**（给库作者的积木）、RxJS 是**流工具库**（时间维度的事件代数）、MobX 是**完整状态解决方案**（可变对象图+自动追踪）、Zustand 是 **React 最小共享 store**。替代关系只发生在同层内部：Signals 语义 vs MobX observable vs Vue ref 是同类竞争；RxJS 与 AsyncIterator/Rx -lite 竞争。答出"层"即过线。

### 2. (A) TC39 Signals 提案的交付物到底是什么？"标准化"标的是什么？
**来源**：https://github.com/tc39/proposal-signals 主题转述。

交付物是 signal()/computed()/effect()/watch() 的**语义规范**（惰性求值、即时一致、订阅自动追踪、清理回调契约）加一份参考实现；标的是行为而不是代码——各家实现可以继续是自己的引擎，只要语义兼容。现状是 Stage 1 推进中，Angular/Preact/Solid 语义高度同源但均未直接采用其实现。

### 3. (B) 团队新人把"用 RxJS 管全局状态"写进了架构方案，你评审时说哪三个反对点？
**来源**：RxJS 误用高频社区答疑转述。

① 状态语义错配：全局状态要的是"当前值+可预测更新"，BehaviorSubject 的 complete/error/多播语义全是额外负担；② 调试与团队心智：流组合器的调用栈对不熟 RxJS 的同事等于黑盒，事故定位成本高；③ 体积与绑定：为一部分共享态引入整个库，而 Zustand 1KB 级解决同一问题。正确用法是保留 RxJS 处理**真事件流**（WebSocket、手势），状态交回状态工具。

### 4. (A) Zustand 的 create 为什么能"没有 Provider 也能全局共享"？这带来什么好处与风险？
**来源**：https://zustand.docs.pmnd.rs/getting-started/introduction 主题转述。

模块顶层的 `create()` 返回的 hook 闭包捕获了模块级单例 store，任何 import 它的组件订阅的是同一个实例——无需 React 树内的注入点。好处：组件外（事件总线、路由守卫、测试）可 getState/setState/subscribe；风险：真·全局单例，SSR 多请求会共享状态，需要 createJSONStorage 每请求新建或用 context 包装的 provider 模式。

### 5. (C) MobX 与 Zustand 都叫状态库，"建模世界观"层面的区别是什么？
**来源**：两派文档对照题；https://mobx.js.org/ 与 https://zustand.docs.pmnd.rs/ 主题。

MobX 的世界观是**领域对象**：Order 类有字段有方法、对象图互相引用、行为贴着数据走；Zustand 的世界观是**扁平快照**：一串可序列化的 state 键值+改它的函数，数据与行为可分离、形状自由。推论：需要"订单改价、五个面板联动"→MobX 顺手；需要"状态可持久化可回放"→Zustand 干净。混用不出错，但一套心智贯穿一个 feature。

### 6. (D) "跨标签页同步主题偏好"的需求，四家各自怎么接？谁最省事？
**来源**：工程场景小题转述。

Zustand：persist 中间件接 storage 事件或 shared worker，十行内；MobX：onSnapshot/patch 写 storage+监听回灌，也不难但要自管循环更新防护；Signals/RxJS：都得自己包一层"signal ↔ storage"桥并处理跨页广播。结论：这是 Zustand+persist 的靶心场景，其他三家都是"能做但都要手搓胶水"。

### 7. (A) 为什么说"RxJS 在 Angular 里是默认依赖"不代表"状态管理该用 RxJS"？
**来源**：技术栈绑定误区题。

Angular 选 RxJS 是因为其**依赖注入+变更检测**体系需要统一的事件流抽象处理输入/HTTP/路由器输出，官方文档也明说"RxJS 不是 Angular 专属"；但 Angular 自己近年推 signals 做**状态**、把 RxJS 定位回**事件流处理**——连母框架都在纠偏。答题引用这个信号，说明分得清"框架惯性"与"最佳实践"。

### 8. (B) 面试白板：用一句话给每个候选库写出"第一性用途"，并各说一个最常见的误用。
**来源**：定位压缩表达题（快节奏轮次高频）。

Signals：响应式**积木的标准语义**——误用：等业务状态库等它的 devtools（它不提供）；RxJS：**带时间的事件处理代数**——误用：当 signal 存状态；MobX：**对象图的自动联动引擎**——误用：三个布尔开关也建 store；Zustand：**React 的最小外部 store**——误用：把接口缓存塞进去（该 React Query）。四句话全部命中即满分。

### 9. (D) 你们项目"用了 Redux 又用 MobX 又用 Context"，重构机会你怎么抓？
**来源**：技术债治理实战题。

先分类症状：三套并存通常不是决策而是历史沉积。动作：① 盘点每处状态按"性质"归层（组件态出全局、服务端态进缓存层、共享 UI 态一家、领域对象一家）；② 立规矩：新代码只准用该层的钦定工具；③ 迁移按 feature 走双写桥。最后给管理层的说法不是"统一"而是"每层一个工具、层间边界清晰"——技术选型题升级成架构治理题。

### 10. (C) 库选型时"框架无关性"为什么对 Signals 和 RxJS 是卖点、对 Zustand 是短板？什么时候这卖点不值钱？
**来源**：可移植性权衡题转述。

RxJS/Signals 语义不绑任何渲染框架，逻辑层可跨 React/Vue/Solid 复用，甚至 Node 端能用；Zustand 的 React 绑定 hook 层价值正在 React 生态里。不值钱的场景：单框架公司、终身只维护一种栈的应用——此时框架无关性带来的收益趋零，不如选绑定层做得最顺手的。答题关键：**把可移植性换算成组织概率，不当教条**。

### 11. (A) "把接口数据缓存进 Zustand"为什么被反复点名？正确的职责切分是？
**来源**：https://tkdodo.eu/blog/ 服务端状态系列主题转述。

服务端数据的真值在远端，本地只是**会过期的缓存**——它需要失效策略、重取时机、加载/错误态、去重竞态，这些 Zustand 一概不管，手搓等于重写劣质 React Query。切分：客户端态（本地是真相：弹窗、草稿、主题）归 Zustand/MobX；服务端态（远端是真相）归缓存层。一句话：**"谁拥有真相"决定"谁拥有状态"**。

### 12. (B) 面试官追问："MobX 能做的 Zustand 也能做，为什么还要 MobX？"你的正面回答？
**来源**：库等价性争论实战转述。

能做什么 vs 做起来顺什么是两回事：深层对象图的联动（computed 链、按字段订阅）在 Zustand 里要手工拆切片+多 selector+useShallow 伺候，且不可变更新对大对象图是持续的结构复制负担；MobX 的代理追踪把这些变成默认行为。反过来小标量共享 MobX 也"能做但丑"。加分句：当你的状态**天生是对象图**，选错范式的成本每周都会付，而不是选库那天付一次。

### 13. (D) 给一个 Vue3+React 双栈并存的组织设计"状态公共层"，你怎么做？
**来源**：跨框架组织题（signals 提案的现实用例）。

逻辑层用 Signals 语义（或跨框架兼容的 signal 库）写纯状态与派生，框架侧各包一层薄绑定（Vue 用 customRef/`toRef`、React 用 useSyncExternalStore 封装），业务规则零重复；服务端态统一 React Query/Vue Query 共享同一查询键规范。这正是提案"写一次、处处可用"的现实演练——但要点破成本：团队要同时维护绑定层，公共逻辑要克制住"顺手 import 框架包"。

### 14. (C) 从"上手成本"维度给四家排序，并说明为什么这个排序对团队决策常常比性能重要。
**来源**：选型现实主义题。

Zustand（半天，API 三件套）< MobX（一两天，但要跨过 observer/action/解构三道心智坎）< Signals（语言不难，但生态与"语义 vs 实现"的坑要靠踩过才懂）< RxJS（操作符心智+订阅生命周期，熟练需以月计）。性能重要的前提是团队都能写出正确代码；RxJS 新手写出的泄漏与冷流重复订阅，比库间微基准的差距贵得多——**选型是团队能力函数，不是基准测试函数**。

### 15. (A) "状态管理选型的最大失误不在四强之间"——课文这句话的完整论证是什么？
**来源**：本包核心论断转述题。

四强之间的选择差异是"风格税"：选错顶多写起来别扭、体积略大；而把服务端缓存状态塞进任何客户端 store，会同时丢失失效、重取、去重、竞态处理四件专业能力，且每一处都要手搓并出 bug——错误量级不同。推论：先划"客户端态/服务端态/URL 态/组件态"四层，再谈每层用哪家；这题的答题模板即 L8 的整包骨架。
