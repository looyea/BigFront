# nuxt-architect 面试题（15 题）

## A. 框架与路线对比

### 1. 从架构角度对比 Nuxt 与 Next.js，你会怎么给团队做选型建议？
**答**：两者能解决的问题高度重叠，建议按团队与场景而非"谁更强"来定。选 Nuxt：团队是 Vue 栈、看重前后端一体的交付速度、需要 Nitro 带来的跨平台部署自由度、不想为 RSC 边界付额外心智成本。选 Next：React 栈、需要 RSC 的首屏 JS 极限削减、深度使用某云平台（Vercel）的增量能力、生态（库/人才）更偏 React。共同前提是团队能承受 SSR/全栈的运维与复杂度——纯内部工具或不需 SEO 的场景，裸 Vite + SPA 往往更划算。**把选型写成"匹配度"而不是"排名"。**

**来源**：《Nuxt 与 Next 选型》、《全栈框架的适用边界》

### 2. RSC 与同构 SSR 分别怎么解决"客户端 JS 太多"？代价是什么？
**答**：RSC 从模型上解决——服务端组件在服务端渲染后序列化成 UI 指令下发，其代码不进客户端 bundle，天然减 JS；代价是心智复杂（Server/Client 划分、`'use client'` 边界带来的瀑布、多层缓存），调试门槛高。同构 SSR 用传统手段解决——组件双端跑，靠代码分包、异步组件、`.client` 后缀、tree-shaking 把客户端 JS 压下去，payload 传数据；代价是客户端仍要下组件 JS 做水合、hydration 有成本、payload 是隐形税。**前者从根上少生成、后者生成后再削，各有复杂度分布。**

**来源**：《RSC 与 SSR 的 JS 成本》、《水合税与 RSC 心智税》

## B. 抽象与工程原则

### 3. 什么是"把易变的藏到稳定接口后面"？Nuxt/Nitro 里有哪些例子？
**答**：这是贯穿多层的通用原则。Nitro preset 把"部署平台"（易变）藏进构建配置；`runtimeConfig` 把"环境相关配置"藏进运行期注入；`unstorage` 把"存储介质"（内存/文件/Redis/KV，易变）统一成 `useStorage` 接口；`$fetch`/BFF 把"上游服务地址与协议"藏进代理端点。好处是切换底层不动业务代码、构建环境可不含生产秘密、多环境一次构建。判断一个设计好坏，常常看它把哪些变化成功隔离到了边界。**接口稳定、实现可换，是这整门课反复印证的一条主线。**

**来源**：《依赖倒置在前端工程中的体现》、《可替换运行时设计》

### 4. 缓存—新鲜度—正确性这个三角，在各关卡里是怎么反复出现的？
**答**：几乎每个"要不要缓存"的决策都是这三方的取舍：prerender/isr/swr（nuxt-render-modes）、handler 级 defineCachedEventHandler 的 maxAge/swr/getKey（nuxt-server-routes）、routeRules 的缓存头（nuxt-deploy）、状态放 payload 还是服务端缓存（nuxt-state）、图片/字体长缓存 immutable（nuxt-styling、nuxt-deploy）。正确性红线始终优先：带身份/私密的页面宁可慢也不能被共享缓存泄露（安全线压过性能）。**"缓存越激进越快，也越容易出错"——成熟的做法是按内容性质分级缓存 + 用测试守住不该缓存的东西。**

**来源**：《缓存三角》、《分级缓存与正确性红线》

## C. 全栈与团队

### 5. 全栈框架给小团队的真正红利是什么？又会放大哪些问题？
**答**：红利是"以少人交付完整产品"：一套 TS/Vue/约定贯通前后端、类型共享、一处部署、BFF 与 runtimeConfig 把凭据与聚合干净落地、Nitro 让平台可换——过去要前端+后端+运维拼的活，现在框架做成约定。会放大的问题：职责边界容易糊（该后端校验的写到前端、该独立的逻辑堆进 server route 变成无人管的影子后端）、单仓库单部署使一次改动牵动前后端（需要更强门禁与灰度）、同构一致性与 SSR 容量的隐性复杂度。**红利属于有工程纪律的团队，风险会被无纪律放大——所以 fail-fast、纵深防御、测试左移不是可选项。**

**来源**：《全栈团队的机遇与陷阱》、《工程纪律决定技术红利》

### 6. 你如何在前后端一体的项目里保持清晰的模块边界？
**答**：①物理边界靠目录与约定：`server/**` 是后端契约面，前端只经 `useFetch`/BFF 访问，不越界直连 DB；②逻辑边界靠分层与依赖规则（表现/取数/状态/服务/数据，每层只依赖下一层，用 lint/CR 守）；③类型边界用 `shared/` 区把 DB schema、接口出入参做成前后端共享类型（改一处、两侧同时报错）；④横切能力框架化（鉴权/埋点/错误各一处实现、别处声明式接入，呼应 nuxt-fullstack-project 第 6 节）。**边界不是靠自觉，是靠"越界会编译失败/门禁变红"来维持。**

**来源**：《全栈项目的边界治理》、《类型贯通防漂移》

## D. 判断力与成长

### 7. 面对一个全新的框架（没学过的），你的上手策略是什么？
**答**：用本课程训练出的"不变量清单"去套：①它解决什么问题、相对什么方案的取舍？②渲染/执行的时机模型（构建期/服务端/客户端各跑什么）；③状态与数据怎么跨边界；④扩展点是什么（插件/中间件/生命周期钩子）；⑤部署形态与运行时依赖；⑥安全边界（鉴权/缓存/凭据放哪）。有了这张问问题的网，任何新框架都能快速定位"它对应我已有知识的哪一块、哪一块是新的"。学 Nuxt 时不断回扣 Next/Vue/Express/Vite，就是在练这种迁移能力——**学的是模型，不是某个 API。**

**来源**：《框架无关的学习模型》、《迁移式学习法》

### 8. "过早优化是万恶之源"——你在性能上如何把握"做与不做"？
**答**：先度量再动手：没有 profiling 支撑的优化多半在优化非瓶颈（呼应 nuxt-perf 第 10 题）。做的标准：有可量化收益（能改善某个 CWV/成本指标）、影响面大（高流量关键路径）、复杂度与风险可控。不做的标准：为不存在的规模设计、用可维护性换微小数字、引入缓存正确性风险（可能越权/串数据）。我会**先立预算和基线**（CrUX/Lighthouse 现场分位），把优化排进"收益/成本"队列，做完复测、数字没动的回滚。工程上真正值钱的是"知道哪些优化不该做"。

**来源**：《度量为先的性能工程》、《克制的优化》

### 9. 三层鉴权、fail-fast 配置、测试左移——这些"套路"背后的统一理念是什么？
**答**：都是**"在不可信的环境里，把正确性建立在最早能拦住它的那一层，并用自动化持续守住"**。三层鉴权：不信任浏览器，把裁判放服务端与数据层。fail-fast 配置：不信任环境一定配对，启动即断言、宁可拒绝启动也不半瘫运行。测试左移：不信任"看起来没问题"，把关键行为固化成 CI 里不可绕过的断言。共同哲学是**防御性 + 可回归**：假设一切会出错，让错误在代价最小、最早暴露的位置被拦下，并保证修过的不再回来。这是把"能跑的软件"变成"敢交付的软件"的底层心态。

**来源**：《防御性工程与可回归性》、《把正确性前移》

### 10. 如果让你从零主导一个 Vue 全栈产品的技术选型与规范，你会定哪几条"不可谈判"的基线？
**答**：①运行时：需要 SEO/首屏/一体化则 Nuxt（Vue 栈默认），否则裸 Vite+SPA，先给页面分渲染类；②安全：任何权限校验服务端成立、数据层带 owner、凭据只走运行期 runtimeConfig 注入、私有内容永不进共享缓存；③质量门禁：类型检查 + 分层测试（单测/集成契约/e2e 关键流程与 SSR 直出）+ 体积/性能预算，任一红不可合入主干；④可回滚：不可变制品 + 灰度 + 一键回滚；⑤配置分层：app.config（构建期）/ runtimeConfig（运行期）职责清晰、fail-fast 断言；⑥横切能力框架化、边界靠工具守不靠自觉。基线要少而硬，其余给团队灵活度。

**来源**：《技术基线的制定》、《少而硬的不可谈判项》

### 11. 大前端这几年从 SPA 到 SSR 复兴再到 RSC/边缘，你怎么看这波"钟摆"？下一步会往哪走？
**答**：这不是简单来回，而是**每次"回到服务端"都带着新约束**：早年 SSR 是为 SEO，今天还叠加了性能（首屏/JS 预算）、成本（serverless/边缘计费）、数据（BFF/流式）、安全（零信任前端）的复合诉求，所以演化出 RSC（少下发 JS）、Nitro（运行时可换）、流式/增量（ISR/SWR）等更细的工具。我的判断下一步集中在：①渲染进一步"按数据就绪流式化"（Streaming/RSC 融合进 Vue 阵营）；②边缘成为默认而非高级选项，框架继续把运行时抽象掉；③构建期与运行期边界更动态（编译时求值 + 运行时水合混排）；④可观测与成本驱动的工程化更吃重。钟摆还会摆，但**"理解为什么在两端之间摆动"的人不会被摆动淘汰**。

**来源**：《服务端渲染的轮回与演进》、《前端架构的下一个十年》

### 12. 作为整门课程的收官题：修完 ES→TS→Node→Vue/React→小程序→Express/Vite→Next/Nuxt，你希望学员带走的核心能力是什么？
**答**：不是背下所有框架，而是三样可迁移的东西。①**模型化理解**：任何新技术先问"时机/边界/数据流/扩展点/安全/部署"六件事，用不变量去套；②**工程判断力**：在场景、团队、成本之间做权衡，知道何时用重方案、知道哪些优化不该做、知道正确性要前移并自动化守住；③**因果思维**：绝大多数疑难来自"代码在错误的时机/错误的一侧运行"或"边界没守住"，会顺着时机与边界追根因而不是碰运气。具备这三样，框架迭代、栈切换都只是"再套一次模型"。这正是本课程全程用"Next↔Nuxt、Vue↔React、Express↔Nitro"对照学习想训练的能力——**给你的是判断力，不只是一份 Nuxt 说明书。**

**来源**：《大前端工程师的能力模型》、《可迁移的判断力》

## 补充（新专题 13-15）

### 13.  为团队写一份"前端框架选型"的决策记录（ADR）：Nuxt vs Next vs 裸 Vite，你怎么搭结构并给结论？

结构五段：① 语境——团队画像（Vue 存量 or React 存量、是否招得到人）、产品画像（SEO/首屏要求、应用域占比）、合规与部署约束（必须自托管？多云？）；② 候选与真实差异轴——不是功能表对照而是"我们的痛点谁付账"：渲染模型（RSC 深绑 vs 同构 SSR 心智统一 vs 裸 Vite 自建链路）、服务端归属（Nitro 产物级部署自由 vs 平台绑定更重）、团队栈匹配（Vue 团队学 Next 是两笔税）、生态与人才市场；③ 决策+权重理由（例：Vue 存量+要自托管可选+后台与门户混合→Nuxt，routeRules 承载双形态）；④ 被否决方案的不甘心点（React 生态的某库确实更强——用 micro-frontend/独立服务补，不推倒主线）；⑤ 复审触发器——"何时这决定作废"写死（SEO 域消失且团队转 React、框架 LTS 断供、RSC 类边界成为团队共识）。结论写法是"在我们的约束下"+30 天验证计划（两个框架各一个真实页面 spike，度量水合/取数/部署三件事的开发时耗）——用实验代替嘴辩，ADR 才不是判决书。

**来源**：ThoughtWorks ADR 实践；InfoQ《选型报告的有效期》

### 14.  前端团队往全栈演进的两年：能力、流程、on-call 怎么建？哪一步最容易翻车？

能力线（按依赖排序）：Node 运行时与 HTTP 基础→Nitro/服务端路由与中间件心智→数据层（连接池、事务、migration 是三门课不是看文档）——最容易翻车的一步恰是"会写 handler 就以为会后端"：SQL 注入、无索引慢查询、migration 锁表三连在第一个季度集中爆发。流程线：server 代码评审加"数据/接口契约"双检（DB 变更走 review+回滚预案）、危险操作门禁（生产 DB 访问与 migration 执行权限和前端部署权限分离——全栈化不等于权限大一统）、故障复盘同锅（前后端同仓故障没资格说"这是服务端的问题"）。on-call：SLO 定义从页面可用性扩到接口错误率/延迟，值班培训含 DB 与连接池排障（不是只回滚前端），新手期"双人放行"（发布带 reviewer、SQL 带 DBA 审）。心理安全：给"第一次把生产库删了"的人以非惩罚复盘+权限收紧的双轨回应——罚人只会让事故私下藏起来。收口句：全栈化的真瓶颈从来不是框架能力，是"对生产系统的敬畏可以速成吗"——流程与门禁就是把它制度化。

**来源**：InfoQ《全栈化一年后我们重做了一次培训》；SegmentFault《前端同学的第一次数据库事故》

### 15.  收官题：给你一个新业务（内容门户+登录应用+轻 API），从 0 定技术方案与三年演化路线，说出你的思考框架。

思考框架四步而非答案清单：① 约束先行——团队规模与栈、SEO/合规/部署硬要求、12 个月内最可能的增长方向（定"哪里必须稳、哪里允许糙"）；② 现状设计——同构 SSR 单仓起步（Nuxt 类框架把 BFF/渲染/部署一次解决），routeRules 分域（公开 SSR+缓存、应用 ssr:false、api 收口），数据模型与鉴权按"一步不错"四件套（数据边界/会话/URL 契约/可观测）Day1 到位；③ 演化预判三节点——用户量（性能债单：缓存分层、payload 瘦身、RUM 门禁）、团队（边界债单：模块化→按域拆分、契约包版本化）、能力（多形态债单：移动端 API、多租户白标按前面题的阶梯上）——每个节点写"触发信号+预案动作+粗估成本"，不承诺时间表；④ 退出机制——最坏假设"要换框架/拆后端"时迁移半径多大：组件/服务标准件化、供应商中立存储、契约文档化，让"押注框架"不滑向"押注架构"。三年视角的元认知：框架的兴衰（RSC/islands/边缘）你控制不了，能控制的是"变化来临时你有几个缝可以扭"——这门课从头到尾教的其实就是找缝：运行位置之缝、配置三与之缝、缓存键之缝、契约版本之缝。收官不是选对答案，是让选错可修复。

**来源**：课程收官视角；InfoQ《三年路线图的诚实写法》
