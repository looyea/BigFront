# nuxt-fullstack-project 面试题（15 题）

## A. 架构概览

### 1. 用 Nuxt 做一个全栈应用，你的整体分层是怎样的？
**答**：自上而下五层。①表现层：pages + components + layouts（文件路由、自动导入）；②数据获取层：`useFetch` 经 BFF（server route）取数、SSR 直出进 payload；③状态层：局部 ref、共享 useState、业务 Pinia、持久 useCookie 四级；④服务层：`server/api`（H3 handler）+ Nitro 插件初始化 + server middleware 解析身份；⑤数据/外部层：DB/Redis/第三方 API，经 runtimeConfig 注入凭据。横切关注点（鉴权、缓存、错误、SEO、埋点）分别有固定落点。这样分层的好处是每个能力只在一层实现、可测可替换。

**来源**：《Nuxt 全栈分层架构》、《前后端一体的职责划分》

### 2. 为什么鉴权要"前端 + 服务端 + 数据层"三处都做？只留服务端不行吗？
**答**：安全上只留服务端确实够（前端判定无安全效力）。但三处各有职责：前端 route middleware/UI 隐藏是**体验与成本**（不该看的不渲染、不发无谓请求、引导登录）；服务端 handler 的 requireUser/requireRole 是**唯一裁判**；数据层 scoped query 是**兜底底线**（handler 漏判也不泄露他人数据）。只留服务端会让用户对着报错页和裸 UI，且一旦某个 handler 忘记加校验就是全量泄露。判据：假设第二层不存在，第三层会不会泄露——会就说明缺了纵深。

**来源**：《鉴权纵深的必要性》、《前端权限的价值边界》

### 3. BFF（用 server route 聚合）相比前端直连多个微服务，优势在哪？
**答**：①首屏一次请求：详情页所需正文/作者/摘要服务端并行聚合，客户端一个 `useFetch`，SSR 直出且内部调用走进程内短路几乎零网络成本（呼应 nuxt-server-routes）；②凭据不外泄：第三方 key、内部地址留在 runtimeConfig 非 public 栏，浏览器只见代理路径（呼应 nuxt-runtime-config）；③裁剪 payload：只把首屏字段下发，控 HTML 体积（呼应 nuxt-perf）；④统一鉴权/缓存/错误契约在一处。代价是多一层要维护、聚合逻辑要有测试。对 SSR 应用这层几乎是必选项。

**来源**：《BFF 模式在 SSR 的价值》、《聚合层的取舍》

## B. 技术决策

### 4. 项目里哪些数据进 payload、哪些放客户端、哪些放服务端缓存？怎么决？
**答**：三个问题定夺：首屏要看吗？对所有人一样吗？会变吗？首屏要看且随身份/实时变 → SSR 取并进 payload（但用 `pick` 裁到最小）；对所有人一样且能容忍旧 → 服务端缓存（defineCachedEventHandler / isr/swr），根本不用进大 payload；首屏不要、交互后才要 → 客户端 `onMounted`/lazy 取（不进 payload，瘦身）；字典/全量列表这类"缓存型" → 留在服务端缓存层，别塞进 Pinia（否则每页 payload 重复，呼应 nuxt-state 第 5 题）。

**来源**：《数据摆放决策》、《payload 与服务端缓存的分工》

### 5. 状态选型上，你为什么把编辑器草稿放 useState 而不是 Pinia 或 localStorage？
**答**：按生命周期匹配载体。草稿要跨编辑器的几个子组件共享（局部 ref 不够），但"刷新后不必保留"（localStorage/后端是过度持久，还会引入脏数据同步问题），也不需要 Pinia 的 action/getter 复杂度——`useState` 恰好：同构、跨组件、进 payload、刷新归零。如果要求"关掉浏览器还在"才升级到 useCookie/后端。选错层要么白白增大 payload，要么丢掉本该保留的数据，所以先问"这份状态活多久、给谁用"（呼应 nuxt-state 第 2、3 节）。

**来源**：《状态生命周期驱动选型》、《别把 UI 状态塞进全局 store》

## C. 工程与协作

### 6. 横切能力（埋点、鉴权、品牌、错误上报）你怎么组织，避免散落在每个页面？
**答**：统一收进"框架扩展点"而非业务代码：埋点/错误上报做成 Nuxt 模块或插件（`defineNuxtPlugin` + `app:error`/`vue:error` 钩子，构建期注入、运行期在 runtime/，呼应 nuxt-modules）；鉴权做成 route middleware + server middleware + guards 工具，页面只声明 `definePageMeta({middleware})`；品牌/主题做成模块暴露 `useBrand`/组件 + app.config tokens。原则是每个横切点**只在一处实现、别处只用声明式接入**，新人不需要知道埋点细节就能写页面（呼应 nuxt-fullstack-project 第 6 节）。

**来源**：《横切关注点的框架化》、《声明式接入优于命令式散落》

### 7. 这个应用要长期演进，你怎么防止架构腐化？
**答**：把"规矩"变成"机器可执行的约束"：①分层依赖规则用 lint/目录约定固化（组件不直连 DB、全局样式只在 css 数组）；②CI 门禁——类型 + 单测/集成/e2e + Lighthouse/体积预算 + 私有路由 no-store 断言 + SSR 直出回归，任一红不可合入（呼应 nuxt-testing、nuxt-deploy 第 10 题）；③不可变制品与灰度让发布可回滚，敢改才不腐；④关键决策写成轻量 ADR（为什么用 isr、为什么 401 走导航）附在代码旁；⑤定期用真实 RUM/错误率复盘优先级。腐化多始于"就这一次绕过约束"，守住门禁比写文档有效。

**来源**：《对抗架构腐化》、《左移的质量门禁》

### 8. 团队里前端出身的人要维护 server route 和数据库，你怎么降低全栈门槛？
**答**：①约定收口：数据层只通过 `server/utils/db.ts` + 一组窄接口的 handler 暴露，不要求人人写 SQL；②脚手架与模板：新 CRUD 有 generator/复制模板（校验、错误、鉴权、测试一次到位）；③把 Node 基础能力课程化（本套课 node-http、node-streams、exp-validation 就是给前端的后端补课）；④类型贯通：DB schema → 接口出入参 TS 类型共享（`shared/` 区，呼应 nuxt-directory），前端调接口有补全；⑤CR 与结对，横切逻辑由 owner 把关。让"能安全改全栈"的门槛降到模板 + 门禁，而不是要求人人都精通。

**来源**：《全栈团队的降门槛实践》、《类型贯通前后端》

## D. 深度追问

### 9. 如果 NoteDeck-N 用户量涨 100 倍，架构上最先崩的是哪里？怎么应对？
**答**：按经验崩溃顺序：①数据库——详情/列表的慢查询与 N+1，先加索引、分页、读写分离、热点走 Redis（handler 级 defineCachedEventHandler）；②SSR CPU——动态渲染饱和，把可缓存内容尽量推到 isr/swr/CDN（命中不打 Node），重页面降级为静态壳 + 客户端水合数据；③缓存与 session 的单点 Redis——集群化 + 就近；④上游依赖抖动——超时/熔断/降级返回旧缓存（呼应 nuxt-error-debug 第 7 题）。扩容前先 profiling 定位，别盲目加机器（呼应 nuxt-perf 第 10 题）。真正难的是有状态部分，所以架构从第一天就要"应用无状态、状态外置"。

**来源**：《规模增长下的瓶颈迁移》、《SSR 系统的容量规划》

### 10. 同构 SSR 应用"一个 bug 在两侧表现不同"，你在本项目里怎么系统性应对？
**答**：这类问题是 SSR 框架最难缠的，应对靠三招：①把"哪段代码在哪侧跑"变成显式约定——`.client`/`.server` 后缀、`import.meta.server/client` 分支、payload 只放可序列化值（呼应 nuxt-styling 第 3 节、nuxt-hydration）；②用两侧一致的数据源——身份/配置在服务端读 cookie/env 后进 payload，客户端复用同一份，杜绝"服务端有客户端无"（呼应 nuxt-fullstack-project 第 3、4 节）；③专门的回归——e2e 断言"首屏 HTML vs 水合后 DOM 一致"、payload 形状断言、禁用 JS 仍能拿到内容（呼应 nuxt-testing 第 12 题）。把"跨边界一致性"当成一等测试目标，而不是等线上偶发再查。

**来源**：《同构一致性工程》、《跨边界 bug 的根因与防》

### 11. 从产品视角，你怎么决定一个功能用 SSR、SSG 还是纯客户端？
**答**：看三个维度：需不需要 SEO/分享、首屏性能要求、数据是否按身份/实时。需要被收录且内容公开稳定 → SSG/prerender（最快最省）；公开但会变 → ISR/swr；需要登录或有实时个性化 → 动态 SSR（配 no-store）；纯交互工具（编辑器画布、后台表格，不被收录、无 SEO 诉求）→ 可以 `ssr:false` 省服务端成本、把预算留给交互流畅度。一刀切"全站 SSR"或"全站 SPA"通常是在回避"给页面分类"这件真正该做的产品+工程判断（呼应 nuxt-seo-meta 面试第 12 题）。

**来源**：《按产品需求选渲染模式》、《页面分类先于技术选型》

### 12. 做完这一整套，你认为"全栈框架（Nuxt）"给团队的真正红利和风险分别是什么？
**答**：红利：①心智统一——前后端同一套 TS/Vue/约定、类型贯通、一处部署；②框架把 SSR/水合/路由/数据/缓存/多平台部署的脏活做成约定，小团队能以少人交付过去需要前端+后端+运维拼起来的产品；③BFF + runtimeConfig 让凭据与聚合干净落地；④Nitro 让部署目标可换。风险：①"什么都能做"导致职责混乱（该后端校验的写到前端、该独立的微服务逻辑堆进 server route）；②全栈单点——一个仓库/一次部署牵动前后端，需要更强的门禁与灰度；③同构一致性与 SSR 容量的隐性复杂度（第 9、10 题）；④团队若缺后端纪律，`server/**` 容易变成无人负责的"影子后端"。红利属于有工程纪律的团队，风险会被无纪律的团队放大——这也是本包反复强调 fail-fast、纵深、左移的原因（呼应 nuxt-architect 收官）。

**来源**：《全栈框架的红利与代价》、《技术选型与团队能力匹配》

## 补充（新专题 13-15）

### 13.  用 Nuxt 从 0 到 MVP 验证一个 SaaS 产品：哪些东西"先忍"、哪些"一步都不能错"？

"忍"的判断标准=错了能改且伤害可承受：UI 组件复用度（丑但能用）、缓存策略（先全动态 SSR，量起来再分层）、i18n/主题（结构留钩子内容先单语）、报表类低频需求（导出先人工）、测试广度（关键路径 e2e 之外忍裸奔）。"一步不错"的四件（错了会指数级变贵）：① 数据模型与租户边界——schema 可迁移但"行级缺 workspaceId"这种历史数据没法回填审计，Day1 就强制（接上题的接口形状纪律）；② 鉴权与会话——安全模型事后补丁=公开裸奔期；③ URL 与对外契约——公开的 /api 与页面路径会被第三方粘住，起版即 v1+重定向表；④ 日志与错误上报——"上线两周没留痕"的故障无法归因，Sentry+request id 第一天接。隐性第三类：产品验证所必需的度量（注册转化漏斗埋点）比任何测试都优先——MVP 的 KPI 是"学到什么"，没埋点等于白跑。反模式：MVP 期抽"通用平台层"（三个真实场景都没出现就抽象=给想象中的未来打工）。收口句：忍的是"体验与规模债"，不忍的是"安全、数据、契约、可观测"——四类债单写进仓库 README 并带清偿触发条件。

**来源**：InfoQ《MVP 的债清单怎么写》；知乎《一年从验证到平台化的 Nuxt 项目》

### 14.  产品从单 Nuxt 仓长到 15 人三团队：什么时候拆、怎么拆、拆不动时的中间态是什么？

何时拆的信号（先对齐再动手）：发布互相阻塞（本周前端想发版被后端故障卡三次）、伸缩画像冲突（报表服务和页面服务抢同一池）、权限边界清晰成团队边界（谁拥有 schema 说不清就是拆早了）、故障半径（一次误删影响全站）。拆的顺序（从最独立开始）：先异步任务/worker（无同步契约、接口天然是队列），再数据密集域服务（导出、内容管道），最后才考虑 SSR 应用群（用户路径纠缠最深）。拆的姿势：shared 里的 schema 升格为"契约包"（版本化 npm 私包，CI 跑契约兼容测试），server/ 对应模块整体搬出成独立服务+原位置留 BFF 薄转发（前端零改动，切流灰度）；Nitro 的 storage/缓存层替换成远端实现（Redis 化）是拆前的隐形前置。拆不动的中间态=模块化单仓：pnpm workspace 分 packages/domain-*、ESLint 边界规则+CODEOWNERS 划文件主权、独立部署可后置——"边界先于拆分"让拆成为可执行选项而非紧急手术。最大的坑：为了组织架构提前拆（三团队共享仓里的微服务=分布式单体），以及拆出后 BFF 层无人维护变成"接口胶水坟场"。

**来源**：《Building the Art of Scalability》拆分三轴；SegmentFault《Nuxt 大仓到第三年我们拆了两个服务出去》

### 15.  多租户 SaaS 的租户隔离与自定义：从接入到数据到运行时，给一套分层方案。

四层逐个给决定：① 身份与接入——租户识别在 server middleware 单点完成（子域→tenantId 映射/路径前缀/workspace claim），进 event.context 后所有下游只信这个来源；域名白名单与证书自动化（通配或 per-tenant SNI）是平台成本要早算。② 数据——默认行级隔离（每表 workspaceId+查询强制注入，接前两题的纪律）；强合规/大数据量租户升 schema/库级（连接路由按租户，代价是 migration N 倍与小租户资源浪费），混合策略"平台表全局、业务表按租户"。③ 运行时——配置面三级（平台默认 env→租户覆盖存 DB+缓存→用户个人偏好 cookie/payload，resolution 顺序写进文档），配额与限流按租户维度（Redis 计数，防一个租户打挂邻居=多租户的"吵闹邻居"问题）。④ 呈现与扩展——品牌走 Layer+CSS 变量（i18n 题的方案复用）、租户自定义逻辑（webhook/脚本）永远沙箱外置执行，"给租户写代码的能力"在 Nuxt 服务端内=平台级 RCE，没有第三条路。横切三件：跨租户操作全部留审计（who/when/tenant）、备份恢复按租户可独立执行（全局备份=救一个租户毁所有）、渗透用例"A 租户凭证尝试访问 B 资源"进 e2e 常跑。

**来源**：OWASP 多租户安全指南；掘金《行级隔离两年后我们上了 schema 级》
