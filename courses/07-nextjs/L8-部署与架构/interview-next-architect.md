# next-architect 面试题（15 题）

> 主题：范式理解、技术选型、演进判断与架构师视野。

## A. 范式与世界观

### A1. 用架构师的一句话概括 Next.js 解决了什么问题，代价是什么？

**答**：一句话：把 React 应用从"浏览器孤岛"升级为"服务端优先的内容分发系统"，统一了路由/渲染/缓存/部署四个断点。代价：① 心智模型复杂度暴涨——RSC 边界、缓存层级、序列化限制都是新增的认知税；② API 高速演变带来的迁移债（缓存语义近两年反复调整）；③ 对 Vercel 平台能力的隐性依赖（全功能自托管要自己补缓存层、Image Optimizer）。架构评估的铁律：没有免费框架，只有把哪种成本付给你能接受的次数。

**来源**：InfoQ《Next.js 的得与失：一份成本清单》；知乎《如何向 CTO 解释为什么选/不选 Next》。

### A2. "服务端优先"范式对团队分工意味着什么？

**答**：边界溶解与责任重排：传统"前端写页面、后端写接口"的契约分工，在 RSC 世界变成"一个团队/一个人从 DB 到按钮"——服务端组件直连数据层后，BFF 层消失，接口退居站外消费者专用（呼应 next-fullstack-project C1）。影响：① 前端要补数据建模、事务、缓存一致性功课；② 后端角色上移为平台/领域服务；③ Code Review 关注点从接口契约转向边界划分与缓存安全线。组织没准备好全栈化时，硬上 Next 会产生"前端干着后端没人接的活"的灰色地带——选型要估组织成本。

**来源**：掘金《RSC 冲击下的团队分工》；CSDN《全栈框架与 BFF 的消亡辩论》。

### A3. 从 React 演进史看，Next 的 RSC 是创新还是倒退？

**答**：是"螺旋上升"：形式上回到 2005 年的服务端渲染（PHP/JSP 模板直出），但本质上带着 SPA 时代的三大遗产回归——组件化模型、声明式 UI、Hydration/渐进增强的交互保留。RSC 真正的新意是"组件级的运行时分治"：同一棵 UI 树里服务端部分零 JS、客户端部分保留全部交互能力，这在 jQuery 时代与 SPA 时代都做不到。判断：它终结的是"所有代码必须进浏览器"的假设，而不是 SSR 的轮回（呼应 next-render-modes、react-render-model）。

**来源**：知乎《RSC：一次蓄谋已久的复古》；InfoQ《服务端渲染四十年》。

## B. 选型判断

### B1. 面试官问"为什么不直接用 Vite + Express 组合，要用 Next？"你怎么答？

**答**：组合方案能到达同样的终点，但 Next 把四个"缝合成本"产品化了：① 路由/渲染/数据一致性——手写 SSR 要自管 hydration 数据注水、路由级代码分割、流式响应（vite-ssr 讲过这些坑全是手工活）；② 缓存基础设施——三层缓存 + tag 失效自己造轮子按月都造不完（呼应 next-fetch-cache）；③ 构建产物与运行时的匹配——standalone、Image、字体链路自带；④ 社区最佳实践的收敛速度。反之当项目对缝合层要求很低（纯静态站、或前后端已有成熟分工），Vite+Express 的可控性更好。答题落点：选的不是技术上限，而是"团队当前最缺的能力由谁补齐"。

**来源**：掘金《Next 还是 Vite+后端：一次真实评估》；SegmentFault《自研 SSR 与框架方案的 TCO 对比》。

### B2. 什么信号出现时，你会建议把 Next 应用的部分功能拆出去？

**答**：四类信号：① 常驻任务/消费者——批处理、定时报表塞不进请求-响应模型，独立 Node worker（呼应 node-workers）；② 连接形态冲突——实时协作的核心链路被 Action 模型反复硌脚，实时层外迁独立服务；③ 资源画像冲突——CPU 密集渲染与 IO 密集的页面服务互相争抢扩缩容指标；④ 复用溢出——两成接口被 APP/小程序高频调用且版本节奏不同，抽成独立 API 域（tRPC/OpenAPI 定契约）。原则：先垂直切功能域、后水平分层；拆分的第一评估项永远是"事务与一致性会不会被割断"。

**来源**：InfoQ《全栈框架的拆分时机学》；CSDN《从 Next 单体里长出来的三个服务》。

### B3. 老板说"官网用 Next，管理后台也用 Next，顺便把定时任务也放进来"，你怎么沟通？

**答**：分场景给出"可以/谨慎/不要"三档并翻译成成本：官网——可以，全功能红利（SEO/图片/缓存）都吃得到；管理后台——谨慎：后台无 SEO 诉求、交互密度高，Vite SPA + 组件库可能更轻，用 Next 则要为每个页面想清楚 RSC 边界，团队若已熟 Next 则统一栈的维护红利可以抵消；定时任务——不要：没有 HTTP 入口的进程塞进框架只会催生"用 cron 调内部 API"的丑设计，独立 worker 进程 + 同一套 lib 层复用业务函数才是正解（呼应 next-deploy 能力矩阵、node-cli 进程形态）。沟通技术：给对比表不给形容词。

**来源**：知乎《如何优雅地对"全家桶统一"说不》；掘金《一个仓库三种进程形态的架构》。

## C. 演进与判断力

### C1. Turbopack 之于 Next，相当于什么之于 Vite？它为什么快？

**答**：定位上对应"esbuild/Rollup 换 Vite 打包器"的升级，但更彻底——Turbopack 是 Rust 重写的整个 webpack 后继者。快的三源：① Rust 与并行化（CPU 密度高处换语言红线）；② 增量计算——函数式增量算法（Small Web）让改动只重算依赖锥，dev 启动与热更新不随项目大小线性变慢（思想同源 Vite 的 ESM 按需，呼应 vite-intro、vite-build）；③ 与框架深度绑定，不必兼容 webpack 生态历史包袱。架构师视角的启示：编译工具链的竞赛已从"配置学"进入"算法与语言层"。

**来源**：InfoQ《Turbopack：增量打包的算法账本》；掘金《Vite 与 Turbopack 谁更谁的皮》。

### C2. "cacheComponents/use cache" 这类提案反映了对现有缓存设计的什么批评？

**答**：批评指向隐式魔法：Full Route Cache 默认按"页面有没有用到动态 API"自动决定缓存行为，新人难以预测、边界事故（用户数据被缓存串号）曾真实发生。社区与官方争论两年后方向收敛为"更显式"：在需要缓存的边界处显式标注（use cache + 生命周期/依赖声明），把"默认静态"变成"声明式静态"。这给所有框架设计上一课：**性能魔法必须同时交付可预测性，否则文档里全是免责声明**。学习策略：地基语义（安全性、失效半径）要精学，具体 API 形态预期还会塑形。

**来源**：知乎《Next 缓存设计之争评述》；InfoQ《从隐式缓存到 use cache》。

### C3. 一个 API 今天标 unstable_/experimental_，你如何使用它？

**答**：三级策略：① 默认不用——生产主链路不押注实验位（改名、语义翻转、被移除都有先例）；② 隔离评估——个人项目/内部工具开实验位收集一手体感，但把该能力包在自己抽象层后面（PPR、cacheHandler 都套一层接口），API 翻转时只改适配器；③ 决策存档——每次启用记录"收益是什么、退回路径是什么"。同款思路适用于 Vite 实验特性与 Node experimental flags（呼应 node-config 的配置纪律）。架构师的价值不在追新，而在让追新的成本可控。

**来源**：SegmentFault《experimental_ 前缀生存指南》；CSDN《把不稳定的框架能力包进自己的抽象层》。

## D. 终局视野

### D1. 前端框架会走向"两大家族 + 一个卫星"吗？谈你的框架世界观。

**答**：趋势已清晰：React 系（Next）与 Vue 系（Nuxt）各自把"服务端优先 + 文件约定 + 全栈缝合"卷成了标配（这正是本课程的包序逻辑），卫星是编译器驱动的轻量路径（SvelteKit/SolidStart——以细粒度响应式与编译期消灭运行时为赌注）。分歧点仍存：RSC 组件级分治 vs SSR 页面级同构，是两种不同的"计算回流服务端"颗粒度。世界观总结：框架竞争的主战场已从渲染性能（早已过剩）转移到**交付效率与基础设施产品化**——评价一个框架，先看它替你把多少"自己也能做但做不好"的事做成了默认值。

**来源**：InfoQ《2025 前端框架格局年度报告》；知乎《RSC 与 SSR 同构的颗粒度之争》。

### D2. AI 编码时代，学 Next 这类重约定框架还有必要吗？

**答**：换个问法：AI 能生成代码，谁对"系统为什么长这样"负责？重约定框架的价值在 AI 时代反而上升：① 约定即提示词——文件路由、段旋钮让"放对位置"有机械标准，AI 产出的结构一致性最好检验；② 认知压缩——架构师不需要读懂每行实现，靠目录结构与约定就能审计 AI 代码的落位；③ 平台闭环——部署、缓存、监控的官方链路是 AI 无法幻觉出来的基础设施。贬值的是"背 API 签名"，升值的是"边界划分、缓存语义、故障预案"这类判断力——恰是本包最后一关训练的东西。

**来源**：掘金《AI 时代还需要学框架原理吗》；InfoQ《从写代码到审架构：工程师角色迁移》。

### D3. 学完 Next，你如何规划未来 12 个月的技术纵深？

**答**：给一条"框架 → 系统 → 领域"的路径参考：3 个月内补分布式地基——缓存一致性、消息队列、可观测性三件套（OpenTelemetry），让 Next 里的每个旋钮背后都有系统原理支撑；6 个月选一个领域纵深：实时系统（WebSocket/CRDT，恰好补 Next 的短板场景）或性能工程（RUM 体系、编译优化）；12 个月做一次架构输出：内部技术评审主讲或公开写作，把"为什么选它、边界在哪、坏了怎么办"讲给同事听——讲不清就是还没懂。框架只是锚点，纵深才是护城河。

**来源**：知乎《前端三年规划的复盘样本》；CSDN《从框架使用者到方案设计者的过渡清单》。

## 补充（新专题 13-15）

### D4.  "Next 全家桶"与"前端 SPA + 独立后端 + CDN"两套架构做 TCO 对比，你会怎么列账？

**答**：账要分五栏：① 人力——全家桶单栈团队端到端交付（沟通与联调成本近乎清零），但招"懂 RSC+缓存+后端边界"的人贵且稀缺；分离制两团队接口契约成本长期存在，但人才池大；② 基础设施——Next 单部署（页面+API 一体）计费简单，独立制要 BFF/Gateway/双份 CI；③ 演化与爆炸半径——分离制后端可被第二个产品复用、独立扩容；全家桶的 DB/业务/API 同进程同部署，重业务逻辑长出来后拆分是一次真重构（要提前按 features/data 层留好切缝）；④ 性能与运维心智——全家桶白吃 SSR/ISR/图片/边缘，但缓存行为不透明（排查链路长），独立制性能优化要自建一整套；⑤ 风险——框架绑定（Next 版本演进激进、Vercel 迁移引力）vs 集成风险（分离制的 CORS/版本错位/重复实现）。结论不给标准答案：主导矛盾是"上市速度与团队一体化"→Next 赢；是"多端复用/合规隔离/重领域逻辑"→独立赢。满分句：把"框架税"与"集成税"摆进同一张表。

**来源**：InfoQ《全栈框架的真实 TCO》；知乎《BFF 与前后端分离的十年周期摆动》。

### D5.  RSC 边界、三层缓存、数据访问这三块，你分别用什么"可逆性原则"设计，让两年后想换还能换？

**答**：可逆性=把每个框架强耦合点包进自己的抽象：① RSC 边界——数据访问统一收在 features/*-data 的异步函数里（组件只是调用方），将来退回"自建 API+客户端取数"时搬的是函数不是组件；客户端岛的 props 接口先于 RSC 设计（岛只吃序列化数据），运行位置可切换；② 缓存——"缓存键与失效"只经 revalidate 封装层（tag 常量集中定义、revalidate 调用全走 lib/revalidate 清单），换 CDN/独立服务时只需重接这一层；把"页面级动态/静态"决定写进 route segment 配置文件而非代码内隐式（显式>魔法）；③ 数据访问——ORM 藏在 data 层接口后（迁移 ORM 不动调用方）、连接与事务原语单点、权限断言在数据函数内部（换鉴权供应商只动 gate 与 session 适配器）。元原则：框架能力用得越"魔法"（隐式缓存、文件约定），越要给它造一个"自己的 API 门面"——门面不是防框架，是把"换框架"从重写降级为适配。

**来源**：SegmentFault《框架深度绑定的解法》；InfoQ《架构的撤销成本》。

### D6.  三年后的 Next/Nuxt/React/Vue 会是什么样？你的预测与押注，以及"哪些人才不会贬值"？

**答**：趋势线（给方向不给时间点更诚实）：① 服务端化继续——RSC 类模型向 Vue/Nuxt 扩散（Nuxt 已在 server components 实验路线）、"运行位置"成为默认课程而非高级话题；② 构建层收敛——Turbopack/Vite（rolldown）双雄，配置驱动向编译器驱动、秒级冷启动成底线；③ 边界标准化——fetch/Web Streams/Web Crypto 跨运行时统一，"同一代码跑 edge/node/浏览器"的运行时可移植性压过框架特性；④ 状态回归两极——服务端真相+URL 公共层+岛内局部 state，大型全局 store 继续退潮；⑤ AI 工程界面进框架（流式生成 UI、server 侧 agent 与表单/Action 接线）。押注与贬值对冲：押"协议与边界"（HTTP 语义、渲染管线、流式）不押"配置项"；不贬值的资产=性能度量方法、状态归属设计、安全纵深、大规模 SSG/缓存运营——这些是跨框架的"同一门课"。收口句：三年视角里框架会换皮，但"代码在哪跑、数据谁是真相、错误谁来兜"三问永远是新项目的设计起点——答得出这三个问题的人才不会贬值。

**来源**：InfoQ《框架演化的下一个十年》；React/Vue 官方 roadmap 与社区趋势综合。
